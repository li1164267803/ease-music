## Why

曲目记录保存的是「重新解析所需的信息」而不是解析结果，因此除本地文件外的每一首曲目，能不能播完全取决于外部：插件被卸载、插件依赖的站点改了接口、网盘链接过期、手机没网——任何一条成立，用户曲库里那首歌就播不了。这与产品要解决的原始痛点「曲目因版权变动无预警消失」正面冲突：曲库里有这条记录，不等于用户真的拥有这首歌。

把音频字节落到本地，是这个承诺唯一的兑现方式。

## What Changes

- 新增**离线缓存**能力：用户对曲目显式执行「下载」，音频**原样**写入应用私有目录，曲库记录该缓存的存在与文件大小
- 播放前的解析入口 `resolveTrack` 增加缓存拦截：命中缓存则直接返回本地文件地址，**不调用来源**。播放层、曲库层、各来源实现均不改动
- 下载入口与状态呈现：曲目行、播放页、歌单页的下载按钮接上真实行为，状态区分未下载 / 排队中 / 下载中（带进度）/ 已下载 / 失败
- 歌单支持整批下载（设计稿已有该按钮位）；下载任务串行排队，失败的单首不影响其余
- 曲库「已下载」分类接上真实数据，替换当前的「离线缓存将在后续版本提供」占位
- 缓存管理界面：显示总占用，支持删除单曲缓存与清空全部缓存
- 本地文件来源的曲目不提供下载入口——它的音频本来就在设备上，再复制一份纯属浪费
- 从曲库移除曲目时，连带删除该曲目的缓存文件（**这是应用自己产生的文件，不是用户的原始文件**）
- 缓存文件的存在与否不改变曲目的任何其他行为：元数据、封面、歌单归属、失效标记都不受影响

### 非目标

| 不做                               | 原因                                                                                                                                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **自动缓存播放过的曲目**           | 已决策排除。它必须配套容量上限与淘汰策略，否则会无声吃满用户存储；且自动缓存与手动下载在界面上必须区分（自动的可被淘汰、手动的不能），工作量约翻倍。手动下载的行为完全可预期，先把它做扎实 |
| **总容量上限与 LRU 淘汰**          | 已决策排除。用户显式下载的东西被应用擅自删掉，恰恰破坏了离线缓存要建立的那份信任。应用只负责把占用摊开给用户看，删不删由用户定                                                             |
| **转码、码率选择、音质切换**       | 原样落盘。转码需要原生音频处理能力，与 PRODUCT.md 中已排除的「均衡器 / 音效」属同一类成本                                                                                                  |
| **115 网盘曲目的缓存**             | C5 尚未启动，该来源在系统中还不存在。但本能力按**来源无关**设计，C5 接入后无需改动即可获得缓存能力                                                                                         |
| **缓存文件加密或对系统媒体库隐藏** | 文件落在应用私有目录，已不出现在系统相册/媒体扫描中。额外加密对本产品的威胁模型没有收益，只增加读写成本                                                                                    |
| **跨设备同步已下载内容**           | PRODUCT.md 已将多设备同步整体排除                                                                                                                                                          |

## Capabilities

### New Capabilities

- `offline-cache`: 曲目音频的本地缓存——下载的触发与生命周期、缓存优先的地址解析、下载状态与失败处理、缓存的查看与清理、缓存与曲目记录之间的一致性

### Modified Capabilities

- `music-library`: 「曲目移除」当前要求移除操作 MUST NOT 删除设备上的原始文件。需要区分「用户的原始文件」与「应用为该曲目产生的缓存文件」——后者在移除曲目时应当一并清除，否则会留下永远无法从界面触达的孤儿文件

## Impact

**新增**

- `src/cache/`：缓存目录管理、下载执行与排队、缓存记录仓储
- 数据库迁移 version 2：新增缓存记录表（曲目 id、文件路径、字节数、完成时间）。已发布的 version 1 不改动
- 缓存管理界面（挂在「我的」页）

**改动**

- `src/sources/resolve.ts`：解析前查缓存。这是 C1 决策 4 预留的拦截点，播放层无需改动
- `src/library/actions.ts`：移除曲目时清理其缓存文件
- `src/app/(tabs)/library.tsx`：「已下载」分类接真实数据
- `src/app/player.tsx`、`src/app/playlist/[id].tsx`：下载入口与状态
- `src/domain/model/track.ts` 不变——缓存状态是曲目的**外部**事实，不塞进曲目记录，否则曲库的每次查询都要背上一个与曲目本身无关的字段

**依赖**

优先使用既有的 `expo-file-system`（已在用于封面与插件代码落盘）完成下载与文件管理，避免为此引入新依赖。其下载能力是否满足进度回调与断点需求，在 design 阶段确认。

**平台**

两端一致。插件曲目仅存在于 Android，但缓存层不认识来源类型，iOS 侧不需要任何裁剪处理。
