## Context

动机见 `proposal.md - Why`。本文只写实施所依赖的现状与约束。

前两片留下的地基，本片直接复用：

- **候选曲目分页页** `/plugin-discovery/tracks`：参数 `platform`、`kind`（`toplist` | `sheet` | `album` | `artist`）、JSON 序列化的条目；`fetchTrackPage(plugin, kind, item, page)` 返回 `{ items, isEnd }`。
- **候选曲目**（`CandidateTrack`）与 `toCandidateTrack`：畸形条目丢弃、主键拼接 `sourceKey`；入库走 `addCandidateTrack → addTrack`，按 `(sourceId, sourceKey)` 去重。
- **统一调用通道** `invokePlugin`：未实现 / 抛错 / 超时 / 畸形四类故障归因为 `PluginCallError`。
- **裁剪线**：发现层界面全部在 `src/plugins/screens` 与 `src/plugins/ui`，只被 Android 侧引用。

歌单体系（`playlist` spec 与 `playlist-repository.ts`）的既有事实，是映射决策的依据：

- 歌单是纯本地对象：`id`、`name`、`createdAt`，加 `playlist_tracks(playlist_id, track_id, position)` 关联表。没有来源字段，核心层不引用插件模块。
- `addTracksToPlaylist(playlistId, trackIds)`：追加到末尾，`INSERT OR IGNORE` 让重复加入成为无操作且不移动既有条目，返回实际新增数。
- 曲目去重在曲库层：`addTrack` 对同一 `(sourceId, sourceKey)` 返回既有记录。插件卸载后曲目保留（`plugin-source` spec）。

协议侧本片新接入的两个方法（对齐 MusicFree 公开规范，只参考协议不复制代码）。提案阶段已在 Node 里用两个样本插件跑通：

| 方法                        | 输入                                  | 返回                                                                       | 样本实测                                                                                                                                                                           |
| --------------------------- | ------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `importMusicSheet(urlLike)` | 分享链接、含链接的分享文案或纯数字 ID | **曲目数组**（插件自己翻完全部页）；不识别输入时返回 `false` / `undefined` | 网易：链接、分享文案、纯数字 ID 均识别，200 首 0.5 秒；不识别时同步返回 `false`。小蜗：识别链接与纯数字 ID，但对真实歌单也返回**空数组**——它内部把上游请求失败吞掉了（插件侧问题） |
| `importMusicItem(urlLike)`  | 同上                                  | **单个曲目对象**；不识别时返回 `false` / `undefined`                       | 网易：识别单曲链接，返回与搜索结果同形的条目。小蜗未实现（`hints.importMusicItem` 为空数组，方法不存在）                                                                           |

两个样本都声明了 `hints.importMusicSheet: string[]`（如「APP 点击分享，然后复制链接」「直接输入纯数字歌单 ID 即可」）。**同一串纯数字两个插件都接受**，这是决策 5 的直接依据。

## Goals / Non-Goals

**Goals:**

- 映射决策落成一条 spec 要求与一段设计理由，后续不再讨论。
- 批量入库与链接导入共用同一个「候选曲目列表 → 目标歌单」动作，两条来路只是候选曲目的来源不同。
- 曲库侧的批量入库放在核心层且不引用插件模块：它对本地文件批量导入同样适用。
- 不新增故障处理路径：取页与解析链接都经 `invokePlugin`，只多一种「不识别」的合法回答。

**Non-Goals:**

- 不给歌单加任何来源字段、订阅状态或刷新动作（决策 1）。
- 不做跨插件的链接归属猜测（决策 5）。
- 不改 `invokePlugin` 的超时取值；`importMusicSheet` 在插件内部翻页可能超过 15 秒，见 Risks。

## Decisions

### 决策 1：导入是快照，产物是普通本地歌单

**本质与信号**：外部歌单导入是对「把别处的一组曲目变成自己的」这一需求的反馈。系统里对「自己的」已有最精确的表达：曲库记录（按插件主键去重）加歌单关联（有序、多对多、`INSERT OR IGNORE`）。这两样东西合起来已经完整表达了「一组有序的、属于用户的曲目」，导入只需把候选曲目灌进去，不需要任何新状态。

因此：导入生成的歌单不记录来源、不跟随外部更新、不依赖插件存在。「更新」由用户再导一次实现——曲库去重保证不产生重复记录，`INSERT OR IGNORE` 保证既有条目不动、只追加新增——零新增状态就得到了手动同步。

**备选 A：订阅型歌单**（记录来源凭据，进入时或定期刷新）。未采纳，三个独立的理由：

1. 与产品承诺相悖。本项目解决的原始痛点是「歌会消失」；跟随外部更新的歌单正是外部一删、本地就少的东西。
2. 违反架构约束。歌单在核心层，刷新要调插件；iOS 上插件模块整个裁掉，订阅型歌单在那里是一个永远刷不动的死对象。
3. 要在歌单上加来源字段、刷新状态、冲突规则（用户手动调过顺序之后外部又变了怎么办），每一条都是新的判定分支。

**备选 B：只批量入库、不生成歌单**。未采纳：来源列表的顺序与分组正是用户要的东西，丢掉它们批量入库就退化成「一次点几十下加号」。

### 决策 2：批量入库先取完整个列表，取不完就不入库

候选曲目页只加载了用户滚到的那几页。「全部加入歌单」的语义是整个列表，因此动作开始时按插件的分页表示逐页取到 `isEnd`，全部取到之后才入库。中途任何一页失败即中止、不入库、报告是哪个插件在取第几页时出了什么问题——半个列表悄悄进了歌单，用户既不知道缺了哪些也无法补齐；报错重试则一切清楚。

页数上限：`MAX_PAGES = 100`。它防的是「插件永远回 `isEnd: false` 且每页内容相同」这一种情况（第一片 spike 记录过不分页插件对任何页码返回同一整页，只是它们不给 `isEnd`，已被缺省规则覆盖）。触顶时按 spec 只导入已取部分并在结果里明说。

**备选：只入库已加载的页。** 未采纳：入口叫「全部加入」，做成「加入已加载的」是文不对题；且用户无法从界面上知道「已加载」到底是多少。

### 决策 3：曲库侧新增一次事务内的批量入库，放在核心层

`track-repository.ts` 新增 `addTracks(inputs: NewTrack[])`：一个排他事务内逐条「查既有 → 不存在则插入」，返回与输入等长、保持顺序的 `{ track, created }[]`。`addTrack(input)` 改为 `addTracks([input])` 的单元素包装，避免两份相同的插入逻辑。

`library/import.ts` 新增 `importCandidates(candidates, target)`，`target` 为 `{ kind: 'new'; name } | { kind: 'existing'; playlistId }`：先 `addTracks`，再 `createPlaylist`（新建时）与 `addTracksToPlaylist`，返回 `{ playlist, added, duplicates, addedToPlaylist }`。名称为空白时返回失败且不入库（spec「空歌单名」）。

放在核心层的理由：批量入库对本地文件导入同样有意义，而且 `CandidateTrack` 本来就是核心层的类型；它不引用 `src/plugins`，裁剪守卫不受影响。

事务的理由：几百条曲目在自动提交模式下每条一次落盘，实测量级是秒；事务内是毫秒级。这不是优化偏好，是「入库阶段没有可取消窗口」（proposal 非目标）成立的前提。

**备选：界面循环调用 `addCandidateTrack`。** 未采纳：几百次往返、几百次落盘，且中途失败会留下半个列表——与决策 2 的「要么全进要么不进」矛盾。

### 决策 4：一个「加入歌单」目标弹层，两条来路共用

新增 `src/plugins/ui/import-to-playlist-sheet.tsx`：输入是候选曲目的**获取方式**（一个返回 `CandidateTrack[]` 的异步函数）加默认歌单名；弹层内部完成取页进度、目标选择（新建：名称输入，默认值为来源标题；既有：歌单列表）、入库、结果三段状态。候选曲目页传「取完整个列表」的函数，导入页传「返回已解析的列表」的函数。

弹层自己持有全部状态、自己调 `importCandidates` 与 `notifyLibraryChanged`，对外只暴露 `visible` / `onClose`——与 `NameSheet`、`ImportSheet` 的既有写法一致。

**备选：候选曲目页与导入页各写一个弹层。** 未采纳：目标选择、进度、结果三段状态完全相同，只有候选曲目从哪来不同。

### 决策 5：链接导入由用户指定插件，不跨插件猜测

导入页 `/plugin-discovery/import`：顶部一行插件胶囊（只列声明了任一导入能力的插件），其下按所选插件的能力列「歌单」「单曲」两种模式胶囊，再是输入框、该插件该模式的 `hints` 文案、「解析」按钮。结果区是候选曲目列表（歌单模式）或单条候选曲目（单曲模式），列表上方有「全部加入歌单」。

理由：两个样本插件都接受纯数字 ID，同一串数字无法判断属于谁；就算只看链接，用户粘贴的分享文案格式也完全由插件决定。让用户指定插件是唯一没有歧义的做法，而且 `hints` 本来就是按插件写的粘贴说明，只有选定插件后才有东西可显示。

**备选：粘贴后依次试每个插件，取第一个识别的。** 未采纳：纯数字 ID 的归属会取决于插件的安装顺序；且每个不识别的插件也可能先发一次网络请求（小蜗对纯数字 ID 就会），耗时叠加。

### 决策 6：「不识别」是协议的合法回答，与「畸形」分开归因

协议约定导入方法对不属于自己的输入返回假值（样本实测：网易 `false`、小蜗 `undefined`）。`invokePlugin` 的 `parse` 对此不返回 null，而是返回带标记的结果：`{ recognized: false }` | `{ recognized: true; items }`。只有既不是假值又不是数组（歌单）/ 对象（单曲）的返回才归为 `malformed`。

界面对三种回答各给一句话：不识别 → 「插件「X」无法识别这个链接，请核对上面的粘贴说明」；识别但空 → 「没有取到任何曲目」；失败 → `PluginCallError` 的原文。

**备选：把假值也归为畸形。** 未采纳：用户粘错链接是最常见的情况，报「插件返回了不符合协议的数据」会把用户引向错误方向。

### 决策 7：能力判定与提示进 `PluginMeta`

`PluginMeta` 增加 `canImportSheet`、`canImportItem`（判据同前两片：方法是否存在）与 `importHints: { sheet: string[]; item: string[] }`（读 `hints.importMusicSheet` / `hints.importMusicItem`，只收字符串元素，其余丢弃）。`manager.ts` 增加 `importingPlugins()`；发现首页的「没有可用于浏览的插件」判断改为把导入能力算在内，入口按能力显示。管理页的能力描述补「导入歌单」「导入单曲」。

**备选：界面直接读插件对象的 `hints`。** 未采纳：`hints` 是未校验的 `unknown`，上层只接触 `PluginMeta` 是 C6a 定下的边界。

## Risks / Trade-offs

- **`importMusicSheet` 在插件内部翻页，大歌单可能超过 15 秒** → 超时按既有规则报失败，用户看到「超过 15 秒未返回」。本片不改超时取值；若验收中样本插件的真实歌单频繁超时，在实施记录里写明并作为校准依据（C6a 已把校准列为待定项）。
- **小蜗的 `importMusicSheet` 对真实歌单返回空数组** → 这是插件侧吞错的结果，本片按「识别但没有曲目」如实呈现；验收用网易做正向用例，小蜗做「识别但空」用例。
- **批量入库几百首后曲库列表与歌单列表要刷新** → 沿用 `notifyLibraryChanged`，一次通知。
- **一次事务内几百次查询与插入** → 排他事务内毫秒级；`reorderPlaylist` 已是同类写法。
- **默认歌单名与既有歌单重名** → `playlist` spec 允许重名，不处理；用户在弹层里可改名。
- **iOS 待复验**：本片全部界面在裁剪线之内，`check:ios-strip` 在产物层面验证；`addTracks` / `importCandidates` 在核心层，两端共用，Android 验收覆盖其逻辑。

## Migration Plan

无数据迁移。歌单表与曲目表结构不变；`addTrack` 的签名与行为不变。

## Open Questions

无。映射决策见决策 1；两个协议方法的形状与三种回答已用样本核对。
