## Why

发现页顶部那块「最近播放」是设计稿从一开始就画好的位置，现在摆的却是**最近添加**——C1 实施时刻意没拿别的数据冒充它，在 `src/app/(tabs)/index.tsx` 留了一行注释把这笔账挂到了 C3。

这不只是一处对不上设计稿的文案。用户重新打开应用时最想接上的是「刚才在听的那些」，而「最近添加」回答的是完全不同的问题：一个反映听的行为，一个反映导入的时间。曲库积累到几百首之后，两者会彻底分叉——半年前导入、每天在听的那首永远排不进「最近添加」，而昨天批量导入却一次没点开的三十首会把它整个占满。

## What Changes

- 新增**播放历史**能力：曲目开始播放时记录一次，界面据此呈现「最近播放」
- 每首曲目在历史中只有**一条**记录，重复播放更新其最后播放时间并累加播放次数——不保留每一次播放的流水
- 历史只保留**最近 N 首**，超出的自动丢弃
- 发现页的「最近添加」换成「最近播放」，兑现设计稿；历史为空时（新用户、刚清空过）回退到最近添加，不给一块空白
- 曲目从曲库移除时，其历史记录一并清除
- 提供两种清理方式：从最近播放中移除**单条**记录，以及清空全部历史。两者都只删记录——曲目留在曲库里，设备上的文件一律不动

### 非目标

| 不做                                               | 原因                                                                                                                                                                                                         |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **歌词显示**                                       | 原 C3 把歌词与播放历史捆在一起，本次拆开。两者不共享数据、不共享界面、也不共享技术风险（歌词的难点在 `.lrc` 的编码与时间轴方言），捆在一个 change 里只会让 proposal 的论证分裂成互不相干的两段。歌词单独立项 |
| **播放次数排行 / 「最常听」**                      | 本次的表结构已经存了 `play_count`，做得出来，但它是一块独立的界面与产品判断（榜单取多少首、按什么周期、放在哪一屏）。等「最近播放」跑一段时间、确认数据可信之后再评估                                        |
| **听歌时长统计 / 年度报告**                        | 需要记录每一次播放的**时长**而不只是发生时间，与「每首只留一条」的存储形态直接冲突。真要做得先改回流水式记录，属于另一次决策                                                                                 |
| **跨设备同步历史**                                 | PRODUCT.md 已将多设备同步整体排除                                                                                                                                                                            |
| **按听歌行为做推荐**                               | 产品定位是不被算法安排。历史只用于「用户自己回看自己听过什么」，不喂给任何推荐逻辑                                                                                                                           |
| **区分播放来源**（从歌单播 / 从搜索播 / 从缓存播） | 记录来源能支撑「继续听某个歌单」这类功能，但那是队列恢复的能力，与历史是两件事                                                                                                                               |

## Capabilities

### New Capabilities

- `playback-history`: 播放行为的记录与回看——何时算一次播放、同一首重复播放如何合并、保留多少、历史的呈现与清空，以及历史与曲库记录之间的一致性

### Modified Capabilities

- `music-library`: 「曲目移除」目前规定了移除时要清除哪些应用自身产生的数据（缓存音频、提取的封面）。播放历史是同一类应用派生物，需要一并纳入该要求

## Impact

**新增**

- `src/history/`：播放历史的记录与查询
- 数据库迁移：新增播放历史表（曲目 id 为主键、最后播放时间、播放次数）
- 清空播放历史的入口

**改动**

- `src/playback/player.ts`：曲目开始播放时记一笔。这是播放层唯一的改动点，且不得让记录失败影响播放
- `src/app/(tabs)/index.tsx`：「最近添加」改为「最近播放」，并移除 C1 留下的那条占位注释
- `src/library/actions.ts`：移除曲目时一并清理其历史
- `src/domain/model/track.ts` 不变——「最后播放时间」是曲目的**外部**事实，与 C2 的缓存状态同理，不塞进曲目记录，否则曲库的每次查询都要背上一个与曲目本身无关的字段

**依赖**

无新增依赖。存储沿用 `expo-sqlite`。

**平台**

两端一致，无平台差异。按 PRODUCT.md 的验收策略，本次只在 Android 上验收。
