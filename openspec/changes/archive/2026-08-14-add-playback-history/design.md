## Context

动机见 `proposal.md`「Why」，行为契约见 `specs/playback-history/spec.md`。这里只记实现路径上的技术选择。

**路线图措辞更正**：PRODUCT.md 中 C3 原本写作「歌词与播放历史」，把两件事捆在一起，**该捆绑作废**。两者不共享数据、不共享界面、也不共享技术风险（歌词的难点在 `.lrc` 的编码与时间轴方言），已拆为两个独立 change，本次只做播放历史。

三条既有事实决定了落点：

1. **位置早就留好了**。`src/app/(tabs)/index.tsx` 里有一段 C1 留下的注释：设计稿这一段是「最近播放」，在播放历史落地前展示的是最近添加，「宁可标题与设计稿差一个词，也不拿别的数据冒充播放历史」。本次把这笔账还上，那条注释一并删除。
2. **同构的先例已经跑通**。C2 的 `track_cache` 解决的是同一类问题——曲目的外部事实、独立成表、`ON DELETE CASCADE`。本次直接沿用这套形态，不另起炉灶。
3. **播放层只有一个装载入口**。`src/playback/player.ts` 的 `load()` 是所有播放路径的必经之处（`playQueue`、`playTrackAt`、`advance` 最终都走它），记录点因此唯一且明确。

## Goals / Non-Goals

**Goals**

- 记录逻辑对播放**完全无副作用**：记录失败、记录慢，都不能让曲目播不了或播得晚
- 表的大小有界，不随使用时长无限增长
- 除 `load()` 中新增的一次调用外，播放层的既有代码路径不变

**Non-Goals**（产品范围的非目标见 proposal）

- **不记录每一次播放的流水**。产品决定是「每首只留一条 + 计次数」，因此本设计不为「昨晚听了什么」这类时间轴回放留结构
- **不记录播放时长**。它需要流水式记录，与上一条冲突
- **不做历史的分页**。上限只有几百条，一次查完即可

## Decisions

### 决策 1：独立表 `playback_history`，不给 `tracks` 加列

新增表（迁移 version 4），主键即 `track_id`，外键指向 `tracks` 并 `ON DELETE CASCADE`。字段：最后播放时间、播放次数。

**为什么**：与 C2 决策 1 同理，且理由在这里更强——播放历史比缓存变得更频繁（每切一首歌就写一次）。本项目的曲库刷新是全局广播，若「最后播放时间」写在曲目行上，用户连着听十首歌就会触发十次全库重查。`ON DELETE CASCADE` 则让「曲目没了、历史还在」在数据库层面无法出现，spec 的一致性要求由此不必靠代码维持。

**备选 A：`tracks` 表加 `last_played_at` / `play_count` 列。** 未采纳，理由如上。附带代价是曲库列表的每一次查询都要多读两个与曲目本身无关的字段。

**备选 B：不建表，从播放队列或日志推断。** 未采纳。队列是易失的，应用重启即消失；历史要求跨重启保留。

### 决策 2：记录点在 `load()` 内、`player.replace` 成功之后，且仅当 `autoPlay`

```
load(index, { autoPlay })
  ├─ resolveTrack(track)          解析失败 → 不记录
  ├─ player.replace(...)          装载
  ├─ updateLockScreen(track)
  └─ autoPlay ? recordPlay(track) : —     ← 记录点
```

**为什么这个位置**：

- **在 `replace` 之后**：地址解析成功不等于播得响，spec 要求「未能开始播放的曲目不记入历史」。
- **仅当 `autoPlay`**：`appendToQueue` 在队列原本为空时会调 `load(0, { autoPlay: false })` 预装载一首但不播。那不是一次播放，不该记。
- **不在 `togglePlayPause` 里**：暂停后继续是同一次播放的延续，在那里记会让播放次数随暂停次数虚涨。
- **`token !== loadToken` 的既有守卫天然生效**：用户在装载过程中又切了歌时，这次 `load` 提前返回，不会留下记录。

**备选 A：在 `resolveTrack` 成功后立即记录。** 未采纳。解析成功只说明拿到了地址，装载仍可能失败（编解码不支持、缓存文件损坏），会记下一首实际没播成的曲目。

**备选 B：播放位置超过某个阈值（如 20 秒）才记录。** 未采纳——产品决定是「开始播就算」。代价与补救见 Risks；补救不需要改表结构，将来加阈值即可。

**备选 C：监听播放状态回调，见到 `playing` 就记。** 未采纳。那个回调每 500ms 触发一次，需要额外的「本首是否已记过」状态来去重，凭空多一份要维护的状态；而 `load()` 本身就是天然的一次一记。

### 决策 3：上限在**写入时**裁剪，不靠查询时 LIMIT

每次写入历史后，删掉排在保留上限之外的记录。上限取 **200 首**。

**为什么**：查询时 `LIMIT` 只是不显示，表仍会无限增长——用户用两年之后，一张几万行的表为了展示 20 条而存在。写入时裁剪让表的大小恒定有界，代价是每次写入多一条 DELETE，而写入频率只有「每切一首歌一次」，可以忽略。

200 这个数：以「一天听 30 首」计约覆盖一周，足够回答「最近在听什么」；它不是用户可调的设置，spec 也没要求可调——真有依据再改，改的是一个常量。

**备选 A：只在查询时 LIMIT，不删。** 未采纳，理由如上。
**备选 B：应用启动时裁剪一次。** 未采纳。长时间不重启的会话期间表仍然无界，而它省下的那点写入开销并不存在——DELETE 本来就便宜。
**备选 C：按时间保留（如 90 天）。** 未采纳。产品决定是按条数。附带一点：按条数的表大小可预测，按时间则取决于用户听歌频率，重度用户可能攒下几万条。

### 决策 4：记录失败绝不冒泡到播放

`recordPlay` 以「发射后不管」的方式调用，内部自行吞掉异常。

**为什么**：spec 明确要求「记录历史失败不影响播放」。播放是核心能力，历史是附属信息；让一次数据库写入失败把一首本可以正常播放的歌变成错误提示，是拿主要能力给次要能力陪葬。同理也不 `await` 它——历史写入没有理由延后播放开始的时刻。

**备选：把记录纳入 `load()` 的 try/catch，失败走 `handleLoadFailure`。** 未采纳，且有害：`handleLoadFailure` 会跳到下一首、累加连续失败计数，甚至可能把曲目标记为失效——一次写库失败会被表达成「这首歌播不了」。

### 决策 5：历史为空时，发现页回退到「最近添加」

「最近播放」有内容就显示它；一条都没有时（新用户、刚清空过）回到当前的「最近添加」，标题随之变化。

**为什么**：spec 要求空历史时不得是空白或加载中。而这一屏是应用的首页，对新用户来说恰恰是历史必然为空的时刻——摆一句「还没有播放记录」等于让首页开天窗，而此时「最近添加」正是他刚导入的东西，是当下最该被点开的内容。

**备选：始终显示两个区块（最近播放 + 最近添加）。** 未采纳。曲库刚建立时两者内容几乎完全重合，一屏之内出现两份相同的列表；且设计稿这个位置只画了一个区块。

### 决策 6：`play_count` 现在就存，但本次不展示

表里存播放次数，界面不用它。

**为什么**：它是记录时顺手就能维护的（写入本来就要 UPSERT，累加一个整数不增加任何 IO），而事后补则要面对「已有的历史没有次数」这个回填不了的空洞——播放次数无法从任何既有数据推算出来。现在存下来，将来若做「最常听」就有真实数据可用；不做也只是一个没人读的整数列。

**备选：等要做「最常听」时再加列。** 未采纳，理由如上：那时新增的列对存量历史永远是空的，等于要用户再听一年才有数据。

### 决策 7：单条移除挂在曲目行既有的「更多」菜单里，只在历史区块出现

`TrackActionsSheet` 增加一项「从最近播放移除」，仅当该行来自最近播放区块时渲染——与既有的「从本歌单移除」是同一种做法（那一项也只在歌单详情页出现）。

**为什么**：「最近播放」里冒出一首不想让它待着的歌（误触、别人借手机放的），此前只能忍着或把整份历史清掉，全无中间档。而曲目行本来就有「更多」菜单，多一项的成本几乎为零，用户也不必学一套新交互。

**这一项与紧邻的「从曲库移除」必须区分得开**：前者只删一条记录，曲目照样在曲库里；后者把曲目从曲库拿掉。两项都不删设备上的文件。靠 `hint` 副文案把差别说清，而不是指望用户从标题里体会。

**备选 A：在最近播放的行上做左滑删除。** 未采纳。设计稿没有左滑交互，且这一屏的列表本来就在纵向滚动的容器里，再叠一层横向手势要处理冲突；而「更多」菜单已经在那儿了。

**备选 B：只提供清空全部，不做单条。** 未采纳——正是这个缺口引出的本次改动：全清是把洗澡水和孩子一起倒掉。

## Risks / Trade-offs

| 风险                                                                                                        | 缓解                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **误触会把曲目顶到「最近播放」第一位**（产品决定「开始播就算」的直接代价）                                  | 接受。补救路径已备好且不需要改表结构：将来加一个「播放满 N 秒才记」的阈值即可，历史的结构与既有数据都不受影响                                                     |
| **单曲循环整晚只计一次**。`advance` 在 loopOne 自然播完时走 `seekTo(0)` 而不经过 `load()`，因此不会重复记录 | 对「最近播放」是**好事**（列表不被刷屏），对将来的「最常听」是失真。本次不展示次数，问题不显现；真要做排行时需重新审视这一处                                      |
| **写入与播放并发**：记录不 await，理论上可能与紧接着的下一次切歌重叠                                        | 每首曲目一行、写入是 UPSERT，重叠只会让两行各自写入，不产生脏数据。SQLite 的 WAL 模式已在 C1 开启，读写不互相阻塞                                                 |
| **裁剪与写入之间的竞态**：两次快速切歌可能让裁剪多跑一次                                                    | 裁剪是幂等的（「删掉第 200 名之后的」），多跑一次没有影响                                                                                                         |
| **历史里的曲目仍可能不可播**（来源失效、插件卸载）                                                          | 不是本次要解决的：spec 只要求历史中不出现**曲库里已不存在**的曲目。曲目仍在曲库、只是暂时播不了，与它出现在任何其他列表里的处境完全一致，由播放层统一报告失败原因 |

## Migration Plan

1. 数据库迁移追加 `version: 4`，只 `CREATE TABLE playback_history` 与其索引，**不修改既有迁移的任何语句**——已在设备上执行过的迁移不会重跑，改写等于让那些设备永久缺失改动
2. 无数据回填：迁移后表为空，「最近播放」因此为空，界面按决策 5 回退到「最近添加」，与当前行为一致。用户播放第一首后历史开始积累
3. 回滚：本次只新增表、新增一次调用、改一处界面文案。若需撤回，移除 `load()` 中的记录调用并把发现页改回最近添加即可；表留着不影响旧代码
