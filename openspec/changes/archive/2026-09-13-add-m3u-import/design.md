## Context

动机见 `proposal.md` 的 Why，行为契约见 `specs/playlist-file-import/spec.md`。这里只记录实施要面对的现状约束。

这条路径上**大部分零件已经存在**，本 change 主要是把它们接起来：

- `src/sources/remote-url/index.ts`：`parseRemoteUrl`（校验 http/https）、`inferTitleFromUrl`（从地址末段推断标题）、`buildRemoteSourceRef`，C1 建立
- `src/library/import.ts` 的 `importCandidates(candidates, target)`：一批 `CandidateTrack` → 一次事务入库 → 建歌单或追加，C6b-3 建立，本身不认识插件
- `src/plugins/ui/import-to-playlist-sheet.tsx`：「取曲目 → 选目标 → 入库 → 结果」的完整弹层，C6b-3 建立
- `src/sources/local-file/index.ts` 的文件选择器：走 `expo-file-system` 而非 `expo-document-picker`

真正要新写的只有一个解析器，以及把上面第三项搬到两端都能用的位置。

一条硬约束贯穿全文：**本能力两端等同可用，因此不得依赖 `src/plugins/` 子树**——该子树在 iOS 上编译期裁剪（`add-plugin-source-system/design.md` 决策 6），由 `pnpm check:ios-strip` 在产物层面把关。

## Goals / Non-Goals

**Goals:**

- 解析逻辑可在无设备、无网络的条件下单测——编码、相对地址、畸形行这三类才是真正容易错的地方
- 复用既有的批量入库与歌单弹层，不产生第二套「候选曲目 → 歌单」的流程
- 把因历史原因放在插件子树下、实则与插件无关的公共件归位，而不是在公共层复制一份

**Non-Goals:**

- 不追求覆盖 m3u 的全部扩展标签（`#EXTGRP`、`#EXTALB`、`#PLAYLIST` 等）。只取 `#EXTINF`，其余注释行一律忽略
- 不校验条目地址是否真的可播放。与 C1 的远程 URL 来源保持一致：可达性到实际播放时才知道，导入阶段预检既多一轮网络往返也保证不了后续成功

## Decisions

### 决策 1：不新增来源，导入的曲目归属既有的「远程 URL」来源

**选择**：曲目的 `sourceId` 为 `SOURCE_REMOTE_URL`，`sourceKey` 为条目的绝对地址——与用户手输一条地址得到的记录完全一致。

**理由**：来源标识在本系统里的唯一作用是「决定用什么方式把曲目解析成可播放地址」（`media-source` spec「来源注册与归属识别」）。播放列表导入的曲目，解析方式与手输地址的曲目**逐字相同**：拿 `uri` 直接播。播放列表文件是入库时的**运输工具**，不是曲目的归属地——导入完成后它就该从系统里消失，这也正是快照原则的另一种说法。

**备选方案与未采纳的理由**：

- **新建一个 `playlist` 来源**：未采纳。它会让同一段解析逻辑有两个注册入口；更糟的是去重键是 `sourceId + sourceKey`，同一个地址经手输与经播放列表导入会被判成两首不同的歌，用户会在曲库里看到重复条目。
- **新建来源并在 `sourceRef` 里记下播放列表出处**：未采纳。记下出处只有在「跟随更新」时才有用，而跟随更新已在 proposal 里明确排除；记了不用的字段会诱导后来者以为存在订阅语义。

### 决策 2：解析器是不碰网络、不碰存储的纯函数

**选择**：新增 `src/library/m3u.ts`，签名形如「播放列表文本 + 基准地址 → 条目列表 + 跳过项」。取回（本地读文件 / 远程 fetch）与入库都在它之外。

**理由**：这个 change 的风险集中在解析本身——编码、相对地址、`#EXTINF` 的方言、HLS 误判。把它做成纯函数，这些分支才能被单测**穷举**；混进 I/O 后，同样的覆盖就要靠跑设备。

**备选方案与未采纳的理由**：

- **解析、取回、入库写在一个 `importPlaylist()` 里**：未采纳。取回有两个来源（本地文件与远程地址），入库路径已经存在且被插件侧共用；写在一起会让唯一新增的风险点永远只能在集成层被测到。
- **引入现成的 m3u 解析库**：未采纳。可选的库要么面向 HLS（正是我们要拒绝的那一半语义），要么带 Node 专有依赖。需要解析的语法只有「`#EXTINF:` 行 + 地址行 + 注释行」三种，自己写比适配一个方向不对的库更短也更可控。

### 决策 3：相对地址以播放列表自身位置为基准；本地播放列表里的相对路径不自动转成本地文件曲目

**选择**：条目地址用标准 URL 解析规则相对于播放列表地址求解。远程播放列表得到 http/https 绝对地址，正常入库；本地播放列表里的相对路径解析后指向设备文件，**按不可用条目处理**，并提示用户本地音频应走本地文件导入。

**理由**：相对路径是导出工具的默认输出，不支持它等于只能导入少数手写文件。而本地那一半之所以不能顺手接上，是因为本地文件来源要的不是一个路径字符串，而是**设备发放的持久授权 URI**——那东西只能由系统文件选择器发放，从播放列表里的一行文本拼不出来。硬拼出的路径在重启或重装后必然失效，会在曲库里留下一批点不响的记录，这正是 C4 被暂缓的同一个坑（见 `PRODUCT.md` 中 C4 的说明）。

**备选方案与未采纳的理由**：

- **只接受绝对 http/https 地址**：未采纳。现实中的播放列表大量使用相对路径，这等于砍掉主要用例。
- **本地相对路径拼成 `file:` URI 入库**：未采纳，理由如上——会生产出注定失效的记录。
- **本地播放列表导入时引导用户再选一次音频目录、按文件名配回**：未采纳。这正是 `PRODUCT.md` 里说的「C4 若重启应当从那里开始」的那块独立工作，成本与本 change 不在一个量级，应当单独立项。

### 决策 4：编码上 UTF-8 优先，解不出就丢标题，绝不写入乱码

**选择**：按 UTF-8 解码（识别并跳过 BOM）。解码失败或结果含替换字符时，尝试中文 Windows 播放器常用的本地编码；仍不成功则**放弃该条目的标题与艺术家**，标题回退为从地址推断，条目照常入库。

**理由**：地址部分是 ASCII 或百分号编码，不受编码影响——所以编码问题最坏只波及元数据，不该波及能不能播。在「标题缺失」与「标题是乱码」之间，缺失明显更好：前者用户看到的是从文件名推断出的可读文本，后者是一行没法检索、没法辨认、还会永久留在曲库里的垃圾。

**备选方案与未采纳的理由**：

- **一律按 UTF-8 解码**：未采纳。中文 Windows 播放器导出的 `.m3u` 常为本地编码，中文标题会整片乱码。
- **引入完整的编码探测库（如 jschardet + iconv-lite）**：未采纳。为一个边缘场景增加可观的包体积与原生面；而本决策的回退路径已经保证了最坏情况仍是「可用但少元数据」，不是「不可用」。
- **让用户手动指定编码**：未采纳。用户通常不知道自己的文件是什么编码，这个提问把实现的难题转嫁给了用户。

### 决策 5：出现 `#EXT-X-` 即整体判为 HLS 并拒绝，不做部分导入

**选择**：解析时一旦发现 HLS 专有标签，整个文件判为流媒体播放列表，告知用户当前不支持，不入库任何条目。

**理由**：`.m3u8` 这个扩展名承载两种语义完全不同的东西。HLS 媒体播放列表里的地址是**同一条流的时间分片**，不是一首首曲目——把它们当曲目入库会得到几百条几秒钟的「歌」，是比报错糟糕得多的结果。整体拒绝而非跳过可疑行，是因为 HLS 与普通播放列表不会混在同一个文件里，判定不存在中间态。

**备选方案与未采纳的理由**：

- **尝试把 HLS 主播放列表当一首曲目入库**（地址就是那个 `.m3u8`）：未采纳。`expo-audio` 对 HLS 的支持未经验证，而且这属于播放引擎能力，应当作为远程 URL 来源的独立议题，不该塞进导入路径。
- **只跳过 `#EXT-X-` 标签、照常解析其余地址行**：未采纳，理由如上——产物是错的，且错得不明显。

### 决策 6：把候选曲目行与「加入歌单」弹层从插件子树上移到公共层

**选择**：`CandidateRow` 与 `ImportToPlaylistSheet` 从 `src/plugins/ui/` 移到 `src/ui/`；`CollectedTracks` 类型从 `src/plugins/discovery.ts` 移到 `src/domain/model/candidate-track.ts`。插件侧改为从新位置引用。纯搬迁，不改行为。

**理由**：这两个组件消费的是 `CandidateTrack`——domain 层的类型——和 `importCandidates`——曲库层的函数，**它们本来就不认识插件**。当初放在插件子树下是因为当时候选曲目只有一个生产者；现在出现了第二个，位置就错了。在公共层复制一份是更坏的选择：同一个弹层的两份实现会立刻开始分叉。

**备选方案与未采纳的理由**：

- **在 `src/ui/` 下另写一套播放列表专用的候选列表与歌单弹层**：未采纳。两份实现意味着往后每次调整「加入歌单」的交互都要改两处，且没有任何机制保证它们一致。
- **让 `src/ui/` 引用 `src/plugins/ui/`**：未采纳。这会把插件子树拉进 iOS 产物，直接违反编译期裁剪约束，`pnpm check:ios-strip` 会拦下。
- **不做预览，播放列表选中即入库**：未采纳。一个播放列表可能有几百条，用户需要先看到解析出多少、跳过多少再决定；而且这条流程现成，不复用反而要新写。

### 决策 7：跳过的条目随解析结果一起交给弹层，而不是另开一个提示

**选择**：给 `CollectedTracks` 增加一个可选字段承载被跳过条目的数量与原因，插件侧不传。弹层在确认页与结果页如实显示。

**理由**：`CollectedTracks` 里已有的 `truncated` 表达的正是「有一部分没能拿进来」，跳过项是同一类信息，放在一起用户才能在**同一屏**上看清「要入库多少、没能入库多少」。做成可选字段是为了让插件侧一行不改。

**备选方案与未采纳的理由**：

- **把 `truncated: boolean` 重构成统一的「未纳入部分」结构**：未采纳。会连带改动插件发现层已归档的 spec 与实现，收益只是形状更齐整。
- **跳过项单开一个提示弹层**：未采纳。用户要在两屏之间对照才能知道发生了什么，且多一次点击。

## Risks / Trade-offs

- **上移公共件会碰到已归档的插件发现层代码** → 纯搬迁不改行为，改动限于 import 路径；完成后跑 `pnpm check:ios-strip` 确认裁剪仍然生效，并回归插件侧的「全部加入歌单」路径。
- **`#EXTINF` 的元数据由播放列表文件提供，可能与音频实际内容不符**（艺人写错、时长不准） → 不做校验，如实入库。这是快照原则的自然结果：我们如实转述用户自己准备的信息，用户可自行在曲库中修正。时长仅用于显示，不参与播放控制。
- **中文编码回退会让部分条目退化为「从地址推断的标题」** → 已在决策 4 中权衡接受。风险的可见性由结果页承担：这类条目仍会入库，用户能看到并自行处理。
- **远程播放列表可能非常大或根本不是文本** → 取回时设体积上限，超出即拒绝并说明；非文本内容在解析阶段自然落入「没有可识别条目」分支。
- **`.m3u8` 的两义性会让用户困惑**（"为什么我的文件不能导入"） → 决策 5 的提示文案必须说清是「流媒体播放列表」而不是笼统的「格式不支持」。
- **iOS 侧本 change 不做真机验收**，沿用 `PRODUCT.md`「先做完 Android，iOS 全量验收一次」的既定策略。本 change 不含平台特有行为，两端走同一段 TypeScript；唯一需要 iOS 复验的是文件选择器读取 `.m3u` 文本的行为，已在 tasks 中标注。

## Migration Plan

无数据迁移。既有曲目、歌单、播放列表不受影响；决策 6 的搬迁是编译期的模块位置调整，不触及任何持久化数据。

回滚即撤销本 change 的提交：新增的解析器与入口无人引用，搬迁的组件回到原位置。已由本功能导入的曲目与歌单是普通的远程 URL 曲目与本地歌单，回滚后照常可用——这是决策 1 的直接好处。
