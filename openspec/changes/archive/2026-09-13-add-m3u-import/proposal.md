## Why

曲库里加一首远程曲目要手输一次地址。**「拿到一个 URL 就能播」在 C1 就已经做完了**（`remoteUrlSource` 解析、`importRemoteUrl` 入库），缺的从来不是播放能力，而是**一次拿到一批**——几十上百首逐条输入没有人会用，这条路径实际上等于不存在。

上一轮网盘调研（2026-09-11）的结论是：不该再为这件事去绑定任何厂商 SDK。百度网盘 2026-06-03 起把第三方应用锁死在 `/apps/{appname}` 目录里，读不到用户自己的音乐；阿里云盘普通应用档下载链接 15 分钟、分段并发 3，且官方文档写明「边下边播场景中……用户进行 seek 操作，每次 seek 均计算为一次未完成的下载任务，则多次 seek 后会超过并发报错」；123 云盘 OpenAPI 2026 年已转为付费权益包；夸克与天翼云盘没有面向个人开发者的网盘开放平台；Google Drive 的 `drive.readonly` 需要每年数百至数千美元的 CASA 安全评估。这些代价的共同点是：**都花在「把用户的文件变成一个 URL」上，而这一步用户往往已经自己完成了。**

m3u 正是「一批 URL + 基础元数据」的行业标准容器：格式是纯文本、无需依赖库，且用户产出它的路径已经存在且免费（foobar2000 / VLC / MusicBee 导出、AList 与对象存储生成、Navidrome 导出，乃至手写）。它不需要鉴权协议、不需要审批、不依赖任何厂商政策，**iOS 与 Android 两端都能上架**——这会是第一个两端等同可用的批量入库路径。

## What Changes

- **播放列表文件导入**：用户选择一个本地 `.m3u` / `.m3u8` 文件，或粘贴一个远程播放列表地址；系统解析出其中的音频条目，以候选曲目列表呈现，可整批加入歌单。
- **`#EXTINF` 元数据入库**：从 `#EXTINF:<秒数>,<艺人> - <标题>` 中取出时长、艺人与标题写入曲目记录。没有 `#EXTINF` 的条目按既有规则从 URL 末段推断标题（`inferTitleFromUrl`），不因缺元数据而丢弃条目。
- **相对路径按播放列表位置解析**：条目写成相对路径时，以播放列表自身的地址为基准解析成绝对地址。这是 m3u 在现实中最常见的形态，不支持它等于只能导入少数手写文件。
- **曲目归属既有的「远程 URL」来源**：不新增来源，不动注册表。导入产物与用户手输一条地址得到的曲目是同一种记录，因而在曲库、歌单、检索、播放、离线缓存里完全同权。
- **产物是普通本地歌单**：沿用 C6b-3 已定的快照原则——导入产生一个与手建歌单完全相同的本地歌单，不记录来源、不跟随播放列表文件的后续变化。要更新就再导一次，曲目按去重键去重。
- **不可用条目逐条点名**：非音频协议（`file:`、`rtsp:` 等）、畸形行、HLS 分片播放列表等无法作为曲目入库的内容，在结果里说明有几条被跳过及原因，不静默吞掉。

### 非目标

- **`.pls` / `.xspf` / `.wpl` 等其他播放列表格式**：正交。三者的产出工具远少于 m3u，且各自要一套解析；先用 m3u 验证整条路径是否成立，确有需求再按同一形状扩展。
- **导出曲库为 m3u**：属于曲库备份（C4）的范畴，而 C4 已因「本地文件曲目备份不出去」暂缓（理由见 `PRODUCT.md`）。导入与导出不共享任何逻辑，捆在一起只会把 C4 的阻塞传染过来。
- **HLS 流媒体播放（`.m3u8` 作为媒体播放列表）**：**明确不做**。`.m3u8` 这个扩展名承载两种完全不同的东西——UTF-8 编码的普通播放列表，与 HLS 的媒体/主播放列表（带 `#EXT-X-` 标签）。本 change 只处理前者；遇到后者应当识别出来并告知用户，而不是把 HLS 分片当成曲目入库。播放 HLS 是播放引擎能力问题，与导入无关。
- **跟随播放列表文件更新的「订阅型」歌单**：与快照原则相悖，理由同 `add-plugin-discovery-import/design.md` 决策 1；不是推迟，是明确不做。
- **读取远端音频文件头补全元数据**：是否对远程地址发 Range 请求取内嵌标签，`bootstrap-music-player/design.md` 已记录留待网盘接入一并决策，至今未定。本 change 只用播放列表文件自述的元数据。
- **接入任何网盘 SDK（百度 / 阿里 / 夸克 / 123 / OneDrive / Google Drive）**：本轮调研已逐项排除，理由见 Why。115（C5）仍按原路线图等待 API 审批，与本 change 正交。
- **导入时一并离线缓存**：正交，用户导入后可在歌单里逐首下载，属于 C2 的能力扩展。

## Capabilities

### New Capabilities

- `playlist-file-import`：从播放列表文件批量建立曲目与歌单。覆盖解析契约（识别哪些行是条目、如何取元数据、相对路径如何解析）、两种入口（本地文件与远程地址）、不可用条目的处理，以及产物与既有歌单体系的关系。

### Modified Capabilities

无。曲目归属既有的远程 URL 来源，`media-source` 的「远程 URL 来源」要求不改措辞即覆盖本 change 产生的曲目；`music-library` 的去重与「元数据由来源直接提供」、`playlist` 的歌单内顺序与重复加入不产生重复条目，都是本 change 依赖而非改动的既有行为。

## Impact

- **新增 `src/library/m3u.ts`**：播放列表文本 → 条目列表的纯函数解析器。无网络、无存储依赖，可直接单测。
- **`src/library/import.ts`**：新增「播放列表 → 候选曲目 → 批量入库」的入口函数，复用既有的 `importCandidates`（C6b-3 建立，本身不认识插件）与 `parseRemoteUrl` / `inferTitleFromUrl` / `buildRemoteSourceRef`（C1 建立）。
- **`src/ui/import-sheet.tsx`**：导入面板增加播放列表入口，与既有的「本地文件」「远程地址」并列。
- **文件选择**：本地 `.m3u` / `.m3u8` 沿用既有的文件选择器路径，不引入新依赖。
- **不触及**：来源注册表、播放引擎、插件模块。两端行为一致，无需编译期裁剪。
