## Context

动机见 `proposal.md`「Why」，行为契约见 `specs/lyrics-display/spec.md`。这里只记实现路径上的技术选择。

**路线图补正**：PRODUCT.md 的 C3b 写作「本地 `.lrc` 与内嵌歌词显示」，**漏了插件歌词**——而实测表明那两处在真实曲库上几乎什么都取不到（见下方第 5 条），插件才是这个功能能否落地的关键。该描述在实施时一并更正。

五条既有事实决定了落点：

1. **协议早就留好了，而且留的是两类**。`src/plugins/protocol.ts` 中 `getLyric?: (mediaItem) => unknown` 已声明；更重要的是 `PluginSearchType` 含 `'lyric'`，`src/plugins/api.ts` 的注释写明「歌词类插件虽有 `search` 方法但只认 `lyric`」——**宿主在 C6a 时就区分了「来源插件」与「歌词类插件」**，只是从未调用过。本次是第一次用它们，插件契约不需要任何改动。
2. **内嵌歌词现成可取**。`music-metadata` 的 `common.lyrics` 同时给同步（带时间轴）与非同步两种，而 `parseAudioMetadata` 已经在导入路径上跑通了 Hermes 上的解析。
3. **同目录找 `.lrc` 行不通**。文件选择器走的是单文档授权，拿不到兄弟文件；`Directory.pickDirectoryAsync`（目录授权）才能枚举，因此只能是「用户指定一个歌词目录」而不是「自动找同名文件」。
4. **文件名不可靠**。实测本地文件曲目存下来的 `fileName`：`雨落东京 → msf:19`、`逆光而行 → msf:20`、`无Xing头-7分06秒 → 无Xing头-7分06秒.mp3`——5 首里 4 首拿到的是 MediaStore 文档编号而非真实文件名。匹配只能用曲目标题。
5. **前两处来源在真实曲库上几乎是空的**。实测一个 12 首的曲库：5 个本地音频文件用 `ffprobe` 查，**没有一个**带歌词标签；整台设备 `find -iname '*.lrc'` **一个结果都没有**。这不是这个曲库特殊——绝大多数音频文件本就不写歌词标签，`.lrc` 收藏也是少数人的习惯。**这条事实决定了歌词类插件不是补充而是主力**：没有它，这个功能做完之后每首歌都显示「没有找到歌词」。

## Goals / Non-Goals

**Goals**

- 播放层一行不改。歌词跟随播放靠订阅既有的播放位置
- 任何一处歌词来源出问题都不影响播放，也不打扰用户
- 歌词区在有词、无词、纯文本三种情形下都不改变播放控制的行为

**Non-Goals**（产品范围的非目标见 proposal）

- **不做流式 / 分段加载**。一首歌的歌词最多几 KB，一次读完
- **不做时间轴的容错校准**。`.lrc` 里时间戳乱序或重复时按原样排序处理，不猜用户意图

## Decisions

### 决策 1：四处来源，优先级为「歌词目录 > 内嵌 > 来源插件 > 歌词类插件」

按这个顺序取第一个成功的。

**为什么这个顺序**：

1. **越是用户主动准备的越优先**。他专门指定一个歌词目录、往里放文件，就是不满意别处的版本；内嵌歌词是文件自带的，属于「他选了这个文件」的间接表达。这两处还都不需要网络。
2. **来源插件排在歌词类插件之前**，因为它拿到的是**精确**的曲目——`mediaItem` 就是这个插件自己给出的，不存在配错的可能；而歌词类插件是拿标题去搜，可能搜到同名的另一首。

**备选 A：内嵌优先于歌词目录。** 未采纳。那样用户放进目录的文件永远盖不过文件自带的版本，而「自带的不好所以我自己找了一份」正是他准备目录的动机。

**备选 B：全部取回来让用户选。** 未采纳。为一个默认场景引入一次选择，而各处内容通常是同一首歌的同一份词；真需要换源时的正解是让他改歌词目录，而不是每首歌问一次。

### 决策 2：歌词类插件按两步调用，且对任意曲目适用

歌词类插件（`supportedSearchType` 含 `'lyric'`）的调用是两步，与来源插件完全不同：

```
来源插件      getLyric(该曲目自己的 mediaItem)                 一步，精确
歌词类插件    search(标题, 1, 'lyric') → 候选[]
              getLyric(候选[0])                                两步，按标题匹配
```

**为什么必须单列**：这是提案初稿漏掉的一路，而它恰恰是**覆盖面最大的**——它不关心曲目来自哪里。实测的真实曲库里，7 首本地文件加 1 首远程直链在其余三处来源全部落空，只有这一路能出词。只写「曲目所属来源的插件」等于把功能的主要价值漏掉。

宿主早就为它留了位置：`PluginSearchType` 含 `'lyric'`，`src/plugins/api.ts` 的注释写明「歌词类插件虽有 `search` 方法但只认 `lyric`」。本次是第一次真正用它，插件契约不需要改动。

**候选取哪一个**：取第一条。备选是按标题与艺人做相似度打分再挑——未采纳，那是在给一个本就模糊的匹配再叠一层猜测；真配错了，用户的补救手段是往歌词目录里放一份自己的，那条路优先级更高，一定盖得过。

**返回形状**：协议里歌词的正文字段是 `rawLrc`（MusicFree 的既有约定，实测安装的三个插件都用它）。按既有 `invokePlugin` 的做法解析，字段缺失或不是字符串时按「这一路没取到」处理，不抛给用户。

### 决策 3：`.lrc` 按曲目标题匹配，不按文件名

在歌词目录中查找 `<title>.lrc`，找不到时再试 `<title> - <artist>.lrc` 与 `<artist> - <title>.lrc` 这两种常见命名。

**为什么不用文件名**：实测数据在 Context 第 4 条——Android 的文件选择器在相当一部分情况下给回的是 MediaStore 文档编号（`msf:19`）而不是真实文件名。按它匹配，用户会遇到「同名 `.lrc` 明明在那儿却匹配不上」，而且**毫无头绪**：他看到的曲目标题是「雨落东京」，无从知道应用内部拿的是 `msf:19`。

而且远程与插件曲目根本没有文件名，按标题匹配是唯一对三类来源都成立的规则。

**备选：让用户在设置里选「按文件名还是按标题」。** 未采纳。这是把实现细节的困境甩给用户，而他没有任何依据做这个选择。

### 决策 4：歌词缓存独立成表，随曲目级联删除

新增 `track_lyrics` 表（迁移 version 5），主键 `track_id`、外键 `ON DELETE CASCADE`。字段：歌词正文、来源标识、获取时间。

**为什么缓存**：插件歌词要联网。不缓存的话，每次播放同一首都打一次插件站点——C2 决策 6 已经吃过这个教训（插件来源对频繁请求敏感，代价由用户承担）。而且缓存让已下载的曲目在离线时也有词，与 C2 的「无网可听」配套；不缓存的话「歌能放、词没了」。

**为什么独立成表**：与 `track_cache`、`playback_history` 同构——歌词是曲目的**外部**事实，不塞进 `tracks`。`ON DELETE CASCADE` 让「曲目没了、歌词还在」在数据库层面无法出现。

**备选 A：只在内存缓存当前曲目。** 未采纳。切走再切回就要重新请求，而用户在播放列表里来回切是常态。

**备选 B：把歌词写成文件。** 未采纳。歌词是几 KB 的文本，为它引入一套文件生命周期管理（孤儿清理、路径推导），而数据库里一行就够——C2 之所以用文件，是因为那是几 MB 的音频。

**不缓存哪一类**：内嵌歌词与歌词目录读出来的**也缓存**。它们虽然不要网络，但每次播放都重新解析一遍文件（内嵌歌词最坏要读整个音频文件）同样浪费，且缓存后三类来源的读取路径统一。来源标识记下来，将来要「重新获取」时能按来源区分。

### 决策 5：`.lrc` 解析自己写，不引依赖

时间标签形如 `[mm:ss.xx]`，一行可以带多个标签（同一句在多处重复），另有 `[ti:]` `[ar:]` 这类元信息标签需要忽略。

**为什么自己写**：规则就是上面这几条，一个正则加一次排序。而新增依赖要过 PRODUCT.md 的许可证核查，为几十行逻辑背一个依赖不划算。

**备选：用现成的 lrc 解析库。** 未采纳，理由如上。附带一点：这类库大多顺手把「歌词翻译」「卡拉 OK 逐字」也实现了，而那两样都在非目标里。

### 决策 6：编码只支持 UTF-8，非 UTF-8 明确报错而不是显示乱码

读取 `.lrc` 时若解码失败或结果含大量替换字符，判定为不受支持的编码并如实告知。

**为什么**：中文 `.lrc` 里 GBK 相当常见，但 Hermes 的 `TextDecoder` 只保证 UTF-8。要支持得引依赖，而这是一次需要单独决策的事（许可证核查）。

关键在于**失败的表现方式**：显示一屏乱码，用户会以为应用坏了或歌词文件坏了；明确说「这个文件不是 UTF-8 编码」，他至少知道该怎么办（用文本编辑器另存为 UTF-8）。

**备选：静默跳过非 UTF-8 文件，当作没找到。** 未采纳。用户明明把文件放进去了却「没找到」，比报错更让人困惑。

### 决策 7：歌词跟随播放靠订阅既有播放状态，播放层不改

歌词组件用 `usePlayback()` 拿当前位置，自行算出当前行。

**为什么**：播放层没有任何理由知道歌词的存在。C1 的分层约定里播放层只负责播放，而 `usePlayback` 已经以约 500ms 的节奏对外暴露位置——对逐行高亮足够（一行歌词通常持续数秒）。

**备选：在播放层加一个「当前歌词行」的状态。** 未采纳。那会让播放层依赖歌词模块，方向正好反了；而且歌词只在播放页可见，把它塞进全局播放状态是让所有订阅者为一个界面细节付出重渲染。

## Risks / Trade-offs

| 风险                                                                                                                       | 缓解                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **插件的 `getLyric` 实现质量不可控**。实测用户当前安装的插件调用它会抛 `TypeError: Cannot read property 'lrclist' of null` | 走既有的 `invokePlugin`，插件故障按 plugin-source spec 处理——不影响宿主、不打扰用户。歌词取不到就是取不到，界面照常说明「没有找到歌词」                                                                                                |
| **按标题匹配会误配**：两首同名不同版本的歌会拿到同一份词                                                                   | 接受。补救是让用户把文件命名成 `标题 - 艺人.lrc`，决策 3 的备选命名已覆盖这种写法                                                                                                                                                      |
| **约 500ms 的位置更新对逐行高亮够，但对逐字不够**                                                                          | 逐字（卡拉 OK）本就在非目标里。真要做需要更密的位置采样，届时再评估                                                                                                                                                                    |
| **内嵌歌词的解析最坏要读整个音频文件**（`parseAudioMetadata` 的两段式读取在头部拿不到时会重读全文件）                      | 由决策 4 的缓存兜住：每首曲目最多解析一次                                                                                                                                                                                              |
| **歌词目录的授权可能失效**（用户删了目录、撤销了授权）                                                                     | 与「未指定目录」同等处理：跳过这一处来源，不报错。用户在设置里能看到当前目录并重新指定                                                                                                                                                 |
| **插件返回的 LRC 形态不规范**。实测歌词网插件把整篇的换行去掉后返回，`[t1]词1[t2]词2…` 挤在一行                            | `.lrc` 解析按**时间标签**切分而不是按行切分：每个标签的词是它后面到下一个标签为止的文本，相邻标签共享后面那句。两种写法都对，不需要知道正文来自哪个插件                                                                                |
| **歌词类插件按标题误配**在实测里比预想的更常见：followlyrics 对「有Xing头-7分06秒」这种标题也会返回一首歌                  | 接受（同上「按标题匹配会误配」）。但由此暴露了一条必须堵住的路：目录里的文件不是 UTF-8 时若继续往下找，误配的词会被缓存，用户把文件另存为 UTF-8 后也永远看不到自己那份。因此「匹配到但读不出」直接报告并停止，不缓存也不记进本进程结果 |

## Migration Plan

1. 数据库迁移追加 `version: 5`，只 `CREATE TABLE track_lyrics`，**不修改既有迁移的任何语句**
2. 歌词目录的路径存在既有的 KV 配置里（`src/domain/settings.ts`），不为一个字符串建表
3. 无数据回填：迁移后表为空，歌词在首次播放各曲目时逐步积累
4. 回滚：本次只新增表、新增 `src/lyrics/`、改播放页一张卡片。若需撤回，把卡片改回占位文案即可；表留着不影响旧代码
