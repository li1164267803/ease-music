## Why

播放页正中间那张卡片现在写着「暂无歌词 / 本地 .lrc 与内嵌歌词将在后续版本支持」——C1 实施时按设计稿留了位置，但不肯拿假数据填。听歌看词是这类应用最被期待的能力之一，而这块空白每次打开播放页都在。

歌词还与 C2 形成配套：已下载的曲目能离线播放，但如果歌词只能联网现取，离线时体验是割裂的——歌能放，词没了。

**一条实测得来的前提**：只做「内嵌歌词 + 本地 `.lrc`」这两处是不够的。实测一个真实曲库（12 首）：5 个本地音频文件**没有一个**写了歌词标签，整台设备**一个 `.lrc` 文件都没有**。绝大多数音频文件本就不带歌词，而 `.lrc` 收藏是少数人的习惯。真正能让歌词落地的是**歌词类插件**——用户装一个，任何曲目都能按标题搜到词。C3b 若只做前两处，结果会是每首歌都显示「没有找到歌词」。

## What Changes

- 新增**歌词显示**能力：播放页那张卡片改为呈现当前曲目的歌词，带时间轴的逐行高亮并跟随播放进度
- 歌词从**四处**获取：音频文件的**内嵌歌词**、用户指定的**本地 `.lrc` 目录**、**曲目所属来源的插件**（一步 `getLyric`）、**歌词类插件**（先按标题 `search(…, 'lyric')` 再对候选 `getLyric`）
- 其中**歌词类插件是覆盖面最大的一路**：它不关心曲目来自哪里，给个标题就能搜，因此本地文件与远程直链曲目也能有词——而那两类曲目在其余三处来源里基本什么都拿不到
- 没有时间轴的纯文本歌词照常显示，只是不跟随播放
- 取到的歌词落库缓存，避免每次播放都向插件站点重复请求，也让已下载的曲目离线时仍有词
- 用户可指定（与更换、清除）一个歌词目录；应用在其中按**曲目标题**匹配，不按文件名——理由见非目标下方说明
- 三处都没有歌词时，卡片明确说明「没有找到歌词」以及可以怎么补，而不是留一句无从下手的「暂无歌词」

### 非目标

| 不做                                               | 原因                                                                                                                                                                                                                                                                |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **非 UTF-8 编码的 `.lrc`（GBK / GB18030 等）**     | 中文歌词文件里 GBK 相当常见，但 Hermes 的 `TextDecoder` 只保证 UTF-8，要支持得引入一个解码库——而新增依赖必须过 PRODUCT.md 的许可证核查。本次读到疑似非 UTF-8 的文件时**明确告知用户该文件不是 UTF-8**，而不是显示一屏乱码。是否为此引入依赖，等有真实需求再单独决策 |
| **逐首手动指定歌词文件**                           | 作为兜底手段它很可靠，但逐首操作繁琐，且在三处自动来源都接上之后剩余的缺口有多大还不知道。等实际用下来发现缺口明显再补                                                                                                                                              |
| **全屏歌词页**（点开卡片展开、手动滚动、点行跳转） | 设计稿没有画这一屏，版式得自己定；而卡片内滚动已经能回答「这句在唱什么」。展开态是独立的一块界面工作，不推翻本次结构即可后续追加                                                                                                                                    |
| **歌词翻译 / 音译**                                | 需要额外的数据源与双行版式，与「显示歌词」是两件事                                                                                                                                                                                                                  |
| **歌词编辑与时间轴校准**                           | 属于歌词制作工具的范畴，远超播放器的定位                                                                                                                                                                                                                            |
| **按歌词内容搜索曲目**                             | 依赖把歌词全文纳入检索，与曲库检索的实现耦合，收益不清楚                                                                                                                                                                                                            |
| **自动联网抓取歌词**（应用内置歌词站点）           | 与产品定位冲突：应用不内置、不指向任何内容源。插件歌词是用户自己装的插件提供的，性质不同                                                                                                                                                                            |

## Capabilities

### New Capabilities

- `lyrics-display`: 歌词的获取、匹配与呈现——从哪几处取、优先级如何、带时间轴与不带时间轴分别怎么显示、取不到时如何说明、以及歌词与曲目之间的一致性

## Impact

**新增**

- `src/lyrics/`：歌词的获取与解析（`.lrc` 时间轴、内嵌标签）、来源优先级、缓存仓储
- 数据库迁移：新增歌词缓存表（曲目 id、歌词内容、来源、获取时间）
- 「我的」页的歌词目录设置入口

**改动**

- `src/app/player.tsx`：那张占位卡片改为歌词区，替换「暂无歌词」的占位文案
- `openspec/PRODUCT.md`：C3b 的描述需要补上**插件歌词**。当前只写了「本地 `.lrc` 与内嵌歌词」，而插件是三处来源里覆盖面最广的一处——插件曲目本身就没有本地文件，内嵌与 `.lrc` 都指望不上

**不改动**

- `plugin-source` 的行为契约不变。协议里 `getLyric` 早已声明，本次只是第一次真正调用它；插件调用失败的处理沿用既有的「插件故障不影响宿主」
- `src/playback` 不改。歌词跟随播放靠订阅既有的播放位置，播放层不需要知道歌词的存在

**依赖**

无新增依赖。`.lrc` 解析是纯字符串处理；内嵌歌词由既有的 `music-metadata` 提供（`common.lyrics`，同步与非同步两种它都给）。

**平台**

两端一致。插件歌词在 iOS 上自然为空——插件模块在 iOS 侧不存在，取歌词时少一个来源，不需要特殊分支。
