## Why

C1 建立的曲库只能装用户「已经拥有」的东西：设备里的音频文件，或用户已知的一个直链地址。这留下一个缺口——用户想听一首歌，但他手上既没有文件也没有地址时，播放器无能为力。

插件音源系统把「找到资源」这件事交给用户自行安装的第三方插件：应用本身不提供、不内置、不指向任何插件源，只提供一个执行插件代码并把结果接入曲库的宿主。协议形状参考 MusicFree 的插件规范，以便既有插件生态可以直接复用，但**仅参考协议规范，不复制其源代码**（AGPL-3.0 传染性约束）。

本 change 是路线图中的 **C6 第一切片**。完整功能地图见 `openspec/PRODUCT.md`。

## What Changes

- 新增插件宿主：加载并执行用户安装的 CommonJS 插件模块，注入受控的 `require` 依赖白名单
- 新增插件管理：从本地文件与 URL 安装插件、按 `srcUrl` 更新、卸载、查看已安装列表、配置插件的 `userVariables`（多数插件需要用户自备的 cookie / token 才能工作）
- 新增插件搜索：调用插件的 `search` 取回**未入库的候选曲目**，用户从结果中选择「加入曲库」，随后该曲目与本地文件曲目完全同权——可进歌单、可被检索、可被备份
- **BREAKING** 来源注册表由编译期静态数组改为运行时可变注册表：一个插件即一个来源，数量在运行时才确定，装卸插件会改变注册表内容
- 曲库放宽两处既有约束：曲目元数据可以由来源直接提供（而非只能从文件内嵌标签解析），封面可以是远程地址（而非只能是本地缓存文件）
- 插件模块在 iOS 构建中整体裁剪：不仅不注册来源，其代码与专属依赖均不进入 iOS 产物

### 明确的非目标

**属于 C6 后续切片**（协议的加载与调用能力在本 change 已完整建立，后续切片只是接入新的插件方法并增加对应界面，不改动本 change 的地基）：

- **发现层**：`getTopLists` / `getTopListDetail` / `getRecommendSheetTags` / `getRecommendSheetsByTag` / `getAlbumInfo` / `getArtistWorks` / `getMusicSheetInfo` / `getMusicComments`。这些方法的返回形状与 `search` 同构（未入库候选曲目 + 分页），本 change 建立的候选曲目模型已经承载它们；排除的原因是它们各自需要独立界面，界面面积远大于地基本身。
- **歌单与单曲导入**：`importMusicSheet` / `importMusicItem`。同上，且需要先确定外部歌单与本项目歌单体系的映射规则。
- **`search` 的 `album` / `artist` / `sheet` / `lyric` 类型**：搜索结果需要跳转到对应详情页才有意义，与发现层一并后移。本 change 只实现 `music` 类型。

**属于其他 change**：

- **插件歌词（`getLyric`）**：归入 C3 歌词能力。歌词的解析、滚动与展示只应有一套实现，先做 C3 的宿主侧歌词渲染，插件歌词作为其数据来源之一接入。
- **插件曲目的离线缓存**：归入 C2 离线缓存。插件返回的地址有时效性，是缓存层最需要覆盖的场景，但缓存策略与存储管理是独立设计。

**确认不做**：

- **内置或默认指向任何插件源、插件市场、插件推荐**：违反产品定位的根基（`PRODUCT.md - 明确不做`），也是规避版权风险的前提。用户从哪里获得插件由用户自行决定。
- **iOS 上以任何形式提供插件能力**：App Store 审核指南 2.5.2（不得下载执行改变应用功能的代码）与 2.3.1（不得包含未披露的隐藏功能）使其无法合规上架。
- **插件的安全隔离**：插件代码与应用代码运行在同一 JS 上下文中，能力等同于应用自身代码，本 change 不引入权限边界或资源限制。信任模型是「用户自行选择安装的插件，由用户自己负责」，应用侧以安装时的明确风险告知承担责任。真正的隔离需要独立 JS 运行时实例，代价与单平台增强功能的收益不匹配。

## Capabilities

### New Capabilities

- `plugin-source`: 插件音源能力。插件的安装与生命周期管理、插件代码的加载与执行、依赖注入白名单、插件协议的元字段与方法契约、用户变量配置、插件搜索与候选曲目、插件曲目的地址解析，以及 iOS 编译期裁剪约束。

### Modified Capabilities

- `media-source`: 「来源注册与归属识别」需求变更——注册表从编译期确定的固定集合，改为包含运行时动态注册的来源；新增插件被卸载后其存量曲目的处理要求。
- `music-library`: 两处需求变更——曲目元数据允许由来源直接提供，而非仅能从音频文件内嵌标签解析；封面允许为来源提供的远程地址，而非仅能是内嵌图片的本地缓存。候选曲目入库后与其他曲目同权，这一行为定义在 `plugin-source` 中，曲库侧不再单列。

> 注：C1 `bootstrap-music-player` 尚未归档，`openspec/specs/` 目前为空，上述两个 capability 的现行 spec 位于 `openspec/changes/bootstrap-music-player/specs/` 下。本 change 的 delta 以其内容为基线。

## Impact

**受影响的既有代码**：

- `src/sources/registry.ts`：静态 `SOURCES` 数组与模块加载期构建的 `Map` 需改为有生命周期的可变注册表。文件顶部「本文件是唯一需要改动的地方，C6 届时在这里追加一项即可」的注释基于「插件 = 一个来源」的错误假设，需一并修正。
- `src/domain/model/track.ts`：`sourceKey: string` 需要一条从插件 `primaryKey`（字符串数组，可为联合主键）派生的确定规则；`artworkUri` 的「本地缓存文件」语义需放宽。
- `src/sources/contract.ts`：`ResolvedMedia` 无需改动——其 `{ uri, headers, userAgent }` 与协议 `getMediaSource` 的返回形状已经一致。需新增「未入库候选曲目」类型。
- 曲库入库路径与曲库/搜索界面。

**新增模块**：`src/plugins/`（插件宿主、安装管理、协议适配），以及插件来源在 `src/sources/` 下的接入点。

**新增依赖**：插件运行时需要注入 `axios`、`cheerio`、`crypto-js`、`dayjs`、`big-integer`、`qs`、`he`。这些依赖只为插件服务，构成纯粹的包体开销，且必须随插件模块一并从 iOS 产物中裁剪——否则 iOS 包内会留下无任何调用方的 HTML 解析器等模块。裁剪方案需在 design.md 中论证到构建配置层面，而不止于「不注册来源」。

**平台差异**：本 change 是项目中第一处两端能力不一致的地方。C1 建立的「核心能力不依赖插件模块」约束在此接受真实检验——iOS 裁剪后必须仍是功能完整的播放器。

**文档影响**：`PRODUCT.md` 的 C6 行需按切片更新；`PRODUCT.md` 与 `bootstrap-music-player/design.md` 决策 5 中「JS 沙箱」的措辞与实际方案不符（插件与应用同上下文执行，无隔离机制），需标注作废并改为「插件宿主」。

**风险**：

- 协议兼容度只能靠真实插件验证。本 change 不内置任何插件，验证需开发者自行取得插件样本进行，兼容性缺口可能在实施后期才暴露。
- `cheerio` 等依赖在 Hermes 上的可用性有 MusicFree 的量产先例，但版本差异仍需在实施早期以 spike 确认。
