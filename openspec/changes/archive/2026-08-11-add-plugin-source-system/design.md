## Context

动机见 `proposal.md - Why`，行为契约见本 change 的 `specs/`。此处只记录塑造技术方案的现状与约束。

**C1 留下的地基**：`src/sources/` 已有统一解析契约（`ResolvedMedia = { uri, headers?, userAgent? }`）、静态来源注册表、以及唯一的解析入口 `resolveTrack`。曲目模型 `Track` 以 `sourceId + sourceKey` 为去重键，`sourceRef` 是开放键值结构，用于保存「重新解析所需的信息」。

**协议基线**：插件协议形状对齐 MusicFree 的公开规范（`platform` / `version` / `srcUrl` / `primaryKey` / `cacheControl` / `userVariables` / `supportedSearchType` 等元字段，加上一组全部可选的异步方法）。其 `getMediaSource` 返回 `{ url, headers?, userAgent? }`，与 C1 的 `ResolvedMedia` 已经同构——这是 C1 决策 4「采用与既有生态一致的形状」兑现的部分。**仅参考协议规范，不复制源代码**（AGPL-3.0）。

### 作废的历史表述

- **`PRODUCT.md` C6 行的「自主实现的 JS 沙箱」、`bootstrap-music-player/design.md` 决策 5 的「插件运行在受限的 JS 沙箱中」——作废。** 参考实现与本方案均不提供任何隔离机制：插件代码与应用代码在同一 JS 上下文中执行，能力等同于应用自身代码。真实的限制只有两条——插件是纯 JS，且只能取到宿主注入的那几个依赖。正确的表述是「插件宿主」。见决策 1。
- **`src/sources/registry.ts` 文件头注释「本文件是唯一需要改动的地方，C6 届时在这里追加一项即可」——作废。** 该注释基于「插件 = 一个来源」的假设，实际上一个插件即一个来源，数量在运行时才确定。见决策 2。
- `bootstrap-music-player/design.md` 决策 5「本地文件与网盘作为宿主内置来源，不作为插件」——**继续有效**，本 change 不改变这一分层。

## Goals / Non-Goals

**Goals：**

- 建立一次成型的插件地基：加载执行、依赖注入、错误边界、生命周期管理、动态注册。后续切片接入新的协议方法时只加界面，不动地基
- 让插件曲目在入库后与本地文件曲目在数据与行为上完全同权，不产生第二套曲库
- 让 iOS 产物在构建层面真实不含插件代码与其专属依赖，而非仅在运行时关闭入口

**Non-Goals：**

- 不追求对既有插件的 100% 协议兼容。本切片只保证元字段解析、`search`、`getMediaSource` 三处可用，其余方法只保证「能被加载、不报错」
- 不设计插件的安全隔离、权限模型或资源配额（理由见 `proposal.md - 明确不做`）
- 不为插件设计独立的曲目存储或独立的播放路径

## Decisions

### 决策 1：插件宿主用 `Function` 构造器在应用自身的 JS 上下文中执行插件，不引入隔离运行时

插件文本被包装为 CommonJS 模块工厂：宿主构造一个函数，向其传入 `module`、`exports`，以及一个只认白名单的 `require` 实现，执行后取 `module.exports` 作为插件对象。

**理由**：这是在 React Native + Hermes 上唯一零额外运行时成本的方案，且有量产先例（MusicFree 即以此方式运行，`hermesEnabled=true`）。插件因此可以直接使用宿主已打包的成熟依赖（HTTP、HTML 解析、加解密），插件作者的心智模型就是普通 Node 风格模块。

**备选与未采纳理由**：

- **内嵌独立 JS 引擎（QuickJS 等）做真隔离**：能获得权限边界与资源配额，但要为引擎内的插件重新提供 HTTP 客户端、Promise 跨边界桥接、依赖打包，并长期维护这套桥。插件是 Android 独占的增强能力，为它承担一整个运行时的维护成本不成立
- **WebView 隔离执行**：跨边界通信全部异步且需序列化，HTML 解析类插件的性能与调试体验明显劣化，且 WebView 自身也不构成可信边界
- **只允许声明式插件（配置而非代码）**：无法兼容既有插件生态，等于放弃「用户已有插件可直接用」这一核心收益

**接受的代价**：恶意插件可以做应用能做的一切。以安装前的明确风险告知处理（见 `specs/plugin-source` 的「安装插件前的风险告知」），不以任何措辞暗示存在隔离。

### 决策 2：一个插件即一个来源，注册表改为「内置常驻 + 动态可变」

`getSource(id)` 的签名与 `resolveTrack` 的调用方式保持不变，改动收敛在 registry 内部：内置来源在模块加载时注册且不可移除，插件来源在插件安装/卸载时增删，`sourceId` 取插件自述的 `platform`。

**理由**：曲库的去重键是 `sourceId + sourceKey`。若所有插件共用一个 `sourceId`，两个不同插件返回的同 id 曲目会被误判为同一首；卸载单个插件时也无法定位其存量曲目；界面无法标明结果来自哪个插件。

**备选与未采纳理由**：

- **插件整体作为一个 `plugin` 来源，用 `sourceRef` 区分具体插件**：能保住「注册表是静态的」这一性质，但上述三个问题全部落到 `sourceRef` 里用私有字段解决，等于让曲库层去理解来源的内部结构——直接违反 `media-source` spec 的「上层 MUST NOT 依赖任何特定来源的私有字段」
- **在注册表之外为插件另建一套路由**：`resolveTrack` 会出现「先查内置、再查插件」的分叉，C2 缓存层将来要在两条路径上各拦一次

**代价**：`sourceId` 的取值不再是编译期已知的有限集合，`SOURCE_LOCAL_FILE` 这类常量只覆盖内置来源。`sourceId` 类型本就是 `string`（`track.ts:8`），无需变更。

### 决策 3：候选曲目是独立类型，不复用 `Track`

新增一个表示「尚未入库的曲目」的类型，携带来源插件标识、插件返回的原始条目、以及展示所需的信息。它只存在于搜索结果与入库动作之间，不落库。入库时由它生成 `Track`。

**理由**：`Track` 的语义是「曲库里的一条记录」——有本地 `id`、有 `addedAt`、`artworkUri` 是本地缓存文件（`track.ts:40`）。候选曲目这三样都没有。让 `Track` 的这些字段变成可空，会把「这条记录到底入没入库」的判断散布到每个消费 `Track` 的地方。

**备选与未采纳理由**：

- **让 `Track` 的 `id`/`addedAt` 可空**：核心模型被一个边缘状态污染，且编译器不再能保证「拿到 Track 就是入库的」
- **搜索结果直接落库、用户不保存就删除**：曲库被搜索行为污染，重复添加去重、备份导出（C4）都要额外排除这些临时记录
- **不引入候选概念，搜到即入库**：等于强制用户为每次搜索的全部结果扩充曲库

**收益**：后续切片的榜单、专辑、艺人、歌单导入返回的都是同构数据，直接复用该类型，这是本切片必须包含 `search` 的根本原因。

### 决策 4：`sourceKey` 由插件声明的 `primaryKey` 按序拼接派生

协议的 `primaryKey` 是字符串数组（默认 `["id"]`），可声明联合主键。宿主按数组声明顺序取出对应字段值，以固定分隔符拼接为 `sourceKey`。字段缺失时该条结果按畸形数据丢弃。

**理由**：`Track.sourceKey` 是单字符串，且参与去重键，必须由一条确定、可重现的规则产生——同一首歌两次搜索必须得到同一个 `sourceKey`。

**备选与未采纳理由**：

- **固定只取 `id` 字段**：声明了联合主键的插件会把不同曲目判为同一首，去重直接出错
- **序列化整个条目做 key**：插件返回的字段（如播放次数、临时地址）会变，同一首歌两次搜索得到不同 key，去重失效并产生重复记录
- **由宿主用「标题 + 艺术家」生成 key**：跨插件同名曲目会被误合并，且插件内真实的主键信息被丢弃

### 决策 5：不实现地址缓存，`cacheControl` 无需特殊处理

C1 决策 4 已确定播放地址每次实时解析、不持久化。协议的 `cacheControl` 用于声明播放地址可否缓存，本方案等价于始终按最保守的 `no-store` 处理，因此对该字段的三种取值都天然安全，宿主读取但不据此改变行为。

**理由**：缓存时效性地址的收益是省一次插件调用，代价是地址过期后播放失败且难以归因。C2 离线缓存要缓存的是**音频内容**，不是地址，两者不冲突。

**备选与未采纳理由**：

- **按 `cacheControl: "cache"` 实现地址缓存**：需要额外的失效策略与过期重试，为了省一次通常只有数百毫秒的插件调用，不划算
- **完全忽略该字段不做记录**：将来若要支持，会缺少插件的原始声明

### 决策 6：iOS 裁剪用平台后缀文件切断依赖引用链，不用条件判断

插件相关的一切（宿主、协议适配、来源接入、管理与搜索界面入口）只被带 `.android` 平台后缀的文件引用；平台中立的一侧只暴露一个空实现，iOS 侧不 import 任何插件模块与其专属依赖。

**理由**：打包器按静态 `import` 关系收集模块，与代码是否可达无关。只有让 iOS 侧根本不存在那条 `import`，`cheerio` 等依赖才不会进入产物。

**备选与未采纳理由**：

- **运行时条件判断（`Platform.OS === 'android'`）**：入口能隐藏，但模块与依赖照样被打进 iOS 产物——包体白涨，且「iOS 包中不存在相关代码」这一审核陈述不再成立
- **babel 常量内联 + 死代码消除**：能消除语句，但对 `import` 声明的消除不可靠，仍可能保留模块引用
- **打包器 `blockList` 按平台屏蔽路径**：被屏蔽的模块一旦仍被引用会导致构建期解析失败，且失败信息与真实原因相距较远

**必须配套的验收**：裁剪是否真的生效无法靠阅读代码确认，需要在 iOS 产物中实际检索插件模块与专属依赖，作为独立验收项执行（见 `tasks.md`）。

### 决策 7：所有插件调用经由统一的调用包装层

宿主不把插件方法直接暴露给上层。每次调用都经过同一层包装：超时上限、异常捕获、返回值形状校验、以及「哪个插件出了什么问题」的错误归因。

**理由**：`specs/plugin-source` 的「插件故障不影响宿主」要求对三类故障（抛异常、畸形数据、无响应）都有确定行为。分散在每个调用点实现，必然出现遗漏。

**备选与未采纳理由**：

- **在各调用点自行 try/catch**：新增协议方法时容易漏掉某一类故障处理，后续切片每加一个方法就要重复一遍
- **依赖插件自己保证不出错**：插件是第三方代码，这是不设防

## Spike 结论

实施第一步的验证结果，直接修正了上面的方案。验证在本机用 RN 0.86 实际捆绑的 Hermes（`250829098.0.16`）与 Expo 的真实 Metro 解析器完成。

**`cheerio` 必须注入 slim 构建。** `cheerio` 1.2.0 的主入口引用 `undici` 与 `node:stream`（为其 `fromURL` 能力），Metro 在 Android 与 iOS 上都无法解析，打包直接失败。`cheerio/slim` 去掉了这条链路，可正常打包。因此**白名单的键仍是插件作者书写的 `'cheerio'`，但宿主注入的实现是 slim 构建**——这一映射是宿主的职责，插件无需改写。丢失的只有 `fromURL`（自行发起 HTTP 请求），插件本就应通过注入的 `axios` 取页面，不构成能力缺口。

**注入依赖集合在 Hermes 上可编译。** 七个依赖（`cheerio` 取 slim）一同打包后由 `hermesc -O -emit-binary` 编译通过、无错误，即不存在 Hermes 不支持的语法。**尚未验证的是运行时行为**，留在真机链路中确认。

**Release 构建的字节码预编译不影响动态执行。** 检查 RN 0.86 随附的 Android **release** 版 `libhermesvm.so`：其中完整存在解析器与编译器（诊断字符串、`DirectEvalInst`、`Compiling JS failed:` 这一"编译被尝试且失败"的错误路径），`eval` 与 `Function` 均为全局对象，且不存在 lean 构建（`HERMESVM_LEAN`，编译器被剔除）特有的标记字符串。即决策 1 的前提在 release 下成立，不因主包被预编译为 HBC 而失效。

**包体量级。** 七个依赖编译为 HBC 约 810 KB。这个数字是决策 6（iOS 裁剪）的收益下限，也是"必须裁剪而非仅隐藏入口"的量化依据。

## Risks / Trade-offs

- ~~**依赖在 Hermes 上的实际可用性未验证**~~ → 见「Spike 结论」。打包与编译两关已过，且已据此把 `cheerio` 改为注入 slim 构建。**剩余缺口收窄为运行时行为**，随第一个真实插件样本的链路验证一并确认
- **协议兼容度只能靠真实插件检验，而本项目不内置任何插件** → 兼容性缺口可能在实施末期才发现。缓解：实施期间由开发者自行取得插件样本验证，并在 spike 阶段就先跑通一个样本的搜索与解析全链路，而不是留到验收
- **裁剪失效不可见** → 运行时看不出差别，只能通过检查构建产物发现。列为独立验收项，且必须在真实 iOS 构建产物上执行
- **插件顶层代码里的游离 Promise 无法被调用包装层接住** → 真机验证时实测到：某插件在模块顶层发起了一个 HTTP 请求且没有 catch，失败后成为未处理的 rejection，绕过 `loadPlugin` 的 try/catch（它只拦得住同步抛出），在 Development Build 里弹出 LogBox 红屏。**这是决策 1「无隔离」的直接后果，不是遗漏**：rejection 在加载函数返回之后才发生，宿主既无法把它归因到具体插件，也没有作用域可以圈住它。不做技术缓解——装一个全局 rejection handler 会连应用自身的错误一起吞掉，代价远大于收益。Release 构建下不会崩溃，spec 的「MUST NOT 导致应用崩溃」仍然成立
- **无隔离意味着恶意插件可窃取数据或滥用网络** → 不做技术缓解（代价不成立），改以安装前明确告知 + 不提供任何插件线索来处理。这是清醒接受的取舍，不是遗漏
- **插件生态的协议会演进** → 宿主读取插件的 `appVersion` 声明，不兼容时明确提示而非静默行为异常
- **动态注册表引入了 C1 没有的状态** → 注册表内容随用户操作变化，播放中卸载插件等时序需要覆盖。`resolveTrack` 已有的 `source-not-registered` 分支正好承载这一场景，无需新增防御逻辑

## Migration Plan

无数据迁移。`Track` 表结构不变：`sourceId` 已是字符串、`sourceRef` 已是开放结构、`artworkUri` 存远程地址无需变更列类型。新增的是插件自身的存储（插件文件、已安装清单、用户变量），属于新增而非改动。

回滚即卸载插件模块：插件曲目会退化为「来源不可用」，仍保留在曲库与歌单中，不丢数据——这与 iOS 侧的既有行为一致。
