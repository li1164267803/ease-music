## Context

动机见 `proposal.md`「Why」，行为契约见 `specs/offline-cache/spec.md`。这里只记录实现路径上的技术选择。

三条既有约束决定了本次的落点：

1. **拦截点已经预留**。C1 的 `design.md` 决策 4 把播放前的地址解析收敛到 `resolveTrack` 这一个函数，并在注释中写明「C2 离线缓存将在此处判断」。本次兑现它，播放层与各来源实现不需要任何改动。
2. **曲目记录不保存解析结果**。`src/sources/contract.ts` 中 `MediaSource.resolve` 注有「每次播放前实时调用，不缓存结果」。这条**不作废**，但需要澄清边界：不缓存的是**地址**（网盘与插件的地址有时效性），本次缓存的是**音频字节**。地址仍然每次实时解析，只是命中缓存时根本不去解析。实现时把这行注释补上这层区分，避免后来者误读成「本次改了 C1 的决策」。
3. **来源可扩展性不能被破坏**。media-source spec 要求新增来源仅需实现解析契约与注册标识。缓存层因此不能认识任何具体来源。

可用工具已确认（`expo-file-system` 57.0.2，无需新增依赖）：

| 能力                              | API                                                                   |
| --------------------------------- | --------------------------------------------------------------------- |
| 带进度、可取消、可传请求头的下载  | `File.createDownloadTask(url, dest, { headers, onProgress, signal })` |
| 文件移动 / 删除 / 存在性 / 字节数 | `file.moveSync(dest)`、`file.delete()`、`file.exists`、`file.size`    |
| 可用磁盘空间                      | `Paths.availableDiskSpace`                                            |

其中一条平台差异必须在设计中处理：**`downloadFileAsync` 在 Android 上失败会把已写入的部分留在目标位置，iOS 则先落临时位置、成功后才移动**（`File.d.ts` 官方注释）。若直接下载到最终路径，Android 上一次断网就会留下一个「看起来已下载」的残缺文件。

## Goals / Non-Goals

**Goals**

- 缓存层对播放层、曲库层、各来源实现均不可见——除 `resolveTrack` 内部新增的一次查询外，既有代码路径不变
- 「记录说有」与「文件真的在」这两件事永远可以自我纠正，任一方向的不一致都不导致播放失败
- 下载中断（断网、杀进程、用户退出）绝不产生可被误判为完整音频的文件

**Non-Goals**（本节只列设计层边界，产品范围的非目标见 proposal）

- **断点续传**。`DownloadTask` 提供 `savable()` / `fromSavable()`，但续传要求服务端支持 Range，且插件解析出的地址常是短时效的临时链接——重启后原地址多半已失效，续传成功率低于直接重下。中断即重下
- **后台持续下载**。iOS 的 `sessionType: 'background'` 能让原生传输在应用挂起后继续，但 JS 侧的 task 实例在应用被终止后不恢复，进度与完成回调都拿不到，属于「传完了但应用不知道」。不依赖它
- **下载优先级、暂停/恢复的用户操作**。队列是先进先出，用户能做的只有取消

## Decisions

### 决策 1：缓存状态存独立表，不给 `tracks` 加列

新增 `track_cache` 表（迁移 version 2），主键即 `track_id`，外键指向 `tracks` 并 `ON DELETE CASCADE`。字段：文件路径、字节数、完成时间。

**为什么**：缓存是曲目的**外部**事实。曲库列表的每一次查询都要读全部曲目行，让它们背上两个与曲目本身无关的字段是纯粹的浪费。更要紧的是一致性方向——`ON DELETE CASCADE` 让「曲目没了、缓存记录还在」这种状态在数据库层面无法出现。

**备选 A：`tracks` 表加 `cache_path` / `cache_bytes` 列。** 未采纳。除上述开销外，还有一个更具体的问题：本项目的曲库刷新是全局广播（`notifyLibraryChanged` 触发所有页面重查）。若下载进度写在曲目行上，一次下载会在几秒内触发几十次全库重查。

**备选 B：不建表，靠扫描缓存目录推断。** 未采纳。求总占用需要每次遍历目录做 IO；且文件与曲目的对应关系必须可逆解析，等于把数据库塞进文件名里。

### 决策 2：缓存文件名用 `track.id`，不用内容哈希

落盘为 `cache/<track.id>.<ext>`。扩展名依次从**文件头的魔数**、URL 路径推断，都推断不出时用 `bin`。

> **实施修正**：本节原写作「先看响应的 `Content-Type`」。实现时发现 `expo-file-system` 的下载任务不把响应头交给 JS 侧，拿不到 `Content-Type`。改为下载完成后读文件头的前 12 字节判断（`ID3`/MPEG 帧同步、`fLaC`、`OggS`、`RIFF…WAVE`、`ftyp`）——这反而更可靠：插件音源指向的 CDN 大多一律返回 `application/octet-stream`，而文件头是内容自己说的。文件此刻已经在 `.partial` 里，读 12 字节的代价可忽略。

**为什么**：一首曲目对一份缓存，`track.id` 天然是一一对应的键，删除曲目时不必查表就能定位文件。保留扩展名是低成本的保险——播放引擎在缺少 MIME 提示时会退回按扩展名判断容器格式。

**备选：按内容哈希命名（与 `src/library/artwork.ts` 的封面一致）。** 未采纳。封面用哈希是因为同一张专辑的十几首曲目共享同一张图，去重收益明确；音频不共享，哈希带来的只有「必须下完才知道文件叫什么」——本来就要先落临时文件，再加一步算哈希再改名，纯增复杂度。

### 决策 3：先落临时文件，成功后移动，最后写库

```
1. 下载 → cache/.partial/<track.id>
2. 成功 → moveSync 到 cache/<track.id>.<ext>
3. 文件就位后 → 写 track_cache 记录
```

顺序不可交换。**文件先就位，记录后写**：反过来会出现「记录说有、文件没有」，而那正是播放时才发现的失败。按此顺序，唯一可能的不一致是「文件在、记录无」——一个孤儿文件，不影响任何功能，由清理兜底。

`.partial` 目录在应用启动时整个清空：能出现在那里的文件，一定属于某次没跑完的下载。

**备选：直接下载到最终路径，用 `idempotent: true` 允许覆盖。** 未采纳。`idempotent` 解决的是「目标已存在时是否报错」，与「部分写入的文件被当成完整音频」是两回事。Android 的部分残留会正好落在最终路径上，下次播放直接读到一个坏文件——且因为记录尚未写入，缓存层还不认识它，连纠正的机会都没有。

### 决策 4：在 `resolveTrack` 内部拦截，不注册「缓存来源」

```
resolveTrack(track)
  ├─ 查 track_cache
  │   ├─ 命中且文件存在 → 返回 { uri: file://... }（无 headers）
  │   └─ 命中但文件已不在 → 删除记录，继续 ↓
  └─ getSource(track.sourceId).resolve(track)   ← 原有路径，不变
```

**为什么**：这正是 C1 决策 4 预留的位置。缓存命中时不产生任何网络请求，也不触碰来源——插件被卸载后已下载的曲目照常播放，正是因为这一步在 `getSource` 之前。

**备选：把缓存注册成一个 `MediaSource`，下载后把曲目的 `sourceId` 改成它。** 未采纳，且是个有害的设计。`sourceId` 表达的是曲目的**归属**，不是它当前从哪读取。改了归属，删除缓存后要改回去（改回哪个？得再存一份原归属），曲库备份（C4）导出的归属信息也会是错的。归属是稳定事实，缓存是易变事实，不能混为一谈。

### 决策 5：下载走 `getSource(...).resolve(...)`，不走 `resolveTrack`

下载器需要的是**来源的真实地址**，而 `resolveTrack` 命中缓存时返回的是本地路径。虽然下载前已判断过「未下载」，但让下载器依赖这个前提是脆弱的耦合。下载器直接向来源要地址，并把返回的 `headers` 与 `userAgent` 原样传给 `createDownloadTask`——插件与网盘的防盗链要求下载请求与播放请求带同样的头。

**备选：给 `MediaSource` 契约增加 `download` 方法。** 未采纳。这会让「新增来源只需实现解析契约」的约束失效，每个来源都要重复实现一遍下载逻辑，而它们要做的事完全一样。

### 决策 6：单队列串行下载，并发度 1

**为什么**：移动网络下多路并发抢同一条链路的带宽，总耗时并不改善；而插件来源指向的站点对并发请求敏感，批量并发容易触发限流甚至封禁——代价由用户承担。并发度是一个常量，将来有依据再调。

**备选：并发 2–3。** 未采纳。收益不确定（受限于链路而非连接数），风险明确（限流、被封）。

### 决策 7：进行中的下载状态只存内存

排队中、下载中、进度、失败原因，全部存在一个内存态里，通过与 `notifyLibraryChanged` 同构的订阅广播给界面。只有**下载完成**这一个事实写入数据库。

**为什么**：进程被杀就是下载中断——spec 明确要求重启后该曲目不得显示为已下载。状态本就随进程生灭，落库反而要在每次启动时把「下载中」改回「未下载」，凭空多一步清理。

**备选：把任务队列持久化，重启后自动续下。** 未采纳，理由同 Non-Goals 中的断点续传：插件地址时效短，重启后大概率要重新解析，而重新解析等于重新下载。

### 决策 8：一致性靠双向清理，不靠事务

| 不一致          | 何时发现             | 处理                             |
| --------------- | -------------------- | -------------------------------- |
| 记录有、文件无  | 播放解析时（决策 4） | 删记录，回退到来源解析。用户无感 |
| 文件有、记录无  | 应用启动扫描         | 删除孤儿文件                     |
| `.partial` 残留 | 应用启动             | 整个目录清空                     |

启动扫描复用 `src/library/artwork.ts` 中 `pruneArtwork` 已经验证过的形态：拿到"仍在使用"的集合，遍历目录删掉不在集合里的。

**备选：文件操作与数据库写入放进同一个事务。** 未采纳——做不到。SQLite 事务无法回滚文件系统操作，强行包裹只会制造「事务回滚了但文件还在」的假安全感。真正有效的是把顺序设计成「唯一可能的不一致是无害的那一种」（决策 3），再对两个方向各做一次廉价清理。

### 决策 9：能否下载由来源自述，缓存层不认识任何具体来源

`MediaSource` 增加一个可选只读字段 `cacheable?: boolean`，缺省视为 `true`；本地文件来源声明 `false`。

**为什么**：这是对契约的**增量**扩展——既有来源与将来的新来源不写这个字段就是默认可缓存，media-source spec「新增来源仅需实现解析契约与注册标识」的约束不受影响。

**备选 A：缓存层直接判断 `sourceId === 'local-file'`。** 未采纳。缓存层因此认识了一个具体来源，将来 C5 网盘、或任何自带本地文件形态的来源出现时，这个判断都要再改一次——正是 media-source spec 要防止的那类改动。

**备选 B：解析出地址后看 URI 是不是 `file://`。** 未采纳。那要先发起一次解析才知道该不该显示下载按钮，界面上每一行曲目都得先打一次网络请求。

### 决策 10：缓存模块按「谁认识来源」切成两半（实施阶段补充）

```
能力层    src/cache/download.ts   （调 getSource 取真实地址）
          src/cache/queue.ts      （串行队列，经 download.ts）
   ↓
来源层    src/sources             （resolve.ts 反过来依赖下面三个）
   ↓
领域层侧  src/cache/repository.ts （缓存记录）
          src/cache/files.ts      （目录与落盘）
          src/cache/store.ts      （内存状态、订阅、缓存命中判定）
```

**为什么**：实现时才撞上一个决策 4 没有点明的后果——来源层的 `resolve.ts` 要查缓存，而下载又必须调用来源。整个模块放在来源层之上，`resolve.ts → cache` 就是下层依赖上层；整个放在来源层之下，下载器拿不到 `getSource`。`docs/architecture.md` 的第一句是「任何新增代码都必须能被归入某一层，且不得反向依赖」，两种放法都违反它。

按「认不认识来源」切开之后两边都成立：`store.ts` 刻意不引用 `src/sources`，因此 `resolve.ts` 依赖它是向下的；`download.ts` 依赖来源层同样是向下的。**这条切法是本模块唯一的结构性约束**，改动时首先要守住。

**备选：把缓存命中判定也放进 `queue.ts`。** 未采纳。那样 `resolve.ts → queue.ts → download.ts → registry.ts` 虽然不成环，但 `resolve.ts → queue.ts` 这条边本身就是来源层依赖能力层，等于把分层规则作废掉一次，而唯一的收益只是少一个文件。

**备选：状态查询改成每次读数据库，不要内存态。** 未采纳。曲目行要同步渲染下载状态，落到数据库就是每行一次异步查询，一个 50 首的歌单要发 50 次；而进度每几百毫秒变一次，更不可能落库。

### 决策 11：记录缓存音频的**实际**时长，但不据此判断「这是不是片段」（实施阶段补充）

`track_cache` 增加可空列 `duration_ms`（迁移 version 3），在下载完成、文件就位后用曲库既有的 `parseAudioMetadata` 读一次，缓存管理界面显示成 `0:30 · 470 KB`。

**为什么**：真机验证时发现，网易插件对版权受限曲目返回的是 **30 秒试听片段**——HTTP 200、响应体完整、`.partial` 顺利转正，下载确实成功了，缓存层没有任何理由认为出了问题。但用户看到的是和整首歌一模一样的绿色对勾，要等到断网想听时才发现只有 30 秒。spec 的「音频原样保存」被满足了，「已下载」这个承诺却没有。

应用无法判断对方给的是不是整首，也不该去判断。能做的是把文件的事实摊开：实测 `0:30 · 470 KB` 与 `3:04 · 7.0 MB` 并排一放，用户自己就看出来了。

**备选 A：拿实际时长与 `Track.durationMs` 比对，差距过大就标记「可能是片段」。** 未采纳。来源自述的时长本身就不可靠——同一个插件对「稻香」给 183948（正确），对「双截棍」给 345453000（把毫秒当秒又乘了 1000）。拿一个不可靠的数去判定另一个数，只会制造误判，而误判的方向是把好文件标成可疑。

**备选 B：界面按体积估算并给出警告。** 未采纳。码率未知，估算等同于猜测；且低码率的完整歌曲与高码率的片段体积可能相同。

**备选 C：不存列，缓存管理界面渲染时现读文件。** 未采纳。`parseAudioMetadata` 最坏要读完整个文件（无 Xing 头的 CBR MP3），每次打开界面对 N 首各读一遍是白花的 IO；而时长是文件落盘那一刻就定死的事实，读一次存起来即可。

**为什么是 version 3 而不是并进 version 2**：v2 尚未随任何版本发布，按理可以改。但它已经在本次验证用的真机上执行过了——改写 v2 不会重跑，那台设备上这一列会永远缺失，而症状是运行时报错而非启动失败，最难查。追加一次迁移的代价远小于此。

## Risks / Trade-offs

| 风险                                                                                                | 缓解                                                                                                                                      |
| --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Android 下载失败残留部分文件**（官方文档明确行为）                                                | 决策 3 的临时目录 + 成功后移动。这是本设计里唯一一条由平台差异直接驱动的结构                                                              |
| **插件/网盘地址有时效**，下载排队等待期间地址已过期                                                 | 每个任务在**轮到自己执行时**才解析地址，不在入队时解析                                                                                    |
| **`Content-Length` 缺失**（服务端不给，`totalBytes` 为 `-1`）导致进度无法计算，也无法预判空间是否够 | 进度退化为「已下载 X MB」而非百分比；空间不足只能由写入失败暴露，按普通失败处理并说明原因                                                 |
| **下载中曲目被移除 / 缓存被清空**                                                                   | 任务持有 `AbortController`，移除与清空时取消对应任务；取消后 `.partial` 文件随启动清理消失                                                |
| **大文件下载期间应用被系统回收**，用户看到的进度永久停住                                            | 状态只在内存（决策 7），重开应用即回到未下载，可重新发起。不做假的「恢复中」                                                              |
| **缓存目录被系统清理**                                                                              | 落在 `Paths.document` 而非 `Paths.cache`——后者是系统在空间紧张时可以自行清空的目录，与「应用不自动删除用户下载内容」的 spec 要求直接冲突  |
| **已下载曲目在无网时封面缺失**                                                                      | 封面走 `expo-image` 的磁盘缓存，不在本次范围内保证。曲目播放不受影响（music-library spec 已要求远程封面不可用不影响播放），界面回退占位图 |

## Migration Plan

1. 数据库迁移追加 `version: 2`（建 `track_cache` 与其索引）与 `version: 3`（给该表加可空列 `duration_ms`，见决策 11），**不修改既有迁移的任何语句**——已在设备上执行过的迁移不会重跑，改写等于让那些设备永久缺失改动
2. 缓存目录 `document/cache-audio/` 与 `document/cache-audio/.partial/` 在首次使用时按需创建，不在迁移中创建——迁移只管数据库
3. 无数据回填：迁移后表为空，全部曲目处于未下载状态，与现状一致
4. 回滚：本次只新增表与新增文件，不改动既有列与既有行为。若需撤回，移除拦截逻辑即可恢复到当前行为；表留着不影响旧代码
