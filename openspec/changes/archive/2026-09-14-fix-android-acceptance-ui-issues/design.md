## Context

动机与范围见 `proposal.md`。本 change 不改 spec，各项对应的既有要求在 proposal 的 Why 中已点名。这里只记录实施时需要先定下来的做法。

与本 change 相关的现状：

- **候选曲目加入**：`addCandidateTrack` 返回 `{ track, duplicate }`。`discovery-tracks.android.tsx` 与 `discovery-import.android.tsx` 各自写了一份「入库 → 广播 → 记已加入 → 按 `duplicate` 设提示」；`search.android.tsx` 的同一段逻辑丢掉了 `duplicate`，也没有提示位置。
- **插件搜索失败条目**：`failures` 只在一次搜索结束时整体替换，加载期间列表底部仍显示上一次的失败。
- **更新入口**：`PluginCard` 中 `plugin.srcUrl ? <CardAction label="更新" /> : null`。
- **下载结果**：`src/cache/queue.ts` 的「本轮」结果 `round` 是全局的，只记 `completed` 计数与 `failed: { title, reason }[]`，不带曲目标识；歌单页 `describeQueue(useDownloadQueue())` 原样展示。
- **底部面板**：`src/ui/sheet.tsx` 是所有底部弹层的唯一实现（`Modal` + 遮罩 + 内容区），没有任何键盘处理；项目未引入键盘相关依赖。带输入框的面板有：新建/重命名歌单、导入音乐、从地址安装插件、插件变量设置、链接导入、「加入歌单」中的新建歌单名。
- **序号列**：`IndexedTrackRow` 的序号容器固定 `width: 22`。
- **JSX 文本换行**：JSX 中跨行书写的文本，换行会被折叠成一个空格，中文里就成了多余空格。
- **风险告知**：`manage.android.tsx` 中 `useState(true)` 作为初值，`readRiskAcknowledged()` 异步返回后才改为真实值。
- **专辑分组**：`useCollections` 按专辑名（缺省为「未知专辑」）聚合，卡片的 `meta` 取组内第一首的艺术家，`coverUri` 取组内第一张封面。

## Goals / Non-Goals

**Goals:**

- 每一项修正都落在该行为唯一的实现处，而不是在各个调用点分别修
- 不引入新依赖、不改原生代码、不改数据库结构

**Non-Goals:**

- 不重新设计底部面板的视觉与交互，只解决键盘遮挡
- 不调整下载队列的并发与调度，只调整结果的归属

## Decisions

### 决策 1：候选曲目的「加入并告知」收敛为一个 hook

**选择**：在 `src/plugins/ui/` 新增 `useCandidateAdd()`，返回 `{ added, notice, add }`，封装「`addCandidateTrack` → `notifyLibraryChanged` → 记入已加入集合 → 按 `duplicate` 设置提示」。插件搜索、榜单/歌单/专辑/艺人曲目页、链接导入三处页面改用它。插件搜索页把提示放在列表上方，与另两处的位置一致。

**理由**：「同一插件同一曲目重复加入要告知」是一条行为规则，三份拷贝中有一份漏了，正是重复实现的直接后果。收敛到一处，以后任一候选曲目列表都不可能再漏。

**备选方案与未采纳的理由**：

- **只在搜索页补上与另两处相同的几行**：未采纳。修掉症状但保留了让它发生的结构，第四个候选曲目列表出现时还会再漏一次。
- **放进 `CandidateRow` 组件内部**：未采纳。「已加入」必须由列表按曲目 key 持有（`candidate-row.tsx` 注释已说明行组件会被 FlashList 回收复用），提示也属于列表而不是某一行。

### 决策 2：键盘避让在 `Sheet` 内统一处理，使用 React Native 自带的 `KeyboardAvoidingView`

**选择**：`Sheet` 的内容区包在 `KeyboardAvoidingView` 中（`behavior="padding"`，两端相同），键盘弹出时内容区连同标题与按钮整体上移，遮罩区域相应缩小。所有调用方无需改动。

**理由**：遮挡是「底部弹层」这一组件的问题，不是某个面板的问题；`Sheet` 是唯一实现，在这里处理，现有与将来的所有面板一次生效。验收实测，当前配置下 `Modal` 里的内容不会随键盘调整位置，因此由弹层自己避让，不依赖窗口层面的调整行为。

**备选方案与未采纳的理由**：

- **引入 `react-native-keyboard-controller`**：未采纳。它的动画与跟随效果更好，但是原生依赖，需要重新构建 dev client；而这里只需要「弹出时整体上移」，自带组件足够。若设备验收发现自带组件在 Modal 内表现不可接受，再回到此选项。
- **在 `app.json` 设置 `softwareKeyboardLayoutMode: "resize"`**：未采纳。它调整的是 Activity 窗口，`Modal` 是否跟随、edge-to-edge 下是否仍生效都未经验证，还需要重新 prebuild；而且只覆盖 Android，iOS 仍要另行处理。在组件内处理对两端都成立。
- **在每个带输入框的面板里各自处理**：未采纳。与决策 1 同理，六处拷贝迟早漏一处。

### 决策 3：本轮下载结果携带曲目标识，歌单页按本歌单曲目过滤

**选择**：`round` 改为记录 `completedIds: string[]` 与 `failed: { trackId, title, reason }[]`；`DownloadQueueSnapshot` 相应暴露曲目标识，`pending` 也改为可按曲目判断（等待中与下载中的 `trackId`）。歌单页用本歌单的曲目 id 集合与之求交，只统计、只展示属于本歌单的部分；交集为空时不显示结果。

**理由**：歌单页要回答的问题是「这个歌单的曲目下载得怎么样」，系统里对「某条结果属于哪个歌单」最准确的信号就是曲目 id 是否在这个歌单里。它同时覆盖了「在 A 歌单发起、打开 B 歌单」和「同一首歌同时在两个歌单里」两种情况，不需要记录「是从哪个页面发起的」。

**备选方案与未采纳的理由**：

- **记录发起下载的页面/歌单 id，只在该页面显示**：未采纳。同一首歌可能在多个歌单里，在 A 发起后打开 B 时，B 里这首歌确实在下载，却看不到结果；「发起位置」是间接信号。
- **离开歌单页时清空本轮结果**：未采纳。结果属于下载队列而不是页面，清空会让用户在下载中途切走再回来时丢失失败信息，违反 `offline-cache`「最终告知用户哪些曲目未成功」。

### 决策 4：序号列宽度按歌单总曲目数的位数计算

**选择**：`IndexedTrackRow` 增加 `positionWidth` 属性，由歌单页按 `String(tracks.length).length` 计算一次：两位数及以内保持设计稿的 22，每多一位增加一个数字的宽度（按 13 号字等宽数字约 8）。序号文本设 `numberOfLines={1}`。

**理由**：同一歌单里所有行的序号列必须等宽，行才对齐；而「最多有几位」只有列表知道，行组件自己推不出来。22 是设计稿给两位数的宽度，按位数扩展，小歌单外观不变。

**备选方案与未采纳的理由**：

- **序号容器改为 `minWidth: 22`，按内容撑开**：未采纳。第 99 行与第 100 行宽度不同，标题列会左右错位。
- **固定一个能容纳四位数的宽度**：未采纳。绝大多数歌单不到一百首，会让所有歌单的序号列都比设计稿宽。

### 决策 5：多段中文文案用单个字符串表达式书写

**选择**：5 处跨行 JSX 文本改为 `{'…'}` 或模板字符串，在源码中可以分行拼接，渲染结果不含换行折叠出的空格。含插值的版本确认文案同样改为模板字符串。

**理由**：JSX 把跨行文本的换行折叠为一个空格，这是语言规则，只能从书写方式上避开。

**备选方案与未采纳的理由**：

- **把文案写成一行**：未采纳。部分文案很长，一行书写会被 Prettier 保留为超长行，可读性差；表达式写法同样能分行。
- **增加 lint 规则禁止 JSX 中跨行的 CJK 文本**：未采纳。项目内没有现成规则可用，自写规则的成本高于收益；本次已全量扫描出 5 处，在 tasks 中记录扫描方法供将来复查。

### 决策 6：风险告知标记区分「未知」

**选择**：`riskAcknowledged` 初值为 `null`（尚未读到）。`guarded` 在值为 `null` 时先等待读取结果再决定是否弹出风险告知，而不是按「已确认」放行。

**理由**：风险告知是安装前的强制门槛，读不到状态时的默认值必须是「未确认」一侧，否则门槛在最开始的几百毫秒里是开着的。

**备选方案与未采纳的理由**：

- **初值改为 `false`**：未采纳。已确认过的用户在读取返回前点安装，会被多弹一次风险告知；`null` 才准确表达「还不知道」。
- **读取完成前禁用安装按钮**：未采纳。需要给按钮加一个不可用态与视觉，而读取通常在一帧内完成，等待即可。

### 决策 7：「未知专辑」「未知艺术家」分组以占位封面与曲目数展示

**选择**：`useCollections` 对没有专辑（或没有艺术家）信息的曲目聚合出的分组，`coverUri` 为 `null`（显示统一占位），`meta` 为「N 首」；有名称的分组保持现状。

**理由**：这个分组是「缺少该信息的曲目」的集合，不是一张专辑或一位艺术家，任何一首曲目的封面与艺术家都不能代表它。

**备选方案与未采纳的理由**：

- **不展示「未知专辑」分组**：未采纳。那些曲目会在专辑与艺术家视图里彻底消失，用户无从按这一维度找到它们。
- **封面取组内出现最多的一张**：未采纳。仍然是用个别曲目代表一个没有共同属性的集合。

## Risks / Trade-offs

- [`KeyboardAvoidingView` 在 Android 的 `Modal` 内偶有偏移不准或需要额外的 `keyboardVerticalOffset`] → 设备验收逐个面板检查；若偏差无法以常量修正，改走决策 2 的备选方案，单独评估原生依赖。
- [下载队列快照的形状变化影响其他读取方] → 目前唯一的读取方是歌单页（`src/app/playlist/[id].tsx`）；`pnpm typecheck` 兜底。
- [序号列宽度用估算的数字宽度，不同字体下可能略有偏差] → 使用 `fontVariant: ['tabular-nums']` 保证数字等宽，宽度留出余量；设备上用 1756 首歌单验收。

## Migration Plan

纯前端修改，无数据迁移、无原生改动，随普通 JS 包更新发布；回滚即回退代码。
