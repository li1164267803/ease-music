## Context

动机见 `proposal.md - Why`。本文只写实施所依赖的现状与约束。

C6a 留下的地基，本片全部直接复用，不改动：

- **候选曲目模型**（C6a 决策 3）与 `toCandidateTrack`：插件条目 → 候选曲目的转换、主键拼接、畸形条目丢弃规则，都在 `src/plugins/candidate.ts`。榜单与歌单里的曲目条目与搜索结果同构，走同一个函数。
- **统一调用通道**（C6a 决策 7）：`invokePlugin` 负责未实现、抛错、超时、畸形四类故障的归因，上层只提供 `call` 与 `parse`。发现层每接入一个协议方法就是多一对 `call` / `parse`。
- **裁剪机制**（C6a 决策 6）：插件实现只被 `index.android.ts` 及其下游引用；路由文件平台中立，转发到 `screens/*.tsx` 空实现，Android 由同名 `.android.tsx` 顶替。三道守卫（ESLint、`check:constraints`、`check:ios-strip`）已在跑。
- **入口位置**：插件相关入口目前只有一处——「我的」页的「插件音源」行，受 `Plugins.supported` 控制；插件管理页头部再链接到插件搜索。

协议侧的现状（对齐 MusicFree 公开规范，只参考协议不复制代码）：

| 方法                      | 参数                   | 返回形状                                                          |
| ------------------------- | ---------------------- | ----------------------------------------------------------------- |
| `getTopLists`             | 无                     | `[{ title, data: [榜单项] }]`，榜单项含 `id`、`title`、封面、描述 |
| `getTopListDetail`        | 榜单项, page           | `{ isEnd?, musicList: [曲目] }`                                   |
| `getRecommendSheetTags`   | 无                     | `{ pinned?: [标签], data: [{ title, data: [标签] }] }`            |
| `getRecommendSheetsByTag` | 标签, page             | `{ isEnd?, data: [歌单项] }`                                      |
| `getMusicSheetInfo`       | 歌单项, page           | `{ isEnd?, musicList: [曲目] }`                                   |

两个「详情」方法把曲目放在 `musicList`，与 `search` 的 `data` 不同；歌单项与标签是与曲目不同的两种展示对象。榜单项、歌单项、标签都要**原样**回传给插件作为下一步调用的参数——它们和曲目的 `sourceRef` 一样，是插件自己的凭据，宿主不解释其内部字段。

界面侧没有设计稿：`ui.pen` 里没有发现层的画面。本片沿用插件搜索页与插件管理页的既有视觉，不引入新的组件风格。

## Goals / Non-Goals

**Goals:**

- 五个协议方法各有确定的形状校验，畸形返回按 C6a 的既有归因处理，不新增任何故障处理路径。
- 榜单详情与歌单详情共用一个「候选曲目分页列表」屏，为 C6b 第二片（专辑、艺人详情）留出直接复用的页面模板。
- 不扩大 iOS 裁剪的守卫范围：不给平台中立门面增加成员，不新增裁剪检查项。

**Non-Goals:**

- 不为个别插件的越界返回写兼容分支（与 `candidate.ts` 对 `duration` 单位的态度一致）。协议里没有的字段名不认。
- 不做发现内容的任何缓存或预取，包括同一次会话内的返回复用——spec 要求每次进入实时请求。
- 不改 `invokePlugin` 的超时取值。发现方法与搜索一样是单次网络请求，沿用同一上限。

## Decisions

### 决策 1：发现能力按「插件是否实现了对应方法」在加载期判定，记入 `PluginMeta`

`PluginMeta` 增加两个布尔：`canBrowseTopLists`（实现了 `getTopLists`）与 `canBrowseSheets`（实现了 `getRecommendSheetTags`）。管理器新增 `discoveryPlugins()`，返回两者至少有其一的已加载插件。发现首页只向具备对应能力的插件发起调用，未实现的那一种在该插件名下不出现。

这与 `canSearchMusic`、`canResolveMedia` 的做法完全一致：能力在加载时一次判明，界面据此决定渲染什么，而不是调用后靠 `not-implemented` 错误来倒推。

**备选：运行时直接调用，捕获 `not-implemented` 后隐藏区块。** 未采纳：spec 要求「未实现不视为错误」，而 `invokePlugin` 会把未实现归为一次失败——那就得在发现层专门过滤这一种失败类型，把「能力有无」和「调用失败」两个概念揉在一条路径上。加载期判定让两者在源头上就是分开的。

**备选：只用一个 `canDiscover` 布尔。** 未采纳：spec 明确两种能力独立，一个插件只实现榜单是常态；合并成一个标志会让「只有榜单」的插件被迫触发一次必然失败的标签请求。

### 决策 2：发现入口挂在插件管理页头部，与插件搜索并列；平台中立门面不改

发现首页的路由是 `/plugin-discovery`，入口图标放在插件管理页头部、搜索图标旁边。发现首页与其下的三个列表页全部位于 `src/plugins/screens`，只被 Android 侧的管理页链接。

这样做的直接结果是 **`PluginsFacade` 一个成员都不用加**：进入发现层的唯一路径始于插件管理页，而管理页本身已经在裁剪线之内；`Plugins.supported` 在「我的」页那一处判断已经把整棵子树挡在 iOS 之外。proposal 的 Impact 起初写了「门面增加发现相关方法」，按本决策改为不改门面。

**备选：在首页「发现」Tab 增加榜单区块。** 未采纳：首页是核心播放器的一部分，加区块意味着首页要引用插件门面并按 `supported` 分支渲染，把裁剪判断从一处扩散到两处；且首页设计稿没有给这一区块留位置，硬加会打乱既有布局。第二片、第三片做完后如果发现层值得进首页，那时再单独评估。

**备选：在「我的」页再加一行「插件发现」。** 未采纳：和「插件音源」并列会让用户误以为是两套东西；发现内容本来就依附于插件，从插件页进去符合它的从属关系。

### 决策 3：榜单详情与歌单详情共用一个候选曲目分页屏，靠路由参数区分调用哪个方法

路由 `/plugin-discovery/tracks` 接收三个参数：`platform`、`kind`（`toplist` 或 `sheet`）、`item`（榜单项或歌单项）。屏内按 `kind` 选择 `getTopListDetail` 或 `getMusicSheetInfo`，其余逻辑——分页、追加、到底、失败展示、逐首加入——完全相同。搜索页里的 `CandidateRow` 抽到 `src/plugins/ui/candidate-row.tsx`，三处共用。

两个方法的返回形状一致（`musicList` + `isEnd`），共用一个 `parseTrackPage`。第二片的专辑详情、艺人作品同样是「某个条目 → 分页曲目」，届时只需在 `kind` 上再加两个值。

**备选：两个独立页面。** 未采纳：两页除了调用的方法名之外没有任何差别，重复的正是最容易在后续修改中走散的分页与失败处理逻辑。

**备选：把分页逻辑抽成 Hook，两页各自组合。** 未采纳：抽 Hook 之后两页的 JSX 仍然逐行相同，抽象只解决了一半重复。共用一屏是更彻底的去重。

### 决策 4：插件返回的榜单项、歌单项、标签以 JSON 序列化后经路由参数传递

榜单项等对象是插件的凭据，必须原样回传。它们不落库、没有本地 id，因此不能像歌单那样只传 id。本片把校验后的展示对象连同原始条目一起 `JSON.stringify` 进路由参数，目标页解析后原样交回插件。

**备选：模块级暂存表（token → 原始条目），路由只传 token。** 未采纳：暂存表是一份进程级状态，要回答「什么时候清」「进程被杀后回栈恢复时 token 失效怎么办」，这两个问题在 JSON 参数方案里根本不存在——参数随导航栈一起保存与恢复。插件条目本来就是从 JSON 反序列化来的，再序列化一次不会丢信息。

**已知边界**：个别插件可能在条目里塞很大的对象。本片不做防御——实测样本的条目都在几百字节量级；若真遇到，正确的做法是回到本决策重新评估，而不是在参数上加截断。

### 决策 5：每个协议方法一个校验函数，返回校验后的展示类型并保留原始条目

新增 `src/plugins/discovery.ts`，对五个方法各提供一个调用函数与一个 `parse`：

- 榜单项、歌单项统一为 `DiscoveryItem = { id, title, artworkUri, description, raw }`；`id` 与 `title` 缺一即丢弃该条，其余可空。封面认协议里的 `coverImg` 与 `artwork` 两个字段名——两者都出现在公开规范中，属于协议事实而非对个别插件的兼容。
- 标签为 `DiscoveryTag = { id, title, raw }`，`pinned` 合并进分组之前作为一个无标题分组。
- 分组为 `{ title, items }`；分组内为空的整组丢弃。
- 曲目页复用 `toCandidateTrack`，畸形条目丢弃、其余继续。

各列表页的分页只面向**单个插件**，不需要搜索那种跨插件的 `continuing` 游标：一个榜单或一个歌单天然属于一个插件，`isEnd` 就是全部。

`isEnd` 缺省的推断规则分两种，依据是「这个方法的返回里，到底的信号是什么」：

- 歌单列表（`getRecommendSheetsByTag`）与搜索同形（`{ isEnd?, data }`），直接复用 `parsePage`：缺省时结果为空才算到底。
- 曲目页（`getTopListDetail` / `getMusicSheetInfo`）缺省时**视为已到底**。spike 实测：不分页的插件（小蜗音乐的榜单详情）不给 `isEnd`，且对任何页码都返回同一整页——按搜索的规则会无休止地把同一页追加下去；而会分页的插件（两个样本的歌单详情）都给了 `isEnd`。「给了就按它说的，没给就是一整页」是这两个方法上更准确的信号；代价是某个既分页又省略 `isEnd` 的插件只会显示第一页，那是它偏离协议，宿主不猜。

**备选：把五个方法的校验都塞进 `search.ts` 的 `parsePage`，靠参数切换 `data` / `musicList`。** 未采纳：三种展示对象（曲目、榜单项或歌单项、标签）的形状不同，一个函数带开关只会让每个分支都要看别的分支才读得懂。

### 决策 6：发现首页对每个插件并发发起请求，按插件分区各自呈现加载与失败

进入发现首页时，对 `discoveryPlugins()` 里的每个插件并发调用它具备的方法（榜单、标签各一）。每个插件一个区块，区块内自带加载中、失败原因、内容三种状态，某个插件慢或失败不影响其他区块的呈现。

**备选：按插件折叠，用户展开后才请求。** 未采纳：多一次点击；实际安装的插件通常只有个位数，并发请求的代价可以忽略，而「打开就看到内容」才是浏览入口该有的样子。

**备选：所有插件请求汇总后一次渲染。** 未采纳：一个插件超时（上限 15 秒）会拖住整页；spec 要求单个插件故障不影响其余内容。

## Risks / Trade-offs

- **真实插件的返回形状与公开规范有偏差**（C6a 已实测有插件把 `duration` 以毫秒返回）→ 实施第一步就用现有样本插件跑通五个方法，把实际形状记进 tasks；偏差按 Non-Goals 的态度处理：协议内的字段名认，协议外的不认，由插件侧修正。
- **`getTopLists` 与 `getRecommendSheetTags` 无参数、无分页，个别插件可能一次返回很多榜单** → 首页用分组标题与横向滚动承载；不分页是协议决定的，不在宿主侧截断。
- **路由参数携带原始条目（决策 4）** → 条目异常巨大时导航可能变慢。实测样本无此问题；出现时回到决策 4 重评。
- **封面来自插件返回的远程地址，可能需要特定请求头才能访问** → 与搜索结果封面同一情况，`Artwork` 组件当前不带头访问；本片不解决，与搜索结果保持一致。
- **iOS 待复验**：本片全部代码在裁剪线之内，`check:ios-strip` 在产物层面验证；裁剪后的完整走查按 PRODUCT.md 的验收策略留待 iOS 全量验收。

## Migration Plan

无数据迁移。`PluginMeta` 新增的两个布尔在加载时计算，不持久化；已安装插件无需重新安装。
