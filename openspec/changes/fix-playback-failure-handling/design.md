## Context

动机见 `proposal.md`，行为契约见 `specs/media-playback/spec.md` 与 `specs/media-source/spec.md`。这里只记录实施要面对的现状。

播放层的全部状态集中在 `src/playback/player.ts`：一个模块级快照（`PlaybackSnapshot`）经 `useSyncExternalStore` 暴露给界面，唯一的 expo-audio 播放器实例被所有曲目复用（每次切歌调用 `player.replace`）。与本 change 相关的现状：

- **推进**：`advance(direction, auto)`。`auto` 同时被三处使用——曲目自然播完（`didJustFinish`）、装载失败（`handleLoadFailure`）、播放出错（`reportFailure`）。`queue.ts` 的 `step` 在 `loopOne && auto` 时返回当前曲目，`advance` 再对当前曲目执行 `seekTo(0) + play`。
- **失败**：快照里只有一个 `error: string | null`。`handleLoadFailure` 先 `publish({ error })`，随即 `advance(1, true)` → `load()` 开头 `publish({ error: null })`。连续失败以 `consecutiveFailures < queue.length` 为上限。失败后固定 `advance(+1)`，与用户刚才的切歌方向无关。
- **装载**：`load()` 在 `resolveTrack`（插件可能要几秒）期间不动引擎，上一首继续发声；这期间 500ms 一次的状态回调报的是上一首的位置、时长、是否在播，照常写进快照。`durationMs` 在装载开始时不重置。
- **状态**：`toState` 把引擎状态映射为 `idle / loading / buffering / playing / paused`。expo-audio 在 Android 上缓冲时 `playing` 返回「意图播放」（`intendedPlayingState`），非缓冲时返回 `isPlaying`；界面按钮只认 `state === 'playing'`，`loading` 与 `buffering` 都显示成 ▶。
- **引擎错误**：expo-audio Android 侧 `onPlayerError` 只回传 `error.message`（ExoPlayer 的 `PlaybackException`，对 HTTP 404、连接失败、解码失败都可能只是「Source error」），错误码与 HTTP 状态码在桥接层被丢弃。
- **锁屏控件**：`updateLockScreen` 首次调用 `setActiveForLockScreen(true)`，此后只更新元数据；清空队列时从不撤下。

## Goals / Non-Goals

**Goals:**

- 每个状态字段都有唯一、准确的来源，界面不需要组合多个字段去猜
- 推进规则保持为 `queue.ts` 里可单测的纯函数
- 两端共用同一段 TypeScript，不改原生代码

**Non-Goals:**

- 不引入全局 Toast / 通知系统。失败提示落在已有的迷你播放器与播放页上
- 不改变「每次播放实时解析地址」的既有决策（`bootstrap-music-player/design.md` 决策 4）
- 不调整 500ms 的状态回调间隔

## Decisions

### 决策 1：推进原因显式化——`finished` / `skipped` / `user`，取代布尔 `auto`

**选择**：`advance` 与 `step` 接收推进原因而不是 `auto`：

- `finished`：曲目自然播完。只有它在单曲循环下返回当前曲目，顺序模式到末尾返回 `null`
- `skipped`：装载失败或播放出错后的跳过。在任何播放模式下都按方向移动（单曲循环视同列表循环），到达队列边界时顺序模式停止
- `user`：用户点上/下一曲。行为与现在的 `auto: false` 相同

`advance` 里「单曲循环同一首 → `seekTo(0) + play`」只在 `finished` 时成立；此时引擎里装着的一定是刚播完的当前曲目，重播不必重新解析。

**理由**：单曲循环 bug 的根因是「自然播完」和「失败后跳过」共用了一个信号。`step` 本来就知道模式与方向，缺的只是「为什么要推进」这一条事实——把它作为参数传进来，是系统里对这件事最准确的表达；任何在 `advance` 内部判断「当前是不是刚失败过」的写法，都是在从副作用反推原因。

**备选方案与未采纳的理由**：

- **在 `handleLoadFailure` 里临时把播放模式当成列表循环再调 `advance`**：未采纳。那是在共用路径上加特判，下一个调用者（例如将来的「播放出错后重试」）又要知道这个约定。
- **单曲循环下失败时直接停止**：未采纳。spec 要求单曲失败不中断队列；单曲循环的语义是「自然播完后重复」，不是「把用户锁死在一首播不了的歌上」。

### 决策 2：跳过沿用触发装载的那次导航的方向

**选择**：`load()` 接收本次装载的方向（`1 | -1`），失败时以该方向执行 `skipped` 推进。`next()` 与自然播完为 `1`，`previous()` 为 `-1`；`playQueue` / `playTrackAt`（用户直接点某一首）为 `1`。跳过链上的每一次装载继承同一方向。

**理由**：用户点「上一曲」表达的是「往前走」，跳过失败曲目是在替用户继续这次导航。方向是发起导航时就确定的事实，随装载一起传下去即可，不需要事后推断。

**备选方案与未采纳的理由**：

- **记住「上一次成功播放的曲目」，失败时跳离它**：未采纳。在随机模式与多次连续失败下，「离开哪首」推不出「往哪边走」，而且要多维护一个状态。
- **失败时总是向后跳（现状）**：未采纳，这正是「上一曲」被弹回原曲的原因。

### 决策 3：失败记录归属曲目，不随装载清空

**选择**：快照中的 `error: string | null` 改为 `failure: { trackId, title, message } | null`。

- **写入**：装载失败、播放出错、连续失败达到上限时写入，新的失败覆盖旧的
- **清除**只有三条，每条对应一个具体事实：
  1. 用户在播放页关闭提示（`clearFailure`）
  2. `failure.trackId` 这首曲目之后成功开始发声——提示描述的事实已不成立
  3. 队列清空——提示所指的曲目已不在任何播放入口中
- `load()` 开头不再触碰失败记录

**界面落点**：播放页沿用现有的失败卡片，内容改为「「标题」播放失败：原因」，点击关闭；迷你播放器在 `failure` 存在时于副标题前显示警示图标（与曲目行「文件已失效」的 `TriangleAlert` 同一视觉语言），点击迷你播放器进入播放页即可看到原因。

**理由**：失败提示是对「某一首曲目」的反馈，它的生命周期应当由这首曲目的事实决定，而不是由「下一次装载开始」这个与它无关的事件决定。现状注释写的是「下一次成功装载时自动清空」，实现却在装载开始时清空——把清除条件绑定到曲目之后，注释描述的意图才真正成立。

**备选方案与未采纳的理由**：

- **保留字符串，改为「装载成功时」才清空**：未采纳。跳到下一首成功播放时仍会清掉上一首的失败原因，用户在列表页照样看不到；它只是把清空时机后移了几百毫秒。
- **失败历史列表（记录最近 N 次失败）**：未采纳。spec 只要求能看到失败原因，列表需要新的界面入口与清理策略，属于过度设计；连续失败时，最后一条加上「连续 N 首」的汇总已足够说明情况。
- **迷你播放器副标题直接替换为失败文案**：未采纳。自动跳过后迷你播放器显示的是正在播的下一首，把它的艺人名换成另一首的失败原因会让用户误以为当前这首坏了；图标只提示「有事」，细节留给播放页。

### 决策 4：连续失败上限为固定常量 5，取代「队列长度」

**选择**：`MAX_CONSECUTIVE_FAILURES = 5`。任一曲目成功开始发声即归零；达到上限时停止跳过、暂停，失败记录的文案为「连续 5 首无法播放，已停止。最近一首「标题」：原因」。用户随后手动点下一曲或选曲会重新开始计数。

**作废**：`player.ts` 中「以队列长度为上限计数」的旧规则作废。

**理由**：自动跳过存在的意义，是不让零星的坏曲目打断收听。连续失败意味着问题不在单首曲目（来源下线、插件接口 503、断网），继续尝试只会以每秒一首的速度消耗网络请求、给第三方服务加压，并且一直占着界面。队列长度与「问题是否系统性」毫无关系——1756 首的歌单会被逐首尝试一遍，这正是验收中观察到的现象。

5 的取舍：零星失效链接连续出现 2–3 首并不罕见，上限太小会让用户频繁手动续播；超过 5 首还在失败，几乎可以确定是系统性原因，而 5 次请求的代价可以忽略。

**备选方案与未采纳的理由**：

- **按来源判断系统性失败（同一来源连续失败即停止）**：未采纳。「来源」是解析层的概念，播放器按来源分支会违反 `media-source`「新增来源不得要求修改播放器」；而且混合来源的队列里，一个来源整体失效时，其余来源的曲目仍应继续播，按来源停反而误伤。
- **按失败原因文本相同判断**：未采纳。原因文本由各来源自由书写（插件异常信息里常带随机 id），不是稳定的判定依据。
- **按时间窗口（例如 10 秒内失败 N 次）**：未采纳。解析耗时从毫秒（本地文件）到十几秒（插件超时）不等，时间窗口在两端都会误判，计数更直接。

### 决策 5：装载开始即脱开上一首音源；引擎状态以「音源归属」过滤；按钮读播放意图

**选择**：

1. **脱钩**：`load()` 开始时暂停引擎，并立即发布新曲目的 `positionMs: 0`、`durationMs: track.durationMs ?? 0`，同步系统媒体控件的元数据。
2. **音源归属**：新增 `sourceToken`，在 `player.replace` 成功时记为当次的 `loadToken`。`onStatus` 在 `sourceToken !== loadToken` 时丢弃回报——那段时间引擎里装的不是当前曲目，它的位置、时长、是否在播都与界面上的曲目无关。
3. **播放意图**：快照新增 `playWhenReady: boolean`，界面的播放/暂停按钮只读它：
   - 装载开始时取 `autoPlay`
   - 装载中用户点暂停/播放，只改意图；`replace` 完成后按意图决定是否 `play()`
   - 音源已归属当前曲目后，由 `onStatus` 的 `status.playing` 同步（expo-audio 在缓冲时回报的正是意图，锁屏或音频焦点导致的暂停也经由这里回到界面）
4. **指示**：`state` 的取值不变。`loading` 或 `buffering` 且 `playWhenReady` 为真时，迷你播放器副标题显示「正在加载…」/「缓冲中…」，播放页在进度条下方的时间行中间显示同样的文案。
5. **失败后按播放**：当前曲目的音源不在引擎里（`sourceToken !== loadToken`，例如装载失败后停下）时，`togglePlayPause` 重新装载当前曲目，而不是对引擎里残留的上一首调用 `play()`。

**理由**：验收看到的三个现象——单曲循环下「界面是 A、发声是 B」、失败后显示上一首的时长、加载时像已暂停——都来自同一件事：界面把「引擎的回报」当成了「当前曲目的状态」。系统里对「这份回报属于哪首曲目」最准确的信号是 `replace` 发生在哪次装载里，用令牌标记即可，不需要比较地址或时长去猜。按钮同理：按钮表达的是「用户想不想播」，这是意图，不是引擎此刻是否发声；把意图作为一等字段，加载与缓冲两个阶段就不再需要各自特判。

**备选方案与未采纳的理由**：

- **装载开始时 `player.replace(null)` 清空音源**：未采纳。expo-audio 对空音源下媒体会话与锁屏控件的行为未经验证，两端也可能不一致；暂停加令牌过滤已足够切断上一首的发声与状态，不需要依赖这条未知路径。
- **不加意图字段，按钮改为 `state !== 'paused' && state !== 'idle'`**：未采纳。`appendToQueue` 的预装载（`autoPlay: false`）同样处于 `loading`，按钮会错误地显示为「正在播放」；加载中点暂停也无处记录。
- **新增 `PlaybackState` 取值（如 `loading-paused`）**：未采纳。状态与意图是两个正交维度，塞进一个枚举会让组合爆炸，所有读 `state` 的地方都要跟着改。

### 决策 6：引擎错误的原因诊断——失败后对 http(s) 地址补一次探测

**选择**：`onStatus` 收到引擎错误时，若当前音源是 http(s) 地址，携带与播放相同的请求头与 User-Agent 发一次 `Range: bytes=0-1` 的 GET（8 秒超时），据结果生成原因：

| 探测结果        | 报告                                            |
| --------------- | ----------------------------------------------- |
| 连接失败 / 超时 | 无法连接到音频地址，请检查网络后重试。          |
| HTTP 4xx / 5xx  | 音频地址返回了错误（HTTP 状态码），可能已失效。 |
| HTTP 2xx / 206  | 音频无法解码，格式不受支持或文件已损坏。        |

非 http(s) 音源（本地文件、离线缓存）不探测，直接报告「音频无法解码，格式不受支持或文件已损坏。」探测期间失败处理照常进行（计数、跳过），探测结果到达后只更新该曲目的失败记录文案；若此时失败记录已属于其他曲目，丢弃结果。解析阶段的失败（`MediaResolutionError`）自带中文说明，不探测。

**理由**：原因之所以只剩「Source error」，是因为引擎的错误码在 expo-audio 桥接层被丢弃了。在不改原生代码的前提下，「这个地址现在是什么情况」最直接的信号就是服务端对同一请求的回应，而用户需要的恰恰是这个区分：网络问题稍后重试，地址失效就该换源或删除。它发生在**失败之后**、只针对失败的那一首，与 `remote-url` 来源里「刻意不在解析阶段做可达性预检」的决策不冲突——那条决策反对的是给每次播放加一轮往返。

文案的措辞与离线缓存 `describeFailure` 已有的 HTTP 状态码文案保持一致。

**备选方案与未采纳的理由**：

- **给 expo-audio 打补丁，在 `onPlayerError` 里透出 `errorCodeName` 与 HTTP 状态码**：未采纳。这是信息最完整的做法，但要同时修改 Android（ExoPlayer）与 iOS（AVPlayer，错误体系完全不同）两份原生代码，每次升级 Expo SDK 都要重新对齐补丁，并需要重新构建 dev client；而本 change 需要的三种区分，探测已经能给出。若将来需要区分探测覆盖不到的错误（例如 DRM、特定编码不支持），再单独评估。
- **按错误信息文本做正则匹配**：未采纳。Android 回传的文本对这几类故障都是同一句「Source error」，没有可匹配的内容。
- **不诊断，只把原文翻译成「播放失败」**：未采纳。`media-source` spec（本 change 修改后）要求区分地址错误与无法连接。

### 决策 7：队列清空时撤下系统媒体控件

**选择**：`clearQueue` 与 `removeFromQueue` 使队列变空时调用 `player.clearLockScreenControls()`，并把 `lockScreenActive` 置回 `false`，下一次装载重新走 `setActiveForLockScreen(true)`。

**理由**：系统媒体控件展示的是「当前曲目」，队列空了就没有当前曲目；撤下是这一事实的直接映射。

**备选方案与未采纳的理由**：

- **只清空元数据、保留控件**：未采纳。通知栏会留下一张空白的媒体卡片，Android 上还会继续占用前台服务。

## Risks / Trade-offs

- [探测请求在服务端产生额外访问，且结果可能与播放当时不同（例如带时效的签名地址恰好过期）] → 只在失败后、对失败的那一首发一次；文案措辞为「可能已失效」，不据此标记曲目失效（proposal 非目标）。
- [探测把错误报成「无法解码」，而真实原因是引擎侧的网络抖动] → 2xx 意味着地址此刻可用，用户重试即可验证；属于可接受的误报方向，不会导致曲目被删除或标记。
- [上限 5 在「长串失效链接夹杂少量可用曲目」的歌单里会提前停止] → 停止时文案明确「连续 5 首无法播放」，用户点下一曲即可继续，计数重新开始。
- [装载期间暂停引擎，插件解析慢时会有一段静音] → 这是正确的语义：界面已经切到新曲目，继续播放上一首才是错误。加载指示（决策 5）让这段静音可被理解。
- [改动集中在播放核心，回归面广] → `queue.ts` 的推进规则补单测；设备验收覆盖四种播放模式下的成功切歌、自然播完、失败跳过，以及锁屏控制与后台播放。

## Migration Plan

纯前端逻辑修改，无数据迁移、无原生改动。按 tasks.md 顺序实施，可随普通 JS 包更新发布；回滚即回退代码。
