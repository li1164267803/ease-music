## Context

动机见 `proposal.md - Why`，功能全景与路线图见 `openspec/PRODUCT.md`。这里只记录塑造技术方案的约束。

这是一个从零开始的项目，本 change 确立的分层与技术栈将约束后续所有 change。有三项后续能力虽不在本 change 范围内，但直接影响当前的架构选择，必须一并考虑：

1. **离线缓存（C2）** — 需要在「解析出地址」与「实际播放」之间插入一层，且不改动上层。
2. **115 网盘接入（C5）** — 需要 OAuth 鉴权、目录遍历、带鉴权的流式播放、以及可能的 HTTP Range 分段读取。
3. **插件音源系统（C6）** — 参考 MusicFree 的插件协议规范自主实现。插件是运行在应用 JS 引擎中的 CommonJS 模块，通过 `Function` 构造器动态执行。

参考项目 MusicFree（AGPL-3.0）验证了插件方案在 React Native + Hermes 上的可行性：其 `android/gradle.properties` 中 `hermesEnabled=true`，插件经由 `Function` 构造器执行，量产版本正常运行。**本项目仅参考其协议规范与设计思路，不复制其源代码**，以避免 AGPL 的传染性约束。协议接口定义本身不受版权保护。

产品将同时上架应用商店与开源发布，这两条路径各自带来约束，见决策 7 与决策 9。

## Goals / Non-Goals

**Goals:**

- 确立一套来源无关的分层：曲库与播放器不感知曲目的来源类型
- 来源抽象必须能容纳后续的网盘来源、插件来源与缓存层，且新增来源不触发上层重构
- 数据模型一次到位，避免后续能力（歌单、历史、备份）反复改表
- 技术栈选择要让后续的插件系统「可以顺手做」，而不是「需要额外造运行时」

**Non-Goals:**

- 不追求本 change 内就把来源抽象做到完全通用。只保证已识别的后续来源装得进去
- 不为鸿蒙做任何妥协。鸿蒙已明确排除，此前为其考虑的约束（原生库需有 `@react-native-oh-tpl` 适配、避免 Expo 运行时、KV 存储需抽象）**全部作废**
- 不在本 change 内建立完整的设计系统。UI 以能验证核心能力为准

## Decisions

### 决策 1：跨平台框架选用 React Native，而非 Flutter

**理由**：决定性因素是插件系统的载体形态。插件是 JavaScript 代码，需要在运行时动态执行。

- React Native 的宿主本身就是 JS 引擎，`Function` 构造器直接可用，成本为零
- Flutter 的 Dart AOT 不支持 eval，必须内嵌 QuickJS（Android）/ JavaScriptCore（iOS），并额外承担：把插件依赖的纯 JS 库打包进该运行时、为 HTTP 客户端手写桥接回 Dart（QuickJS 无 XHR/fetch）、处理 Promise 跨 Dart↔JS 边界、以及同时对两个不同 JS 引擎的行为差异负责

**备选方案 Flutter 的真实优势**（已评估并接受放弃）：`just_audio` + `audio_service` 的音频栈成熟度高于 `react-native-track-player`；Dart isolate 是真多线程，批量元数据处理优于 JS 单线程；自绘引擎在复杂动画场景更稳。

**为何仍不选 Flutter**：插件在 iOS 上存在上架合规问题，因此插件实际上是 Android 独占能力。为一个单平台增强功能付出「自建并长期维护一个 JS 运行时」的代价不成立；而选 RN 时该能力的成本为零，不做也不亏。此外开发者本身是 React 技术栈，个人项目中学习成本是真实的完成率风险。

**接受的代价**：音频播放能力弱于 Flutter 方案，需要在实施早期摸清 `react-native-track-player` 的边界。

### 决策 2：使用 Expo（Development Build 工作流），而非裸 React Native CLI

**理由**：截至 2026 年，React Native 官方文档推荐新项目使用 Framework，Expo 是唯一推荐项（React Conf 2024 起）。社区采用率佐证：State of React Native 2025（3501 份回答）中 Expo Router 在导航库类别占 71%。

对本项目价值最大的两点：
- **RN 版本升级**：Expo 把 RN 升级与全部原生依赖的版本对齐打包为一次 SDK 升级。个人项目长期停摆后的升级成本是常见的项目死因
- **构建**：EAS Build 云端构建，无需本地维护 Xcode 证书与 Android SDK/NDK

**必须是 Development Build 而非 Expo Go**：`react-native-track-player` 是原生模块，Expo Go 无法加载。

**备选方案**：裸 RN CLI。此前因鸿蒙约束（`expo-*` 无 OpenHarmony 适配）曾倾向该方案；鸿蒙排除后此理由失效。

**版本锁定**：Expo SDK 57 / React Native 0.86。

### 决策 3：播放引擎选用 expo-audio

> **本决策已于实施阶段推翻重写。** 原方案为 `react-native-track-player`，理由是它原生提供播放队列 + 后台播放 + 锁屏/通知栏媒体控制 + 耳机按键这一整套，而当时的 `expo-audio` 只做音频播放本身、媒体会话需自行补齐。原决策同时预留了「该库历史上有过维护断档，需在实施早期验证，若存在硬缺口需尽早暴露」——下面就是那个硬缺口。

**推翻原方案的事实**（2026-08 在任务 1.4 装依赖时发现，早于 spike 2.2）：

1. `react-native-track-player` 自 v5 起**转为商业授权**，包名更为 `@rntp/player`（当前 5.8.0，`license: SEE LICENSE IN <license.txt>`），个人与教育用途免费，商用需付费。
2. Apache-2.0 的 v4 线**已冻结**：npm `latest` 停在 4.1.2（2025-08-12），官方声明 v4 分支不再更新。该版本早于 React Native 0.82 删除旧架构，对 RN 0.86 / Expo SDK 57 的兼容性无人负责。
3. 商业授权版**与本项目的 GPL-3.0 分发冲突**。GPL 第 6 条不允许对接收者施加进一步限制，专有授权的第三方库无法与 GPL 代码一并分发，且会直接断绝 F-Droid 收录——这与决策 9 派生约束 2（依赖不得引入无法由维护者自行授权的第三方库）是同一条红线，只是方向相反：那里防的是 GPL 传染，这里防的是专有授权反噬。

参考项目 MusicFree 使用 `react-native-track-player: ^4.1.1`，但其运行在 RN 0.76.5 / Expo SDK 52 上——旧架构直到 RN 0.82 才移除，因此它**不能作为该库在 RN 0.86 上可用的依据**；相反，它停留在两年前的 SDK 这一事实本身，正是决策 2 所警惕的「被原生模块拖住导致升级停摆」的实例。

**改选 `expo-audio` 的理由**：原决策排除它的前提（媒体会话能力缺失）在 SDK 57 上已不成立。核对其源码而非文档所得：

- `AudioPlayer.setActiveForLockScreen(active, metadata, options)` / `updateLockScreenMetadata` / `clearLockScreenControls` 提供锁屏与通知栏媒体会话。iOS 侧 `MediaController.swift` 注册 `playCommand` / `pauseCommand` / `togglePlayPauseCommand` / `changePlaybackPositionCommand` / `skipForward` / `skipBackward`；Android 侧走 media3 `MediaSession` 配合 `AudioControlsService` 前台服务。
- `setAudioModeAsync({ interruptionMode: 'doNotMix', shouldPlayInBackground: true })` 覆盖音频焦点与后台播放；`AudioStatus` 暴露 `isBuffering` / `error` / `duration` / `currentTime` / `didJustFinish`，满足 spec 的播放状态可观测要求。
- **`AudioSource` 直接支持 `headers`**，与决策 4 的契约形状（可播放地址 + HTTP 请求头 + User-Agent）天然吻合，无需额外适配。
- 许可证为 MIT，且随 Expo SDK 一同升级——这正是决策 2 选择 Expo 的核心收益，改用它反而让该收益覆盖到播放引擎本身。

**接受的代价一：锁屏、通知栏与蓝牙设备上没有「上一曲/下一曲」按钮。** 这是 `expo-audio` 的主动设计而非疏漏——Android 侧 `AudioMediaSessionCallback.kt` 显式 `.remove(Player.COMMAND_SEEK_TO_NEXT_MEDIA_ITEM)` 等四条曲目导航命令，iOS 侧从未注册 `nextTrackCommand`；且 `setActiveForLockScreen` 只挂在 `AudioPlayer` 上，具备队列 API 的 `AudioPlaylist` 没有锁屏能力。

对照 `media-playback` 的「系统级媒体控制」要求：三个 scenario（锁屏点击暂停、耳机播放/暂停键、媒体控件显示标题/艺术家/封面）**均可满足**，spec 无需修改。做不到的是车机与蓝牙耳机上的切歌操作——它没有写进 spec，但对音乐播放器是日常操作。本 change 如实记录该缺口并接受，若日后判断必须补齐，写一个只负责注册媒体会话命令并转发到 JS 的最小 Expo Module 即可，成本可控且不触动分层。

**接受的代价二：播放队列自行实现。** `expo-audio` 的 `AudioPlaylist` 虽有队列 API，但不支持锁屏，因此播放层采用 `AudioPlayer` + 自研队列。这不构成额外成本——spec 要求的四种播放模式（顺序、列表循环、单曲循环、随机）本就无法由任何现成队列直接表达，且每首曲目播放前需按来源实时解析地址（决策 4 的关键约束），队列本来就必须掌握在自己手里。

### 决策 4：来源解析契约的形状

统一契约的输出形状定为：**可播放地址 + HTTP 请求头 + User-Agent**。

**理由**：这个形状的抽象力已被 MusicFree 的生产实践验证（其 `IMediaSourceResult` 即为此形状），能同时覆盖：
- 本地文件（返回文件路径）
- 远程直链（返回 URL，无需请求头）
- 网盘（返回带鉴权 token 的临时直链 + 必要的请求头/UA）
- 插件（返回插件解析出的地址 + 防盗链请求头）

采用与既有生态一致的形状，也为后续插件兼容性降低了摩擦。契约由本项目自主定义与实现。

**关键约束**：曲目记录中必须保存「该来源重新解析所需的信息」，而不是保存解析结果。因为网盘与插件返回的地址通常是时效性的，缓存地址会导致过期后无法播放。

**为 C2 离线缓存预留**：播放前的地址解析必须是一个可拦截的单一入口，使缓存层能够在此处判断「本地已有缓存则返回缓存路径，否则走来源解析」。本 change 需保证该入口的唯一性，但不实现缓存逻辑。

### 决策 5：本地文件与网盘作为宿主内置来源，不作为插件

**理由**：插件运行在受限的 JS 沙箱中，只能使用纯 JS 依赖，无法处理大文件流式读取、断点续传、后台下载、以及需要原生能力的文件系统访问。MusicFree 的实现也印证了这一分层——其播放地址解析的第一优先级是本地路径检查，本地文件在其架构中同样是宿主一等公民而非插件。

因此来源分为两类，二者实现同一契约但实现位置不同：
- **内置来源**：本地文件、远程 URL、（C5）115 网盘 —— 原生能力可用
- **插件来源**：（C6）沙箱中的第三方音源 —— 受限但可动态加载

### 决策 6：曲库持久化使用 SQLite，配置使用轻量 KV

**理由**：spec 要求支持数千首曲目的排序与关键词检索，歌单要求多对多关联查询，后续还有播放历史（C3）与备份导出（C4）。这些都需要结构化查询，`expo-sqlite` 适配该场景。播放模式等少量配置项使用轻量 KV 存储即可。

此前因鸿蒙约束而要求的「KV 存储需抽象出接口以便替换实现」不再必要，可直接使用具体实现。

### 决策 7：iOS 与 Android 在本 change 内能力完全一致

平台差异仅会出现在插件系统（C6）中：App Store 审核指南 2.5.2（不得下载执行改变应用功能的代码）与 2.3.1（不得包含未披露的隐藏功能）使得插件音源在 iOS 上无法合规上架。已确定的处置方向是**插件系统作为编译期可裁剪模块，iOS 构建不包含该模块**——iOS 包中不存在相关代码，可在审核说明中如实陈述。

明确排除的方案：远程开关（审核期关闭、过审后开启）。该行为属于欺骗审核，后果为开发者账号终止而非单次拒审，且封禁关联开发者身份信息。

**本 change 需保证的是**：核心能力（本地文件、远程 URL、曲库、歌单、播放）不依赖插件模块，裁剪后 iOS 版本仍是功能完整的播放器。这是一条必须在实施中持续守住的约束，而非一次性检查项。

### 决策 8：歌单采用独立关联表建模多对多关系

歌单与曲目的关系用独立的关联表表达（歌单 id、曲目 id、歌单内序号），而非在曲目记录上存储歌单列表。

**理由**：
- spec 要求一首曲目可属于多个歌单，且歌单内顺序由用户指定——顺序是「关系」的属性而非「曲目」的属性，必须存在关联表上
- 曲目从曲库移除时需级联清理其在所有歌单中的条目，关联表配合外键约束可直接表达该语义
- 后续的播放历史（C3）与备份导出（C4）都需要查询这层关系，规范化建模避免届时重构

**备选方案**：在曲目记录中存 JSON 数组记录所属歌单。被否决——无法表达歌单内顺序，且检索「某歌单包含哪些曲目」需要全表扫描。

### 决策 9：开源与上架并行带来的约束

**应用标识**：项目定名为「琥珀音乐 / AmberMusic」，标识见 `openspec/PRODUCT.md - 项目标识`。对本 change 的直接约束是三处标识必须一次定死、不得在实施中临时拍板：Expo `app.json` 的 `name`（琥珀音乐）与 `slug`（`amber-music`）、`android.package` 与 `ios.bundleIdentifier`（均为 `com.ambermusic.app`）。包名一旦提交到应用商店即无法变更，重命名意味着重新上架并丢失全部下载量与评价，因此必须在 EAS Build 首次出包前确定。英文名在代码、文档与商店材料中固定连写 `AmberMusic`，不单独使用 `Amber`——GNOME Amberol 是同品类知名开源播放器，词形相近。

**许可证：GPL-3.0（已确定）**。本项目不复制 MusicFree 源代码，因此不受其 AGPL 传染，可自由选型。

选 GPL-3.0 的理由与已接受的代价：

- **能拦住 iOS 侧套壳**：GPL 第 6 条禁止对接收者施加进一步限制，而 App Store 的 DRM 与设备数限制构成该限制。套壳者不是版权人，无权为 Apple 做额外授权，因此上不了 App Store；维护者作为版权人可以自我豁免。这是同一份协议下的不对称优势
- **保留开源身份与 F-Droid 收录资格**，后者的用户群与本产品的目标用户高度重合
- **接受的代价**：GPL 允许商业使用。Android 侧套壳者只要开源其修改即可合规上架 Google Play，该侧只能靠商标与 DMCA 应对。若日后判断商用管控优先于开源身份，可改用 PolyForm Noncommercial 一类的源码可见协议，但那将失去开源身份与 F-Droid
- **方向可逆性**：从 GPL-3.0 放宽到 Apache-2.0 / MIT 随时可行且有效；反向收紧无效（最后一个宽松版本永远可被闭源分叉）。因此起步选严格一侧是安全的默认

**未采纳的方案**：

- **AGPL-3.0**（MusicFree 的选择）：其第 13 条针对网络服务场景，本项目为纯客户端、无服务端，条款永远空转；却要额外承担更高的上架敏感度与更小的贡献者池（多家公司明令禁止使用 AGPL 代码）。MusicFree 的约束条件与本项目不同——它不上 App Store，且需防范插件生态被服务化
- **Apache-2.0 / MIT**：允许闭源套壳并上架，防套壳完全依赖商标
- **在开源协议上附加「禁止商用」声明**：GPL 系第 7 条禁止附加额外限制，此类声明要么无效，要么使授权状态含糊。MusicFree 的 README 即存在「AGPL-3.0 + 禁止商业使用」这一自相矛盾的表述，不应效仿

**由此派生出三条必须长期守住的约束**：

1. **维护者必须始终是唯一版权持有人**。接受任何外部 PR 之前 CLA 必须就位（`CLA.md`，含「以任何许可证再许可」条款）。一旦合并了未签 CLA 的贡献，iOS 版本即失去合规上架的前提，且许可证的可逆性一并丧失
2. **依赖不得引入 GPL / LGPL / AGPL 授权的第三方库**。CLA 只能解决贡献者的代码，无法解决第三方库——维护者无权替他人的 GPL 库向 Apple 做额外授权。当前技术栈是安全的（Expo 为 MIT、`react-native-track-player` 为 Apache-2.0、`expo-sqlite` 为 MIT），但每次新增依赖都需核查许可证
3. **源文件头部需附 GPL 声明块**，在工程初始化（任务 1.1）时随模板一并建立

**免责声明**：README 必须明确本应用不提供、不内置、不分发任何音源。这既是产品定位的表达，也是开源发布时的必要声明。

**插件源中立**：C6 实现插件系统时，不得内置或默认指向任何插件源，插件完全由用户自行获取和安装。此约束在本 change 内无需实现，但记录于此以免后续遗忘。

**上架材料**：隐私政策、数据收集说明等在首次提交商店前准备。本 change 不涉及任何用户数据上传，应如实声明为不收集。

**[~~react-native-track-player 无法满足锁屏/音频焦点要求~~]** → **该风险已在任务 1.4 兑现，且以更严重的形式：库转为商业授权、开源版冻结。处置见重写后的决策 3——改用 `expo-audio`。** 风险预案（「若存在硬缺口，可评估补写原生模块或更换方案，此时项目尚未在其上堆积代码」）按设计生效：发现时间点在装依赖阶段，播放层尚无一行代码。

**[expo-audio 的媒体会话能力在真机上不及预期]** → 决策 3 的结论来自阅读 `expo-audio` 的 iOS/Android 原生源码，尚未经真机验证。spike 2.2 仍需在两端真机上确认锁屏控制、通知栏控制、耳机按键、来电打断恢复实际可用。若发现进一步缺口，补写最小媒体会话原生模块是既定退路，且不触动分层。

**[数据模型在后续 change 中被迫重构]** → 歌单的多对多关系已按决策 8 规范化建模，播放历史与备份导出的查询需求已在建模时纳入考虑。剩余风险主要来自 115 网盘曲目可能需要的额外字段（如网盘文件 id、父目录），缓解方式是曲目记录中「来源重解析所需信息」采用可扩展的结构而非固定列。

**[核心能力意外依赖插件模块]** → 决策 7 的约束若在实施中被破坏，将直接导致 iOS 无法上架。缓解方式：本 change 完成时显式验证「不存在插件模块的情况下应用功能完整」，并在后续 change 中保持该验证。

**[误用 MusicFree 源码导致 AGPL 传染]** → 实施过程中参考其协议规范与文档，不复制源码。该约束在 C6 中影响最大，本 change 内基本不触及。

## Spike 结论

### spike 2.1：音频元数据解析 —— 采用 `music-metadata` 11.14.0（MIT）

原设计把该库列为首选但标注「依赖 Node 生态假设，RN 下可行性未验证」。**该顾虑已过期**：`music-metadata` v11 的 `exports` 映射提供 `node` 与 `default` 两套入口，`default` 指向不含任何 Node 内置模块的 `lib/core.js`。Metro 的解析条件不含 `node`，因此在 RN 下自动选中该入口，无需 polyfill、无需改 Metro 配置。

实测结果（`ffmpeg` 生成的带标签样本，仅以 `Uint8Array` 调用 `parseBuffer`，不经 `Buffer` / `fs` / stream）：

| 容器 | 标题 / 艺术家 / 专辑 | 音轨号 | 时长 | 内嵌封面 |
| --- | --- | --- | --- | --- |
| MP3（ID3v2.3） | ✅ 含中文，UTF-8 正确 | ✅ `{no:7, of:12}` | ✅ 3.030s | ✅ `image/png` |
| FLAC（Vorbis Comment） | ✅ | ✅ | ✅ 3.000s | ✅ 支持 |
| M4A（MP4 atom） | ✅ | ✅ | ✅ 3.023s | ✅ 支持 |
| 无标签 MP3 | 字段为 `undefined` | `{no:null}` | ✅ 仍可得 | 无 |

另外三项对实现方式有直接影响的发现：

1. **可以只读文件头部。** 喂入前 8KB 即可解出标题、封面与时长（时长来自首帧的 Xing/Info 头）。因此导入流程采用「先读头部 → 若 `format.duration` 缺失再读全文件」的策略，避免为数千首曲目逐个整文件载入内存。缺少 Xing 头的 CBR 文件需要全文件扫描才能得到准确时长，这是回退路径存在的原因。
2. **不需要传 MIME 类型**，库按字节嗅探容器格式。这一点重要——本地文件来源拿到的 URI 未必带可靠扩展名。
3. **损坏输入抛出具名错误**（`CouldNotDetermineFileTypeError`）而非静默返回空对象，`music-library` spec 要求的「解析失败降级到文件名」因此有明确的捕获点。

Metro 打包验证：在 `src/app` 中引入该库后执行 `expo export -p android`，1767 个模块打包通过，产出 4.3MB Hermes 字节码，**无任何 Node 内置模块缺失报错**。其依赖链中 `Buffer` 仅出现在注释与错误文案里，`globalThis.TextDecoder` / `TextEncoder` 在 `@borewit/text-codec` 中带自实现回退，Hermes 缺少这两个全局也不影响。

**未覆盖的部分**：以上为打包期与 Node 环境下的验证，Hermes 运行时的实际解析行为需随 spike 2.2 一并在真机确认。若真机上出现意外，design.md 原列的方案 3（自实现最小解析器）仍是保底退路，spec 的功能底线（降级到文件名）不受影响。

### spike 2.2：`expo-audio` 的媒体会话能力 —— 源码层已核对，真机验证待补

已通过阅读 `expo-audio` 57.0.3 的 iOS/Android 原生源码确认能力边界，结论已并入重写后的决策 3（含锁屏无「上一曲/下一曲」这一缺口）。**锁屏控制、通知栏控制、耳机按键、来电打断恢复的真机实测尚未进行**，需在具备 iOS 与 Android 真机的环境中补齐。

## Migration Plan

新项目，无迁移与回滚需求。实施顺序上有一处硬约束：**元数据解析的 spike 必须在曲库能力实现之前完成**，因为其结论决定该能力的实现路径。其余部分可按 tasks.md 的顺序推进。

数据库需从第一版起建立迁移机制，后续 change（播放历史、缓存记录、网盘字段）都会增改表结构。

## Open Questions

- **封面图的缓存形式**（文件缓存 vs 随曲目记录存储）：影响存储占用与加载性能，但不改变 spec 中的可观测行为，也不改变任务拆分。可在实现封面提取时依据实际数据体量决定。
- **远程 URL 曲目是否尝试读取远端元数据**：当前 spec 允许降级到 URL 推断的标题。是否发起 Range 请求读取远端文件头以获得完整标签，与 115 网盘的元数据方案是同一问题，留待 C5 一并决策。
