## Why

现有商业音乐 App 存在两个无法接受的问题：核心播放能力被会员墙锁定；曲目会因版权变动在无预警的情况下从曲库中消失，用户对自己已经在听的内容没有任何控制权。

解决办法是把「音源」和「播放器」彻底解耦：播放器本身不提供、不内置、不分发任何音源，只负责播放用户自己拥有或自己指定的资源。用户自行准备音乐（本地文件、可访问的远程地址、个人网盘），播放器保证这些资源可以被稳定地组织、检索和播放。这样既解决了会员墙和曲目消失的问题，也从根本上规避了版权风险。

GitHub 上没有同时满足「跨平台 + 自带曲库管理 + 多来源」的开源方案：现有项目要么只做单一平台，要么是纯粹的聚合搜索器而没有个人曲库的概念。

完整的功能地图与 change 路线图见 `openspec/PRODUCT.md`。本 change 是路线图中的 **C1**，建立工程基座与核心播放能力，并为后续能力提供架构承载。

## What Changes

- 新建 Expo (React Native) 工程，确定并锁定技术栈、工程规范与构建流程
- 引入统一的媒体来源抽象：无论歌曲来自本地文件、远程地址还是未来的网盘/插件，对上层曲库和播放器暴露同一套解析契约
- 实现播放引擎：播放/暂停/上下曲、播放队列、播放模式、后台播放、锁屏与通知栏控制
- 实现本地曲库：曲目索引、持久化、内嵌元数据（ID3/Vorbis/MP4 atom）解析与封面提取
- 实现歌单体系：歌单的增删改、曲目与歌单的多对多归属、歌单内排序、歌单播放
- 实现两个媒体来源：本地文件导入、远程 URL 手动添加
- 实现基础 UI：曲库列表、歌单、播放器页、迷你播放器、播放队列页
- 建立开源仓库的基础设施：许可证、README（含不提供音源的免责声明）、构建与开发环境说明

### 明确的非目标

以下能力已确认要做，但属于后续独立 change，本 change 不实现：

- **离线缓存（C2）**：与核心播放链路正交，且需要独立的缓存策略与存储管理设计。本 change 的来源抽象需保证缓存层可以插入到「解析地址」与「播放」之间而不改动上层。
- **歌词与播放历史（C3）**：均不影响核心数据模型，后加不需要改动既有表结构。
- **曲库备份导出（C4）**：依赖曲库与歌单的数据模型稳定之后再做，否则导出格式会反复变动。
- **115 网盘接入（C5）**：开发者 API 权限审批中（约 5 个工作日），且依赖一项尚未验证的前提（直链是否支持 HTTP Range）。本 change 只在架构上预留来源扩展点。
- **插件音源系统（C6）**：与本 change 的核心能力正交，且在 iOS 上存在上架合规问题需单独评估。本 change 的来源抽象需保证插件可作为一种来源接入而不需要重构上层。

以下能力已确认**不做**，理由见 `openspec/PRODUCT.md - 明确不做`：鸿蒙支持、多设备同步、均衡器、倍速播放、内置音源。

## Capabilities

### New Capabilities

- `media-playback`: 播放引擎能力。音频播放控制、播放队列与播放模式、播放进度与状态、后台播放及系统级媒体控制（锁屏、通知栏、耳机按键）。
- `music-library`: 个人曲库能力。曲目的索引与持久化、元数据解析与存储、曲目的检索与排序、曲库的增删维护。
- `playlist`: 歌单能力。歌单的创建与管理、曲目与歌单的多对多归属、歌单内排序、歌单播放。
- `media-source`: 媒体来源能力。统一的来源解析契约、来源注册与管理、本地文件来源、远程 URL 来源，以及为后续来源（网盘、插件）预留的扩展约束。

### Modified Capabilities

无。这是项目的第一个 change，`openspec/specs/` 下不存在既有 spec。

## Impact

**代码**：全新项目，无既有代码受影响。本 change 将建立整个仓库的目录结构与分层约定，后续所有 change 都在此基础上展开。

**技术栈锁定**（详见 design.md 的决策记录）：
- Expo SDK 57 / React Native 0.86，Development Build 工作流
- `expo-audio` 作为播放引擎（原定 `react-native-track-player`，因其转为商业授权且开源版冻结而在实施阶段改选，见 design.md 决策 3）
- `expo-sqlite` 作为曲库存储
- EAS Build 作为构建方案

**平台范围**：iOS + Android。两端在本 change 的能力上完全一致，平台差异只会出现在插件系统（C6）中。

**分发形态**：应用商店上架 + 代码开源，两条路都走。这对本 change 的直接影响是：仓库从第一次提交起就要具备开源项目的基础设施（许可证、README、免责声明、构建说明），且核心能力不得依赖后续的插件模块——否则 iOS 裁剪插件后将无法交付完整功能。

**外部依赖与风险**：
- 在 React Native 环境中解析音频文件内嵌元数据（ID3v2 等）的可行方案尚未验证——主流的 `music-metadata` 依赖 Node.js 的 Buffer/stream。这是本 change 唯一的技术未知项，需要在实施早期以 spike 形式解决，可能影响曲库能力的实现方式。
- 后续 change 依赖本 change 的来源抽象设计。若该抽象无法容纳网盘与插件两类来源，将导致返工，因此其契约设计需要在 design.md 中明确论证。
