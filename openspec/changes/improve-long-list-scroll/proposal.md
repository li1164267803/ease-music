## Why

`music-library` 要求「曲库中存在数千首曲目，用户快速滚动列表 → 列表保持可用的滚动流畅度，不出现长时间白屏或卡死」。2026-09-14 在 Android 模拟器上用 dev 包验收时：

- **「全部曲目」（4818 首）**：单次快速甩动后，列表区整片空白约 3–4 秒，惯性结束才补出内容
- **1756 首的歌单**：快速上滑时出现连续空白，出现过 700ms 以上的单帧

当时的判定是「无卡死、中速滑动可用」，但快速甩动时的长时间空白不满足 spec 字面。

这组数据有两处明显偏悲观：一是 dev 包（JS 未压缩、带开发期检查），二是模拟器。**问题是否真实存在，要先用 release 包复核**；而且即使存在，原因也可能不止一个，未经测量就动手很可能改错地方。因此本 change 以测量开头，只在测量证实问题存在后，按测量指向的原因实施优化。

## What Changes

- **建立可复现的滚动测量方法**：release 包，固定数据规模（注入测试曲目），固定手势，记录帧统计与列表区空白持续时间，分别在「播放中」与「暂停」两种状态下测量，结果记录在本 change 中。
- **明确验收门槛**：把 spec 里的「长时间白屏」落成可测量的判据（见 design.md 决策 1）。
- **按测量结果实施优化**，候选项已预先列出并排好优先级（见 design.md 决策 3），包括：
  - 列表所在页面不再因播放进度更新而整体重渲染：「是否为当前曲目」改由行自己订阅
  - 稳定列表的渲染属性，避免每次渲染都生成新的分隔组件与渲染函数
  - 封面组件在回收复用的行中正确切换图片
  - 歌单页长列表的窗口化参数，或更换为支持回收的列表实现
- **若 release 包已达标**：不做代码修改，记录测量结果，并据此在验收记录中将「列表流畅度」由有条件通过改为通过。

### 非目标

- **修改 `music-library` spec 的措辞或加入具体数值**：未采纳。帧率与空白时长高度依赖设备，写进 spec 会让同一实现在不同设备上时而合规时而不合规；数值判据放在 design 中作为本 change 的验收门槛。
- **iOS 上的测量**：按 `PRODUCT.md` 既定安排，iOS 验收集中进行；本 change 的测量方法同样适用于 iOS。
- **曲库查询与排序性能（SQLite 侧）**：正交。本轮验收中搜索筛选即时响应，未观察到数据侧瓶颈。
- **播放失败处理、界面问题**：分别由 `fix-playback-failure-handling`、`fix-android-acceptance-ui-issues` 处理。
- **快速滑动中手势被识别为点击**：验收中出现过一次，倾向为模拟器注入手势与主线程卡顿叠加所致，未确认是应用问题；本 change 在测量中顺带观察，确认可复现后再单独处理。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

无。本 change 让实现满足既有的 `music-library`「大曲库下的列表流畅度」，不改变 spec 层面的行为，`.openspec.yaml` 声明 `skip_specs: true`。

## Impact

- **测量**：需要构建 release 包（`android/` 下 Gradle 构建），宿主内存紧张时需先确认环境；测量期间临时注入测试曲目，测完删除。
- **可能涉及的代码**（取决于测量结果）：`src/app/(tabs)/search.tsx`、`src/app/playlist/[id].tsx`、`src/ui/track-row.tsx`、`src/ui/indexed-track-row.tsx`、`src/ui/artwork.tsx`、`src/playback/use-playback.ts`（新增按曲目订阅的选择器）。
- **可能涉及的依赖**：若歌单页需要更换列表实现，可能调整 `react-native-reorderable-list` 的使用方式；不引入需要原生重建的新依赖为优先。
- **不触及**：播放逻辑、数据库结构、来源与插件模块。
