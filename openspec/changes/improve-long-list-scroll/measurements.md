门槛与方法见 `design.md` 决策 1、决策 2。本文件只记录数值与结论。

| 脚本     | `ease-music-acceptance/tools/frames.sh`（帧统计）、`tools/blank.sh`（空白采样）             |

### 手势与采样参数

- **手势**：`input swipe`，距离 1600px，时长 60ms。起点必须落在列表区内且离顶边留余量——「全部曲目」页从 y=500 起手的上滑不被列表接住（20 次仅 42 帧），因此下滑取 2100→500、上滑取 650→2250。
- **帧统计**：每组 `dumpsys gfxinfo reset` 后连续 20 次手势（间隔 0.3s），读 Janky 比例、百分位与直方图中非零的最高桶（「最大帧」，读数为桶下界）。
- **空白采样**：相对 design 决策 2 做了两点改进，判据不变——
  - 甩动与截图放在同一次 `adb shell` 中执行，时间戳记在设备端；截 raw 而非 PNG。实测采样间隔 50–150ms（原 PNG + adb 传输方式首张到次张间隔约 1.5s，达不到 1 秒门槛所需的粒度）。
  - 除整块 YMAX 外，把列表区横切 8 段逐段判定有无内容（`bands=n/8`），并比较相邻两张列表区的像素摘要，相同即记为静止（`still`），用于判定「惯性停止后 500ms 内补齐」。
  - 亮度标定：白色标题 YMAX≈227、占位封面≈137、纯背景≈25，阈值取 100。「全部曲目」裁剪区 `1080:1600:0:520`。
- **宿主防睡眠**：测量期间 `caffeinate -dimsu`。首轮空白采样途中宿主 Mac 进入闲置睡眠 15 分钟（21:03:37–21:18:45，模拟器随之暂停），该轮及睡眠前后的数据全部作废重测。

行距按截图计约 175px；位移按手势前后截图的首行序号估算，误差在 1 行以内，不影响结论。

对照：同一注入方式在「全部曲目」（FlashList）上每次都产生正常甩动（约 2.6s 惯性），40+ 次手势未出现一次误触播放。

初步分析（未验证）：歌单页用 `react-native-reorderable-list` 0.18.1，列表外层是 `GestureDetector` + `Gesture.Simultaneous(Gesture.Native(), Gesture.Pan())`，Pan 未设 `activateAfterLongPress`，按下即参与识别。慢拖也丢失约 550px 位移，说明问题不只在注入手势过短：拖动起始阶段的位移没有交给原生 ScrollView，松手速度随之丢失，因此没有惯性；行上的 `Pressable` 同时可能在手势未被列表接管时收到点击。这与 9-13 dev 包验收记录的「歌单快速上滑时手势被识别为点击」一致。

用户判断（2026-09-15）：认为当前没有实际问题，暂不处理。

## 自动测试（应用内匀速滚动）

方法见 `design.md` 决策 2「实施中的调整」。临时代码 `src/ui/use-scroll-bench.ts` 接入两处列表，release 包重新构建（仍基于 `a8e1482`，仅多出临时测量代码）。脚本 `tools/bench.sh`：

- `frames`：设备端 `logcat -m 1 -e` 等到 `[bench] start` 才重置 `gfxinfo`，`end` 后读取
- `blank`：`start` 后连续截 raw 判空白；汇总行自检实际滚动时长与预期（距离 ÷ 7dp/ms）偏差在 ±20% 内才记为 valid，并给出空白采样点与「到达目标后补齐 8/8」的时刻
- 速度 `speed=1` = 7000dp/s，与 Android 默认最大甩动初速度（8000dp/s）同量级且全程不减速，条件比真实甩动更严
- 首批 6 次 `blank` 采样滚动在第一帧即结束（`reached` 仅比 `start` 晚 17ms，画面全程静止），原因未查明且无法复现，全部作废；此后加入上述自检，所有记录的轮次均为 valid

区域（「全部曲目」行距 65dp）：注入曲目区 0–195000dp（无封面）；尾部真实曲目中，220000dp 附近为占位封面，290000–305000dp 为带远程封面的行（抽样截图确认）。

## 2.5 结论

按 `design.md` 决策 1 的门槛逐条判定。「全部曲目」只采用环境正常时的数据（排除上文标注的宿主内存压力轮次）。

| 门槛                   | 全部曲目 · 暂停                                | 全部曲目 · 播放中                        | 歌单 · 暂停                              | 歌单 · 播放中                   |
| ---------------------- | ---------------------------------------------- | ---------------------------------------- | ---------------------------------------- | ------------------------------- |
| 1a 整片空白 < 1s       | ✓ 最长 < 0.97s（冷启动首次），其余 11 次无空白 | ✓ 环境正常的 7 次均无空白                | ✗ ≥1.2s / ≥2.6s / ≥2.9s                  | ✗ ≥1.5s / ≥2.0s / ≥2.4s         |
| 1b 停止后 500ms 内补齐 | ✓ +7–302ms                                     | ✓ +0–196ms                               | ✗ +1288ms、窗口内未补齐（另一次 +185ms） | ✗ +835ms、+1203ms、窗口内未补齐 |
| 2a Janky ≤ 10%         | ✓ 手势 0.18% / 0.00%；自动 4.07% / 2.32%       | ✓ 手势 0.75% / 0.35%；自动 0.85% / 0.23% | ✗ 57.59% / 60.00%                        | ✗ 49.79% / 63.45%               |
| 2b 无 > 700ms 单帧     | ✓ 最大 150ms 桶                                | ✓ 最大 85ms 桶                           | ✗ 850ms 桶 ×2、≥4950ms 桶 ×4             | ✗ 1100ms 桶、950ms 桶 ×2        |

**结论：不达标。**

- **「全部曲目」达标**：暂停与播放中两种状态、手势与自动滚动两种驱动方式下均满足全部门槛。
- **歌单页不达标**：暂停与播放中两种状态下四条门槛全部不满足，超标幅度为门槛的数倍；JS FPS 平均 2.8–9.9，列表位置远落后于滚动目标。暂停与播放中量级相同，说明瓶颈不在播放快照的发布。

测量中的其他观察：

- **封面错位**：抽样截图（远程封面区滚动途中与静止后）未见封面错位或旧图残留；个别行封面图片仍在加载（显示为空的封面位），行本身已渲染。
- **滑动被识别为点击**：在歌单页可复现——`adb input swipe` 注入的 5 组手势中 3 组误触播放（第 31 首「黑白」、第 3 首「冷冰冰」、第 15 首「The Gentlemen」），且注入手势在该页丢失约 550px 位移、不产生惯性；「全部曲目」页 100+ 次注入手势未出现。是否影响真实手指操作未验证（用户手测判断无明显问题）。常态改用 FlashList 后这一现象预计随之消失（手势冲突来自可拖动列表外层的 `GestureDetector`）。

### 4.5 评估：常态 FlashList、排序模式切换为可拖动列表

**依据**：「全部曲目」与歌单行的渲染内容量级相当（封面 / 序号 + 两行文本 + 下载按钮 + 更多），前者用 FlashList（回收行）在 7000dp/s 下 JS FPS 59；后者用 `react-native-reorderable-list`（基于 `FlatList`，不回收行，且每个 cell 由 `renderAnimatedCell` 包一层 reanimated 动画视图并挂手势），固定行高后 JS FPS 仍只有 8–10。瓶颈在列表实现的「逐行挂载 + 每行动画包装」，不在行组件或播放订阅，窗口化参数调小反而更差也印证了这一点。

**方案**：

- 常态：歌单页用 FlashList 渲染 `IndexedTrackRow`（与「全部曲目」同一列表实现），点击播放、「更多」、下载按钮行为不变
- 排序：进入排序模式后才渲染 `ReorderableList`，拖动、`onReorder` 即刻持久化、`pendingOrder` 叠加逻辑原样保留；退出排序模式切回 FlashList
- `playlist` spec「歌单内排序」只要求「用户在歌单内将一首曲目拖动到新位置 → 立即更新、重启后保持」，未规定入口，排序模式仍满足

**代价与风险**：

- 交互变化：现在长按任一行即可直接拖动；改后需先进入排序模式。入口需用户确认（见下）
- 排序模式下仍是 `FlatList`，数千行时快速滚动依旧卡顿；排序本身以慢速拖动为主，可接受
- 不引入新依赖、不需原生重建；两套列表共用行组件与 `getItemLayout` 之外的逻辑

**用户确认（2026-09-15）**：实施，入口为右上角「…」菜单中的「调整顺序」。结果见文末「最终方案与验证」。

## 最终方案与验证

### 实施（用户确认）

- **4.5 常态 FlashList + 排序模式**：歌单页常态用 FlashList 渲染 `IndexedTrackRow`；「…」菜单新增「调整顺序」，进入后才渲染 `ReorderableList`（页头显示「完成」、提示「长按曲目，拖动到新的位置」），`onReorder` 即刻持久化与 `pendingOrder` 叠加逻辑不变。
- **撤回**：`IndexedTrackRow` 固定行高与 `getItemLayout`（缺行问题与行高无关，排序模式以慢速拖动为主，不再需要）；`windowSize=5` 试验；全部临时测量代码。
- **升级 `@shopify/flash-list` 2.0.2 → 2.3.2**（纯 JS，无需原生重建），修复下述缺行问题。

### 顶部缺行：FlashList 2.0.2 的 `firstItemOffset` 计算错误

改为 FlashList 后，歌单页向上滑动停止时列表顶部 1–2 行不渲染（用户真机手势复现并截图）。临时打印 FlashList 自身状态得到 `firstItemOffset=-317.33`，而正常应为 0：

- 2.0.2 以 `measureLayout(view, view)` 测列表自身位置，在当前 React Native 上返回的是列表相对父容器的位置（歌单页列表顶边 833px ÷ 2.625 = 317.3dp），再用「首项位置 − 该值」得到 `firstItemOffset`
- 可见范围按「滚动位置 − firstItemOffset」计算，视口被当成下移 317dp；默认预绘制距离 250dp 补不上差值，顶部约 67dp（一行）不渲染
- 「全部曲目」列表顶边在 188dp，小于预绘制距离而被掩盖，属同一隐患
- 2.3.2 已改为直接取首项相对外层容器的位置（`firstItemOffset = firstChildViewLayout.y`）

排除过程中试过关闭 `maintainVisibleContentPosition`、恢复自然行高，均无效，已撤回。
