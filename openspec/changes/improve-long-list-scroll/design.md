## Context

动机与范围见 `proposal.md`。行为要求是既有的 `music-library`「大曲库下的列表流畅度」，本 change 不改 spec。

两处长列表的现状：

- **「全部曲目」**（`src/app/(tabs)/search.tsx`）：`@shopify/flash-list` 2.0.2。页面组件调用 `usePlayback()` 订阅整个播放快照，只为计算每行的 `active`；`renderItem` 与 `ItemSeparatorComponent` 都是每次渲染新建的内联函数。播放中快照每 500ms 发布一次，页面随之整体重渲染。
- **歌单详情**（`src/app/playlist/[id].tsx`）：`react-native-reorderable-list` ~0.18.1，底层是不回收行的 `FlatList`（基于 reanimated 实现拖动排序）；同样在页面层订阅播放快照计算 `active`，`renderItem` 内联。
- **行组件**：`TrackRow`（封面 50 + 两行文本 + `DownloadButton` + 更多）与 `IndexedTrackRow`（序号 + 两行文本 + 时长 + `DownloadButton` + 更多）。`DownloadButton` 每行各自订阅缓存状态；`Artwork` 用 expo-image，未设置 `recyclingKey`。

2026-09-14 的 dev 包数据（模拟器 Medium Phone API 36，`-memory 3072`）：

| 列表             | 手势          | 帧统计（不录屏、不截图）                                | 空白                            |
| ---------------- | ------------- | ------------------------------------------------------- | ------------------------------- |
| 全部曲目 4818 首 | 20 次快速下滑 | 482 帧，Janky 6.02%，p50/p90/p95/p99 = 20/32/38/121ms   | 单次快速甩动后约 3–4 秒整片空白 |
| 歌单 1756 首     | 20 次快速上滑 | 318 帧，Janky 12.58%，p50/p90/p95/p99 = 23/48/133/700ms | 截图采样时多段连续空白          |

测量当时处于暂停状态，播放中的情况未测。

**与 `fix-playback-failure-handling` 的顺序**：该 change 会给播放快照增加字段、调整发布时机，直接影响「页面订阅播放快照」这条路径的开销。本 change 的测量与优化应在其实施之后进行，否则测到的是即将被改掉的代码。

## Goals / Non-Goals

**Goals:**

- 先证实或证伪问题，再决定改什么；每一项优化都能指向一条测量数据
- 测量方法可复现，后续 iOS 验收与回归可以直接沿用

**Non-Goals:**

- 不追求模拟器上的满帧，门槛以「不出现长时间空白、滑动可用」为准
- 不为了测量引入常驻的性能埋点代码

## Decisions

### 决策 1：验收门槛

**选择**：在同一台模拟器上，以 release 包测量，两处列表都满足以下全部条件视为达标：

1. **单次快速甩动**（`input swipe` 1600px / 60ms）后，列表区「整片空白」的持续时间小于 1 秒，惯性停止后 500ms 内可见区域完整补齐
2. **连续 20 次快速滑动**（上下两个方向各测一次）期间，Janky 帧比例不超过 10%，且没有超过 700ms 的单帧
3. 上述两条在「暂停」与「播放中」两种状态下都成立

**理由**：spec 的「长时间白屏」需要一个可以判定的数值，否则无法判断改动是否有效、何时可以停止优化。1 秒是用户明显感知到「内容没了」的量级；700ms 是 dev 包实测的最坏帧，release 包不应更差。门槛只用于本 change 的验收，不写入 spec（理由见 proposal 非目标）。

**备选方案与未采纳的理由**：

- **以帧率（如平均 55 fps）为门槛**：未采纳。FlashList 的空白发生在 JS 线程来不及渲染新行时，UI 线程帧率可以很好看而列表区仍是空白；dev 包实测 Janky 仅 6% 却有 3–4 秒空白，正是这种情况。
- **以真机为准，不在模拟器上设门槛**：未采纳。项目当前的验收环境就是这台模拟器；模拟器偏悲观，在它上面达标，真机只会更好。真机复核作为补充记录。

### 决策 2：测量方法——release 包、不录屏、截图采样判空白

**选择**：

- **构建**：release 变体，JS 包内置，不连 Metro
- **数据**：沿用验收时的注入方式，向曲库注入 3000 首 `source_key` 带 `acc-bulk-` 前缀的测试曲目，测完删除
- **帧统计**：每组手势前 `dumpsys gfxinfo <package> reset`，结束后读取 Janky 比例与各百分位
- **空白判定**：手势结束后连续 `screencap`，裁出列表区域，用 ffmpeg `signalstats` 取亮度最大值；列表行含白色文字，整片空白时最大值接近背景色。连续判为空白的采样跨度即空白持续时间
- **不录屏**：`screenrecord` 本身会显著拖慢模拟器（验收中录屏时帧数降到约 13 fps），数据不可用
- **记录**：每轮测量的原始数值写入本 change 目录下的 `measurements.md`，注明代码版本、播放状态、手势参数

**理由**：这是验收中已经跑通、且证明能区分「有内容 / 空白」的方法，只把 dev 包换成 release 包、补上播放中的一组。截图采样本身有开销（每次约 0.6 秒），因此帧统计与空白判定分两轮进行，互不干扰。

**备选方案与未采纳的理由**：

- **在应用内用 FlashList 2 自带的 `useBenchmark` / `useFlatListBenchmark` 自动滚动并统计**：未采纳为主要方法。需要临时改代码并单独构建，自动滚动的速度曲线也与用户手势不同；截图法不改代码、对两种列表一视同仁。可作为定位原因时的辅助手段。
- **用 Perfetto / Android Studio Profiler 抓完整轨迹**：未采纳为验收方法。适合定位原因，但每次操作成本高，不适合作为可重复的通过判据；在决策 3 的定位阶段按需使用。

**实施中的调整（2026-09-15）**：`adb shell input swipe` 在歌单页（`react-native-reorderable-list`）上不产生甩动——列表只移动数行、无惯性，且 5 组中 3 组误触播放，数据无效（详见 `measurements.md` 2.3）。经用户确认，滚动的驱动方式改为「应用内自动滚动」：临时加入 `useScrollBench`，由 deep link 参数触发 FlashList 导出的 `autoScroll`（匀速 7dp/ms × 倍率，`scrollToOffset` 逐帧定位），两处列表一视同仁。判定口径不变——帧统计仍读 `gfxinfo`，空白仍用设备端截图采样；手势定义相应改为：

- 「连续 20 次快速滑动」→ 一次往返匀速滚动（上下两个方向各覆盖一次）
- 「单次快速甩动」→ 一段匀速滚动，空白从滚动开始计，「惯性停止」对应滚动到达目标

FlashList 2.x 的 `useBenchmark` 本身只报 JS FPS、不统计空白面积，因此只借用它的自动滚动与 JS FPS，不以其输出作判据。临时代码测完即删，不提交（Non-Goals：不引入常驻性能埋点）。

### 决策 3：优化候选与优先级——每项都要有测量依据才实施

**选择**：release 包不达标时，按以下顺序定位与实施；每实施一项重测一轮，达标即停止，不预先全做：

1. **页面不再订阅整个播放快照**。新增按曲目订阅的选择器（例如 `useIsCurrentTrack(trackId)`，基于 `useSyncExternalStore` 只在「是否为当前曲目」变化时触发），`active` 由行组件自己取。依据：「播放中」一组明显差于「暂停」一组。
2. **稳定列表的渲染属性**。分隔组件提升到模块级，`renderItem` 用 `useCallback` 并只依赖真正变化的数据。依据：滚动期间行组件在数据未变时仍被重渲染（React Profiler 可见）。
3. **封面在回收行中正确切换**。`Artwork` 为 expo-image 设置 `recyclingKey`（取图片地址），回收复用时不先显示旧图再切换。依据：快速滚动时出现封面错位或闪烁；它同时是正确性修正。
4. **行组件渲染开销**。依据 Profiler 中单行耗时，考虑把 `DownloadButton` 的状态订阅与图标渲染拆开、减少每行 `Pressable` 层级等。
5. **歌单页列表实现**。`FlatList` 不回收行，数千行时内存与首次布局都随行数增长。先尝试固定行高下的 `getItemLayout` 与窗口化参数；仍不达标时，评估「常态用 FlashList 渲染、进入排序模式时才切换到可拖动列表」。依据：歌单页在 1 与 2 实施后仍明显差于「全部曲目」。
6. **FlashList 的预绘制距离**（`drawDistance`）。最后手段：加大预绘制会增加每帧工作量，可能改善空白也可能加重卡顿，只在前几项之后仍有边缘性空白时试验。

**理由**：列表空白的直接原因是「新进入视口的行来不及渲染出来」，而来不及的原因可能是 JS 线程被无关工作占用（1、2）、单行太重（4）、列表实现本身不回收（5）。这些原因在测量前无法区分，按「成本低、收益面广、兼顾正确性」的顺序逐项验证，避免一次改动多处后说不清是哪一项起了作用。

第 1 项同时符合项目「子组件能自己取的数据不经 props 传入」的约定：是否为当前曲目只有行自己关心。

**实施结果（2026-09-15）**：release 包测得「全部曲目」已达标、歌单页四条门槛全部不满足，且暂停与播放中量级相同。经用户确认，第 1、2、5 项合并实施，不逐项归因；第 5 项中固定行高与 `getItemLayout` 仅把歌单 Janky 从约 55% 降到约 33%，窗口化参数调小反而更差，最终采用「常态 FlashList、排序模式（「…」菜单「调整顺序」）切换为可拖动列表」。第 3、4、6 项未实施（已达标）。

实施中另发现 `@shopify/flash-list` 2.0.2 的 `firstItemOffset` 计算错误：列表距父容器顶边超过默认预绘制距离（250dp）时，向上滑动停止后顶部约一行不渲染；2.3.2 已修复，经用户确认升级（纯 JS，无原生重建）。数据与排查过程见 `measurements.md`。

**备选方案与未采纳的理由**：

- **直接更换为其他高性能列表库（如 LegendList）**：未采纳为起点。在不知道瓶颈的情况下换库，可能搬走了问题也可能没有，还带来迁移成本与新的行为差异；只有当测量表明 FlashList 本身是瓶颈时才考虑。
- **一次性做完全部候选项**：未采纳。部分候选项有副作用（如第 6 项），在无测量依据时实施可能让结果变差，而且无法归因。

### 决策 4：release 包已达标时的处理

**选择**：不做代码修改；在 `measurements.md` 记录 release 包的测量结果，并把 `bootstrap-music-player` tasks.md 末尾问题清单中的「快速甩动时列表长时间空白」更新为「release 包复核达标，dev 包现象不代表发布版本」，本 change 以测量结论归档。决策 3 的第 3 项（`recyclingKey`）属于正确性修正，若测量中观察到封面错位，仍单独实施。

**理由**：本 change 的目标是满足 spec，不是追求更高的数值。已经达标还去优化，改动没有验收依据。

**备选方案与未采纳的理由**：

- **无论是否达标都实施第 1、2 项**：未采纳。它们在工程上合理，但本 change 以测量驱动为原则；如确有必要，可在后续 change 中以代码质量为理由单独提出。

## Risks / Trade-offs

- [宿主 Mac 内存紧张，Gradle release 构建与模拟器同时运行可能触发交换或被系统杀进程] → 构建前检查 `vm.swapusage`，必要时先关闭模拟器构建、再启动模拟器安装；出现内存不足时停下报告，不反复重试。
- [release 包不可调试，验收脚本依赖的 `run-as` 读写数据库在 release 包上不可用] → `android/app/build.gradle` 的 release 与 debug 使用同一个签名，可以覆盖安装并保留应用数据：先在 dev client 上注入测试曲目，再 `adb install -r` 覆盖为 release 包测量，测完覆盖回 dev client 删除注入数据。每次覆盖前用既有脚本备份 `files/SQLite`。
- [截图采样的间隔约 0.6 秒，无法精确测出小于该间隔的空白] → 门槛设为 1 秒，高于采样粒度；需要更细粒度时临时接入 FlashList 的 `useBenchmark` 辅助定位。
- [模拟器结果与真机差异大] → 门槛以模拟器为准（偏悲观）；有真机时补一轮测量写入 `measurements.md`。

## Migration Plan

测量阶段不改应用代码。若实施优化，均为前端修改，无数据迁移，随普通 JS 包更新发布；回滚即回退代码。测量用的注入数据在每轮结束时删除。
