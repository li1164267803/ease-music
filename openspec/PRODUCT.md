# 产品全景

跨平台个人音乐播放器。本文档是功能地图与 change 路线图的唯一落点，具体行为契约见各 change 的 `specs/`。

## 项目标识

| 项               | 值                                            |
| ---------------- | --------------------------------------------- |
| 中文名           | 自在音乐                                      |
| 英文显示名       | EaseMusic（固定连写，不单独使用 Ease）        |
| GitHub 仓库      | `ease-music`                                  |
| 应用商店显示名   | 自在音乐 - 无广告本地播放器                   |
| 包名 / Bundle ID | `com.easemusic.app`（Android 与 iOS 一致）    |
| Slogan           | 你的歌，你说了算。/ Your library, your rules. |
| 品牌色           | 荧光青柠 `#C8FF4D`，深色界面 + 青柠强调       |

**命名立意**：「自在」修饰的是用户状态，不是音乐风格。产品不干预内容——不提供音源，用户放什么都照放；它改善的是用户处境：不必买会员、不被广告打断、不被算法安排，这三件事合起来就是自在。英文取 _at ease_（自在、不拘束）之意，刻意避开 _easy listening_（轻音乐体裁），与中文侧避开体裁词「轻松」的取舍对称。名字不含任何提供音源的暗示——与产品定位一致。

**已知命名风险**（决策时已接受，非遗漏）：

- 「自在」带禅意，单看名字存在被误认为冥想 / 助眠类应用的风险。缓解手段：商店副标题固定带「本地播放器」，视觉上避免圆润禅系造型，以荧光青柠 + 利落几何强化工具属性
- 英文 `Ease` 词根搜索噪音中等（EaseUS 等同词根软件品牌）。英文侧搜索排名不强求，任何场合固定连写 `EaseMusic`，不单独使用 `Ease`
- 中文「自在音乐」在国内应用市场音乐类未见占用（检索日 2026-08-08），且天然含「音乐」二字，可吃到商店泛搜召回
- 商标状态需在上架前自行检索（中国商标网第 9 类与第 41 类、USPTO），本文档的重名结论不构成法律意见

**已评估并排除的命名**（记录取舍依据，避免重复讨论）：

- **琥珀音乐 / AmberMusic**：琥珀金 `#FFBF00` 与国内音乐应用的「会员色」（黄钻、黑胶 VIP）观感接近，与反会员墙的定位相悖；且 `ambermusic.com` 已被占用、GNOME **Amberol** 存在听觉混淆
- **青柠音乐**：与灰产免费听歌应用「青听音乐」「柠乐音乐」字面高度重叠，易被误认为提供音源，与产品定位正面冲突
- **净听音乐 / 聆听类**：「X 听」词根已被「免费听全网」类应用占满，同上风险
- **轻松音乐**：与音乐体裁词 _easy listening_ 撞义，会把适用范围窄化为轻音乐；且属对商品特点的直接描述，商标显著性不足
- **夜光音乐 / GlowTape**：中文侧干净，但英文仓库名 `glowtape` 与 GitHub 既有项目冲突

## 产品定位

**播放器不提供音源，只播放用户自己拥有或自己指定的资源。**

解决两个问题：核心播放能力被会员墙锁定；曲目因版权变动无预警消失。用户自行准备音乐，播放器保证这些资源能被稳定地组织、检索和播放。这一定位同时规避了版权风险——应用本身不内置、不分发任何音源。

**分发形态**：应用商店上架 + 代码开源，两条路都走。这带来一条硬约束：插件音源系统在 iOS 上无法合规上架，因此它必须是编译期可裁剪的模块，且核心能力不得依赖它。

## Change 路线图

|         | Change                     | 内容                                                                                                              | 状态                                         |
| ------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **C1**  | `bootstrap-music-player`   | 工程基座 · 来源抽象 · 本地文件与远程 URL · 播放引擎 · 曲库 · 歌单 · 基础 UI                                       | 已归档，两端真机验收未跑完                   |
| **C2**  | `add-offline-cache`        | 用户手动下载曲目到本地；无网络、来源失效或插件被卸载时照常播放。不做自动缓存，不自动淘汰                          | 已归档，Android 主流程已验；iOS 侧验收未跑   |
| **C3**  | `add-playback-history`     | 播放历史：曲目开始播放即记一次，每首只留最近一次并计次数，保留最近 200 首；发现页「最近播放」，支持移除单条与清空 | 已归档，Android 验收全部通过；iOS 侧验收未跑 |
| **C3b** | 歌词显示                   | 本地 `.lrc` 与内嵌歌词显示                                                                                        | 待启动                                       |
| **C4**  | 曲库备份                   | 曲库导出为文件、再导入合并                                                                                        | 待启动                                       |
| **C5**  | 115 网盘接入               | OAuth 鉴权 · 目录浏览 · 音乐刮削 · 流式播放                                                                       | 阻塞：开发者 API 权限审批中                  |
| **C6a** | `add-plugin-source-system` | 插件宿主 · 安装与生命周期管理 · 搜索与入库 · 播放地址解析 · iOS 编译期裁剪。仅 Android                            | 已归档，Android 全链路已跑通；iOS 侧验收未跑 |
| **C6b** | 插件发现层                 | 榜单 · 专辑 · 艺人 · 推荐歌单 · 外部歌单导入。复用 C6a 的地基，只加界面                                           | 待启动                                       |

**排序理由**：C2 排在歌词之前，因为离线缓存直接对应「歌会消失」这个原始痛点——缓存下来的曲目才真正属于用户。C5 的时间取决于 115 开发者权限审批，权限下来后可插队。C6 独立性最强，任何时候都可以做。

> **拆分说明**：C3 此前写作「歌词与播放历史」，**该捆绑作废**。两者不共享数据、不共享界面、也不共享技术风险（歌词的难点在 `.lrc` 的编码与时间轴方言），捆在一个 change 里只会让论证分裂成互不相干的两段。已拆为 C3（播放历史，已实现）与 C3b（歌词，待启动）。

### 验收策略：先做完 Android，iOS 全量验收一次

**当前阶段只在 Android 上开发与验收。iOS 侧的真机验收不逐个 change 跑，而是等 Android 功能全部开发完成后，集中做一次全量验收。**

因此上表中「iOS 侧验收未跑」不是遗漏，是既定安排——单个 change 归档时 iOS 验收为空属于预期状态，不构成阻塞。

这么排的原因：iOS 验收要接一整套单独的成本（Mac + Xcode、真机或模拟器、EAS 构建、签名），每个 change 各跑一遍是重复付出；而两端共用同一套 TypeScript 实现，差异集中在少数几处平台行为上，攒到一起一次跑完更划算。

代价也要认：**平台差异会被推迟发现**，且发现时离写下那段代码已经很久。因此实施阶段遇到已知的平台差异必须当场写进 design 的 Risks，并在 tasks 的验收项里标出「iOS 待复验」，不能靠事后回忆。已经记在案的两处：

- **C2 决策 3**：Android 下载失败会把已写入的部分留在目标位置，iOS 不会。`.partial` → move → 写库这个顺序就是为它设计的，Android 已验，iOS 未验
- **C6a 决策 6**：插件模块在 iOS 上编译期裁剪。`pnpm check:ios-strip` 能在产物层面验证裁剪生效（这一条不需要真机，已在跑），但裁剪后的完整走查仍属 iOS 验收

> **措辞更正**：C6 此前描述为「自主实现的 JS 沙箱」，**该表述作废**。插件与应用代码运行在同一个 JS 上下文中，能力等同于应用自身代码，方案不提供任何隔离机制——参考实现（MusicFree）同样没有。正确的说法是「插件宿主」。真实的限制只有两条：插件是纯 JS，且只能取到宿主注入的固定几个依赖。理由见 `changes/add-plugin-source-system/design.md` 决策 1。

## 明确不做

| 不做                      | 原因                                                                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **鸿蒙 (HarmonyOS NEXT)** | 已排除出产品范围。此前为其考虑的约束（原生库需 `@react-native-oh-tpl` 适配、避免 Expo 运行时、KV 存储需抽象）全部作废 |
| **多设备同步**            | 需自建服务端或依赖网盘/WebDAV，复杂度显著高于其他项。曲库备份导出（C4）覆盖了「换设备不丢数据」这一核心诉求           |
| **均衡器 / 音效**         | 需要原生音频处理能力，成本明显高于收益                                                                                |
| **倍速播放**              | 播客/有声书场景常用，纯音乐场景用得少                                                                                 |
| **内置任何音源**          | 产品定位的根基，不可动摇。这是规避版权风险的前提                                                                      |
| **在线元数据补全**        | 依赖插件系统（C6）或独立元数据源，届时再评估                                                                          |
