# 分层约定

本文件是 `bootstrap-music-player` 变更中 design.md 所确立分层的落地约定。**任何新增代码都必须能被归入下列某一层，且不得反向依赖。**

## 依赖方向

```
UI 层        src/ui, src/app
  ↓
能力层       src/playback（播放）   src/library（曲库导入 / 元数据 / 封面）
             src/cache/{download,queue}（下载执行与排队）
             src/lyrics（歌词：四处来源的查找、缓存、播放页歌词区）
  ↓
来源层       src/sources
  ↓
领域层       src/domain
             src/cache/{repository,files,store}（缓存记录、文件、内存状态）
             src/history（播放历史：记录与广播）
```

`src/plugins`（仅 Android）不属于这四层，它是跨层的独立模块，见文末。

上层可以依赖下层，**下层不得依赖上层**。同层之间的横向依赖需要有明确理由。

## 各层职责

### 领域层 `src/domain`

曲目、歌单、播放模式等领域模型与其持久化。这一层**不知道曲目来自哪里**，也不知道音频如何被播放。

- `model/` — 领域类型定义
- `db/` — SQLite 连接与迁移
- `repository/` — 曲库、歌单的仓储
- `settings.ts` — 轻量 KV 配置

### 来源层 `src/sources`

把「用户拥有的东西」转换成「可播放的地址」。每个来源实现同一套解析契约（可播放地址 + HTTP 请求头 + User-Agent），并在注册表中注册自己的来源标识。

- `contract.ts` — 解析契约类型与 `MediaSource` 接口
- `registry.ts` — 来源注册表
- `resolve.ts` — **唯一解析入口**，离线缓存在此处拦截
- `local-file/`、`remote-url/` — 具体来源实现

**约束**：**播放层不得感知具体来源**，只能通过 `resolve.ts` 取地址、`contract.ts` 取类型。此约束由 `eslint.config.js` 中一条仅作用于 `src/playback/**` 的 `no-restricted-imports` 规则机器化执行。

约束只落在播放层，不落在导入流程与 UI：导入本来就是来源特有的动作（本地文件要开系统文件选择器、远程地址要校验 URL），把它们一并禁掉只会逼出绕过规则的写法。media-source spec 要求来源无关的是**播放**——它只能拿到「地址 + 请求头 + UA」这一个形状。

### 播放层 `src/playback`

播放引擎的封装：播放控制、播放队列、播放模式、系统媒体会话、播放状态对外暴露。这一层通过来源层的解析入口拿地址，**不感知曲目来源类型**。

### 曲库能力 `src/library`

与播放层同级的另一个能力模块：元数据解析、封面提取与缓存、曲目导入流程的编排。它同时依赖领域层与来源层，但不被播放层依赖。

### 离线缓存 `src/cache`

**这个模块横跨两层，是全仓库唯一这样的常规模块，原因很具体**：来源层的解析入口要在播放前查一次缓存，而下载又必须调用来源去取真实地址。若把整个模块放在来源层之上，`resolve.ts → cache` 这条边就成了下层依赖上层；若整个放在来源层之下，下载器就拿不到 `getSource`。因此按「谁认识来源」切开：

| 文件                                      | 认识来源？             | 所在层   |
| ----------------------------------------- | ---------------------- | -------- |
| `repository.ts` 缓存记录的读写            | 否                     | 领域层侧 |
| `files.ts` 缓存目录、落盘位置、扩展名推断 | 否                     | 领域层侧 |
| `store.ts` 内存状态、订阅、缓存命中判定   | 否                     | 领域层侧 |
| `download.ts` 单曲下载执行                | **是**                 | 能力层   |
| `queue.ts` 串行队列、批量结果             | 是（经 `download.ts`） | 能力层   |

`store.ts` **刻意不引用 `src/sources`**——这是让分层保持无环的那一条约束，改动时首先要守住它。

**拦截点**：`src/sources/resolve.ts` 在取来源之前先查缓存。命中就直接返回本地文件地址，连 `getSource` 都不走——插件被卸载后已下载的曲目照常播放，靠的正是这个先后顺序。

**三种不一致，各自的发现与纠正方式**。文件系统与 SQLite 之间没有共同的事务（SQLite 事务回滚不了文件操作），因此不追求「不出现不一致」，而是把落盘顺序设计成「唯一可能的不一致是无害的那一种」，再对每个方向各做一次廉价清理：

| 不一致          | 何时发现                                           | 怎么纠正                                             |
| --------------- | -------------------------------------------------- | ---------------------------------------------------- |
| 记录有、文件无  | 播放解析时（`store.ts` 的 `resolveCachedFileUri`） | 删记录、状态改回未下载，回退到来源解析。用户无感     |
| 文件有、记录无  | 应用启动（`initTrackCache`）                       | 按记录集合删掉孤儿文件，形态同 `pruneArtwork`        |
| `.partial` 残留 | 应用启动（`initTrackCache`）                       | 整个目录清空——能在那里的文件一定属于某次没跑完的下载 |

「记录说有、文件却没有」之所以不可怕，是因为落盘顺序是**文件先就位、记录后写**；反过来才会造出播放时才暴露的失败。

### 播放历史 `src/history`

与 `src/cache` 属于同一类东西：**曲目的外部事实**。它们都描述「这首曲目怎么了」而不是「这首曲目是什么」，因此都独立成表、以 `track_id` 为主键、外键 `ON DELETE CASCADE`，而不是给 `tracks` 加列。

不加列的理由在历史这里比缓存更硬：曲库刷新是全局广播，历史每切一首歌就变一次，若「最后播放时间」写在曲目行上，用户连听十首就会触发十次全库重查。

- `repository.ts` — 记一次播放（UPSERT + 裁剪到上限）、按最后播放时间倒序查询、清空。只依赖领域层
- `store.ts` — 变更广播与订阅 Hook

**`store.ts` 刻意不引用 `@/library/store`**。播放层要在记录成功后发这个广播，而分层约定里曲库能力不被播放层依赖；若历史的广播挂在曲库广播上，这条依赖就绕回来了。三个会改动历史的入口（记一次播放、清空、移除曲目）各自发一次窄播，界面只订阅这一个信号——**不要图省事改用 `notifyLibraryChanged`**，那等于把上面刚拒绝掉的全库重查从广播这一侧放回来。

记录点是 `src/playback/player.ts` 的 `load()`：所有播放路径的必经之处，因此一次播放只会记一笔。记录以「发射后不管」的方式调用且就地吞掉异常——写库失败绝不能冒泡到 `load()` 的 catch，那里会跳曲、累加连续失败计数、甚至把曲目标记为失效，等于让一次写库失败被表达成「这首歌播不了」。

### 歌词 `src/lyrics`

与 `src/cache`、`src/history` 属于同一类东西：**曲目的外部事实**——「这首曲目的词是什么」而不是「这首曲目是什么」。因此同样独立成表（`track_lyrics`）、以 `track_id` 为主键、外键 `ON DELETE CASCADE`。

它整体落在**能力层**，而不像缓存那样劈成两半：歌词不参与播放解析，没有任何下层需要回头查它。

- `lrc.ts` — `.lrc` 解析与生成，纯字符串处理，不引依赖
- `directory.ts` — 歌词目录：按**曲目标题**匹配 `.lrc`，只认 UTF-8，非 UTF-8 明确报告而不是显示乱码
- `sources.ts` — 四处来源的统一取法，优先级固定为 **歌词目录 > 内嵌 > 来源插件 > 歌词类插件**：越是用户主动准备的越优先；来源插件拿到的是精确曲目，排在按标题模糊匹配的歌词类插件之前。任一处失败只进日志，换下一处找
- `repository.ts` / `store.ts` — 缓存与订阅。读取路径只有一条：缓存命中即刻返回，未命中才去四处找，找到写回。只缓存**找到了**的歌词——「没找到」不落库，否则用户装上歌词插件后旧曲目永远不会再找
- `ui/lyrics-card.tsx` — 播放页歌词区

**播放层不参与**。歌词组件自己订阅 `usePlayback()` 拿当前位置、自己算当前行；播放层没有任何理由知道歌词的存在，反向依赖只会让所有播放状态的订阅者为一个界面细节付出重渲染。

**与插件的边界**：歌词模块只经 `@/plugins` 门面调用插件（`lyricForTrack` 与 `searchLyric` 两个方法），不引用任何插件实现模块——iOS 上门面为空实现，插件那两路自然为空，不需要平台分支。歌词类插件的筛选在门面之内（`supportedSearchType` 显式含 `lyric`），歌词模块不知道插件长什么样。

### UI 层 `src/ui` / `src/app`

`src/app` 是 expo-router 的路由文件，保持极薄，只做布局与组合。真正的界面组件、主题与交互放在 `src/ui`。

## 为什么这样分

- **来源可扩展**：新增网盘（C5）来源时，只在 `src/sources` 下加一个目录并注册，其余各层不动。
- **缓存可插入**：离线缓存（C2）在 `src/sources/resolve.ts` 这个唯一入口处拦截，播放层与各来源实现一行未改。
- **插件可裁剪**：见下。

## 插件模块 `src/plugins`（仅 Android）

插件不在上面四层里，它是**跨层的独立模块**：自带宿主运行时、自己的持久化、自己的界面，并把自己注册进来源层。

注册方向是**插件推向注册表**（`registerSource` / `unregisterSource`），而不是注册表去拉插件——因此 `src/sources` 完全不知道插件的存在。这与 C5 网盘不同：网盘是内置来源，编译期就在数组里；插件的数量与标识运行时才确定，**一个插件即一个来源**。

与其余代码之间只有一条通路：

```
其余各层  ──►  src/plugins/index.ts        （门面，全空实现）
              src/plugins/screens/*.tsx    （屏幕，全空实现）
                        ▲
                        │ 同名 .android 文件在 Android 上顶替
                        │
              src/plugins/index.android.ts ──► host / manager / source / ui …
```

这条分界线就是 iOS 裁剪的全部机制：打包器按静态 `import` 关系收集模块，与代码是否可达无关，所以只有让 iOS 侧**根本不存在**那条 import，插件宿主与 `cheerio` 等专属依赖才不会进入产物；运行时判断 `Platform.OS` 做不到这一点。

三道守卫，缺一不可：

1. ESLint 禁止 `src/plugins` 之外的代码引用插件实现模块与插件专属依赖
2. `pnpm check:constraints` 在引用层面复查核心路径
3. `pnpm check:ios-strip` 导出真实 iOS 产物，断言模块清单里确实没有它们——**前两条都只看源码，只有这一条能证明裁剪真的生效**

### 候选曲目的两条来路：搜索与发现

插件曲目进入曲库只有一条路径——先以**候选曲目**（`src/domain/model/candidate-track.ts`）呈现，用户逐首「加入曲库」后才成为曲目记录，入库后与本地文件曲目同权。候选曲目有两条来路，共用同一套地基：

| 来路                    | 模块                       | 协议方法                                                                                                       | 形状差异                                                                                                                                             |
| ----------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 搜索                    | `src/plugins/search.ts`    | `search`                                                                                                       | 曲目在 `data`；跨插件并发，`continuing` 游标记录哪些插件还有下一页                                                                                   |
| 发现（榜单 · 推荐歌单） | `src/plugins/discovery.ts` | `getTopLists` · `getTopListDetail` · `getRecommendSheetTags` · `getRecommendSheetsByTag` · `getMusicSheetInfo` | 曲目在 `musicList`；列表面向单个插件，没有跨插件游标。榜单项、歌单项、标签是插件的凭据，校验后连同原始条目一起随路由参数传递，下一步调用原样交回插件 |

两条来路都经 `host/invoke.ts` 的统一调用通道（未实现 / 抛错 / 超时 / 畸形四类故障的归因）、同一个 `toCandidateTrack`（主键拼接与畸形条目丢弃）、同一个 `CandidateRow`（`src/plugins/ui/candidate-row.tsx`），也都在同一条裁剪线之内：发现层的入口在插件管理页头部，整棵子树只被 Android 侧引用，平台中立门面没有为它增加任何成员。发现能力（`canBrowseTopLists` / `canBrowseSheets`）与搜索能力一样在加载期按方法是否存在判定，未实现的能力在界面上不出现、不报错。
